# Как тестировать Redis код через Docker, Testcontainers и mocks?

> [!NOTE]
> Redis-код лучше тестировать на настоящем Redis, если проверяется поведение TTL, atomic commands, Streams или Pub/Sub. Mocks подходят только для простых unit tests.

## Уровни тестирования

| Уровень | Чем тестировать |
|---|---|
| Unit wrappers | mock Redis client |
| Integration cache logic | real Redis container |
| Streams/queues | real Redis container |
| Pub/Sub | real Redis container |
| Production config | staging Redis |

## Docker для локальных tests

```bash
docker run --name test-redis -p 6379:6379 -d redis:latest
```

Перед каждым тестом:

```ts
await redis.flushDb();
```

Не используй `FLUSHALL` против shared Redis.

## Vitest setup

```ts
import { beforeAll, afterAll, beforeEach } from 'vitest';
import { redis } from '../src/redis';

beforeAll(async () => {
  await redis.connect();
});

beforeEach(async () => {
  await redis.flushDb();
});

afterAll(async () => {
  await redis.quit();
});
```

## Test TTL

```ts
import { expect, it } from 'vitest';

it('stores code with ttl', async () => {
  await redis.set('code:user:1', '123456', {
    EX: 60,
  });

  const ttl = await redis.ttl('code:user:1');

  expect(ttl).toBeGreaterThan(0);
  expect(ttl).toBeLessThanOrEqual(60);
});
```

## Когда mock нормален?

Mocks подходят:

- проверить, что service вызывает `set` с правильным TTL;
- изолировать business logic;
- симулировать Redis outage;
- проверить fallback.

Mocks плохо проверяют:

- atomicity;
- TTL expiry;
- Pub/Sub;
- Streams pending;
- Cluster constraints.

## Мини-шпаргалка

- Реальное поведение Redis тестируй на real Redis.
- Unit tests могут mock-ать client.
- Перед тестом чисти isolated DB.
- Не запускай destructive commands против shared env.
- TTL tests должны учитывать время и допуск.
