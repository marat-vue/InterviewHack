# Что такое “Container-Presentational Pattern”?

> [!summary]
> Container-Presentational Pattern разделяет компонент на слой логики и слой отображения. Container получает данные, управляет состоянием и обработчиками, а Presentational component показывает UI по переданным props.

## Идея паттерна

```text
Container component -> знает, откуда взять данные и что делать
Presentational component -> знает, как эти данные красиво показать
```

Это разделение ответственности.

## Presentational component

```jsx
function UserCard({ name, email, onRefresh }) {
  return (
    <article>
      <h2>{name}</h2>
      <p>{email}</p>
      <button onClick={onRefresh}>Refresh</button>
    </article>
  )
}
```

Такой компонент:

- получает данные через props;
- не знает про API;
- не знает про Redux/Zustand/Query;
- легко тестируется;
- может использоваться в Storybook.

## Container component

```jsx
function UserCardContainer({ userId }) {
  const { data, isLoading, refetch } = useUserQuery(userId)

  if (isLoading) {
    return <UserCardSkeleton />
  }

  return (
    <UserCard
      name={data.name}
      email={data.email}
      onRefresh={refetch}
    />
  )
}
```

Container:

- вызывает hooks;
- получает данные;
- хранит или выбирает state;
- обрабатывает loading/error;
- подготавливает props для UI-компонента.

## Зачем это нужно?

Паттерн помогает:

- отделять бизнес-логику от верстки;
- переиспользовать UI с разными источниками данных;
- проще тестировать отображение;
- использовать компоненты в Storybook;
- уменьшать размер "толстых" компонентов.

## Современный React и кастомные хуки

Сегодня явные containers часто заменяют кастомными хуками:

```jsx
function useUserCard(userId) {
  const { data, isLoading, refetch } = useUserQuery(userId)

  return {
    isLoading,
    user: data,
    refresh: refetch,
  }
}

function UserCardContainer({ userId }) {
  const { user, isLoading, refresh } = useUserCard(userId)

  if (isLoading) {
    return <UserCardSkeleton />
  }

  return <UserCard name={user.name} email={user.email} onRefresh={refresh} />
}
```

Принцип остается тем же: логика отдельно, UI отдельно.

## Когда паттерн может быть лишним?

Если компонент маленький и используется один раз, искусственное разделение на два файла может усложнить код.

```text
Не каждый компонент обязан иметь Container.
Паттерн нужен там, где логика и UI действительно начинают мешать друг другу.
```

## Мини-шпаргалка

- Container отвечает за данные и действия.
- Presentational отвечает за отображение.
- UI-компонент должен быть максимально независимым от источника данных.
- В современном React роль container часто выполняют hooks.
- Не применяй паттерн механически к каждому компоненту.
