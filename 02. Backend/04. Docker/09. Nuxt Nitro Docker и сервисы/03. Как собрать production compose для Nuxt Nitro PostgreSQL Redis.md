# Как собрать production compose для Nuxt Nitro, PostgreSQL и Redis?

> [!NOTE]
> Production Compose для Nuxt/Nitro обычно содержит application service, PostgreSQL, Redis и reverse proxy. Наружу публикуют только публичный вход, а база и Redis остаются во внутренней Docker-сети.

## Базовая структура проекта

```text
project/
  Dockerfile
  compose.yaml
  compose.prod.yaml
  .env.example
  nuxt.config.ts
  package.json
  pnpm-lock.yaml
```

## Production compose без Nginx

```yaml
services:
  app:
    build:
      context: .
    environment:
      NODE_ENV: production
      NITRO_HOST: 0.0.0.0
      NITRO_PORT: 3000
      DATABASE_URL: postgresql://app:${POSTGRES_PASSWORD}@db:5432/app
      REDIS_URL: redis://redis:6379
      NUXT_PUBLIC_SITE_URL: ${NUXT_PUBLIC_SITE_URL}
    ports:
      - "3000:3000"
    depends_on:
      db:
        condition: service_healthy
      redis:
        condition: service_healthy
    restart: unless-stopped

  db:
    image: postgres:18
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
      POSTGRES_DB: app
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app -d app"]
      interval: 5s
      timeout: 3s
      retries: 20
    restart: unless-stopped

  redis:
    image: redis:8-alpine
    command: ["redis-server", "--appendonly", "yes"]
    volumes:
      - redisdata:/data
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 5s
      timeout: 3s
      retries: 20
    restart: unless-stopped

volumes:
  pgdata:
  redisdata:
```

## Почему не публиковать Postgres и Redis?

В production обычно не нужно:

```yaml
db:
  ports:
    - "5432:5432"
redis:
  ports:
    - "6379:6379"
```

Если ports не опубликованы, services все равно доступны внутри Compose network:

```text
app -> db:5432
app -> redis:6379
```

Но снаружи host-машины они не открыты.

## `.env.example`

```env
POSTGRES_PASSWORD=change-me
NUXT_PUBLIC_SITE_URL=https://example.com
```

Production secrets лучше передавать через secret manager, CI/CD variables или Docker secrets, а не хранить реальные значения в git.

## Как запускать?

```bash
docker compose --env-file .env up -d --build
docker compose ps
docker compose logs -f app
```

Проверить сеть:

```bash
docker compose exec app node -e "console.log(process.env.DATABASE_URL)"
docker compose exec db psql -U app app
docker compose exec redis redis-cli ping
```

## Как добавить migration service?

```yaml
services:
  migrate:
    build:
      context: .
      target: build
    command: pnpm prisma migrate deploy
    environment:
      DATABASE_URL: postgresql://app:${POSTGRES_PASSWORD}@db:5432/app
    depends_on:
      db:
        condition: service_healthy

  app:
    depends_on:
      migrate:
        condition: service_completed_successfully
      redis:
        condition: service_healthy
```

Для реального production часто лучше запускать migrations отдельным CI/CD шагом до rollout приложения.

## Что отвечать на собеседовании?

Production Compose для Nuxt/Nitro описывает приложение как Node server, который слушает `0.0.0.0:3000` и запускается из `.output/server/index.mjs`. Postgres и Redis поднимаются отдельными services, данные лежат в named volumes, приложение обращается к ним по service names, а readiness проверяется healthcheck-ами. Наружу обычно публикуют только app или reverse proxy.

## Частые ошибки

- Публиковать `5432` и `6379` наружу без необходимости.
- Думать, что `depends_on` без healthcheck ждет готовности базы.
- Хранить реальные passwords в compose-файле.
- Делать Redis persistent без понимания, какие данные в нем лежат.
- Запускать migrations из каждой реплики приложения.
- Не задавать restart policy.

## Мини-шпаргалка

- Nuxt app: `NITRO_HOST=0.0.0.0`.
- Postgres URL: `db:5432`.
- Redis URL: `redis:6379`.
- Data: named volumes.
- Readiness: healthcheck.
- Public ports: минимум.
