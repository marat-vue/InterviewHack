# Как составлять валидаторы Zod по шагам?

> [!summary]
> Хороший Zod validator строится от формы входных данных к бизнес-правилам: сначала описывают типы, потом ограничения, затем нормализацию, cross-field checks, TypeScript-типы и подключение к NestJS pipe.

## Шаг 1. Определи границу доверия

Zod нужен там, где данные приходят извне:

- `body` HTTP-запроса;
- `query` и `params`;
- `.env`;
- webhook payload;
- ответ внешнего API;
- сообщение из queue.

Внутренний объект, который уже создан твоим кодом, обычно не нужно валидировать повторно на каждом шаге.

## Шаг 2. Опиши базовую форму

```ts
import { z } from 'zod';

export const createArticleSchema = z.object({
  title: z.string(),
  content: z.string(),
  tags: z.array(z.string()),
  published: z.boolean(),
});
```

На этом этапе schema отвечает только на вопрос: "какая структура вообще ожидается?"

## Шаг 3. Добавь ограничения

```ts
export const createArticleSchema = z.object({
  title: z.string().trim().min(3).max(120),
  content: z.string().trim().min(20).max(20_000),
  tags: z.array(z.string().trim().min(1).max(30)).max(10).default([]),
  published: z.boolean().default(false),
});
```

Ограничения должны отражать реальные правила продукта и базы данных. Если в Prisma поле `title String @db.VarChar(120)`, validator тоже должен ограничивать `title` до 120 символов.

## Шаг 4. Подумай о coercion для query params

HTTP query params приходят строками.

```ts
export const listArticlesQuerySchema = z.object({
  page: z.coerce.number().int().min(1).default(1),
  limit: z.coerce.number().int().min(1).max(100).default(20),
  search: z.string().trim().min(1).max(100).optional(),
  published: z.coerce.boolean().optional(),
});
```

Без coercion `?page=2` не пройдет `z.number()`, потому что фактически это строка `'2'`.

## Шаг 5. Раздели create и update

Create DTO обычно требует обязательные поля. Update DTO обычно частичный.

```ts
export const createUserSchema = z.object({
  email: z.email(),
  name: z.string().trim().min(2).max(100),
  password: z.string().min(8).max(100),
});

export const updateUserSchema = createUserSchema
  .omit({ email: true, password: true })
  .partial();
```

Так ты не даешь пользователю менять поля, которые не должны обновляться через этот endpoint.

## Шаг 6. Добавь cross-field validation

Когда правило зависит от нескольких полей, нужен `superRefine`.

```ts
export const registerSchema = z.object({
  email: z.email(),
  password: z.string().min(8),
  confirmPassword: z.string(),
}).superRefine((data, ctx) => {
  if (data.password !== data.confirmPassword) {
    ctx.addIssue({
      code: 'custom',
      path: ['confirmPassword'],
      message: 'Passwords do not match',
    });
  }
});
```

`path` важен для frontend: он показывает, к какому полю относится ошибка.

## Шаг 7. Нормализуй данные

```ts
export const createUserSchema = z.object({
  email: z.string().trim().toLowerCase().pipe(z.email()),
  name: z.string().trim().min(2).max(100),
});
```

Нормализация помогает не хранить в базе `USER@EXAMPLE.COM` и `user@example.com` как разные значения.

## Шаг 8. Выведи TypeScript-типы

```ts
export type CreateUserInput = z.infer<typeof createUserSchema>;
export type ListArticlesQuery = z.infer<typeof listArticlesQuerySchema>;
```

Теперь controller, service и tests используют тип, полученный из validation schema.

## Шаг 9. Подключи validator к NestJS

```ts
@Post()
create(
  @Body(new ZodValidationPipe(createUserSchema))
  body: CreateUserInput,
) {
  return this.usersService.create(body);
}
```

Для query:

```ts
@Get()
findAll(
  @Query(new ZodValidationPipe(listArticlesQuerySchema))
  query: ListArticlesQuery,
) {
  return this.articlesService.findAll(query);
}
```

## Шаг 10. Приведи ошибки к удобному формату

```ts
if (!result.success) {
  throw new BadRequestException({
    message: 'Validation failed',
    issues: result.error.issues.map((issue) => ({
      path: issue.path.join('.'),
      message: issue.message,
      code: issue.code,
    })),
  });
}
```

Так frontend получает понятный список ошибок, а не просто строку "Bad Request".

## Полный пример для CRUD

```ts
export const createProductSchema = z.object({
  title: z.string().trim().min(2).max(120),
  price: z.coerce.number().positive(),
  categoryId: z.coerce.number().int().positive(),
  tags: z.array(z.string().trim().min(1)).max(10).default([]),
});

export const updateProductSchema = createProductSchema.partial();

export const listProductsQuerySchema = z.object({
  page: z.coerce.number().int().min(1).default(1),
  limit: z.coerce.number().int().min(1).max(100).default(20),
  categoryId: z.coerce.number().int().positive().optional(),
  search: z.string().trim().min(1).optional(),
  sortBy: z.enum(['createdAt', 'price', 'title']).default('createdAt'),
  sortOrder: z.enum(['asc', 'desc']).default('desc'),
});

export type CreateProductInput = z.infer<typeof createProductSchema>;
export type UpdateProductInput = z.infer<typeof updateProductSchema>;
export type ListProductsQuery = z.infer<typeof listProductsQuerySchema>;
```

## Как связать Zod с Prisma?

Zod валидирует вход, Prisma пишет в базу. Хорошее правило: Zod schema должна быть совместима с Prisma schema, но не обязана повторять ее один в один.

```prisma
model Product {
  id         Int      @id @default(autoincrement())
  title      String   @db.VarChar(120)
  price      Decimal  @db.Decimal(10, 2)
  categoryId Int
  createdAt  DateTime @default(now())
}
```

```ts
const createProductSchema = z.object({
  title: z.string().trim().min(2).max(120),
  price: z.coerce.number().positive(),
  categoryId: z.coerce.number().int().positive(),
});
```

В service можно преобразовать `number` в `Prisma.Decimal`, если проект хранит деньги через Decimal.

## Частые ошибки

| Ошибка | Почему плохо | Как лучше |
|---|---|---|
| Валидировать только TypeScript-типом | TS исчезает в runtime | использовать Zod на входе |
| Делать все поля optional в create | в базу попадут неполные данные | create и update schemas отдельно |
| Не ограничивать `limit` | можно случайно нагрузить базу | `max(100)` |
| Не нормализовать email | дубли пользователей | `trim().toLowerCase()` |
| Использовать `z.any()` | validation почти исчезает | `z.unknown()` или точная schema |
| Не указывать `path` в `superRefine` | frontend не поймет поле ошибки | `ctx.addIssue({ path: [...] })` |

## Мини-шпаргалка

- Начинай с границы доверия: body, query, params, env, webhook.
- Сначала структура, потом ограничения, потом нормализация.
- Query params почти всегда требуют `z.coerce`.
- Для `PATCH` удобно `partial`, но запрещенные поля лучше убрать через `omit`.
- Cross-field rules делай через `superRefine`.
- Ошибки возвращай с `path`, `message` и `code`.
- Zod schema должна дружить с Prisma schema и ограничениями базы.
