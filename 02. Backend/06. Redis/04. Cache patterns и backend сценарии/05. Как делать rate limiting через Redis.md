# Как делать rate limiting через Redis?

> [!NOTE]
> Redis часто используют для rate limiting, потому что `INCR` атомарен, TTL удаляет счетчики автоматически, а все инстансы приложения видят один общий лимит.

## Fixed window counter

Простой вариант:

```ts
export async function fixedWindowLimit(ip: string) {
  const key = `rate:ip:${ip}:${Math.floor(Date.now() / 60_000)}`;
  const count = await redis.incr(key);

  if (count === 1) {
    await redis.expire(key, 60);
  }

  return count <= 100;
}
```

Плюс: просто.

Минус: на границе окна пользователь может сделать почти двойной burst.

## Sliding window через sorted set

```ts
export async function slidingWindowLimit(userId: string) {
  const key = `rate:user:${userId}`;
  const now = Date.now();
  const windowMs = 60_000;

  await redis.zRemRangeByScore(key, 0, now - windowMs);
  await redis.zAdd(key, {
    score: now,
    value: `${now}:${crypto.randomUUID()}`,
  });
  await redis.expire(key, 60);

  const count = await redis.zCard(key);

  return count <= 100;
}
```

Плюс: честнее распределяет запросы.

Минус: дороже и требует cleanup.

## Token bucket идея

Token bucket хранит:

- количество токенов;
- timestamp последнего refill.

Для атомарности лучше Lua script, потому что нужно прочитать состояние, пересчитать tokens и записать обратно как одну операцию.

## Что учитывать в key?

Key должен учитывать:

- user id или IP;
- route group;
- tenant;
- auth state;
- window;
- environment.

Пример:

```txt
prod:api:rate:user:42:route:login
prod:api:rate:ip:203.0.113.10:route:signup
```

## Где делать rate limit?

Слои:

- CDN/WAF для грубой защиты;
- API gateway/reverse proxy;
- backend middleware для бизнес-лимитов;
- auth-specific limiter для login/reset endpoints.

Redis хорош на backend-слое, но не заменяет DDoS protection.

## Мини-шпаргалка

- Fixed window: `INCR` + `EXPIRE`.
- Sliding window: sorted set с timestamps.
- Token bucket: лучше Lua.
- Redis делает limiter общим для всех инстансов.
- Login/reset routes лимитируй строже.
