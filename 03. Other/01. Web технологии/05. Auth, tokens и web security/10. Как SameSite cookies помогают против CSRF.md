# Как SameSite cookies помогают против CSRF?

> [!summary]
> `SameSite` ограничивает отправку cookies в cross-site контексте. Это снижает риск CSRF, потому что browser может не приложить session cookie к запросу, инициированному с чужого сайта.

## SameSite Strict

```http
Set-Cookie: sid=abc; SameSite=Strict; Secure; HttpOnly
```

Cookie отправляется только в same-site requests.

Плюс: сильнее ограничивает CSRF. Минус: может ломать удобные сценарии перехода с внешних ссылок.

## SameSite Lax

```http
Set-Cookie: sid=abc; SameSite=Lax; Secure; HttpOnly
```

`Lax` часто является практичным default для session cookies. Он ограничивает многие cross-site subrequests, но сохраняет часть обычной навигации.

## SameSite None

```http
Set-Cookie: sid=abc; SameSite=None; Secure; HttpOnly
```

`None` нужен, когда cookie должна отправляться cross-site, например:

- frontend и API на разных sites;
- embedded widgets;
- third-party integrations.

Для `SameSite=None` нужен `Secure`.

## Почему SameSite не всегда достаточно?

Причины:

- старые browser edge cases;
- сложные cross-site auth flows;
- subdomain/site нюансы;
- XSS может обойти CSRF-слои внутри origin;
- sensitive operations лучше защищать несколькими слоями.

## Мини-шпаргалка

- `SameSite=Strict` максимально ограничивает cross-site отправку.
- `SameSite=Lax` часто хороший баланс.
- `SameSite=None` требует `Secure`.
- SameSite снижает CSRF-риск.
- Для критичных actions добавляй CSRF token и Origin checks.
