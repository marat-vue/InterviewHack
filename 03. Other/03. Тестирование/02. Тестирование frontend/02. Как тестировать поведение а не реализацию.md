# Как тестировать поведение, а не реализацию?

> [!summary]
> Тестирование поведения означает проверку того, что видит и делает пользователь или внешний потребитель компонента. Тестирование реализации проверяет внутренние переменные, методы и структуру кода, из-за чего тесты часто ломаются при безвредном рефакторинге.

## Пример теста реализации

```ts
test('sets isOpen to true', async () => {
  const wrapper = mount(Dropdown);

  await wrapper.vm.open();

  expect(wrapper.vm.isOpen).toBe(true);
});
```

Такой тест знает слишком много о внутренностях компонента.

## Пример теста поведения

```ts
test('shows menu after clicking trigger', async () => {
  const wrapper = mount(Dropdown);

  await wrapper.get('[data-testid="dropdown-trigger"]').trigger('click');

  expect(wrapper.text()).toContain('Настройки');
});
```

Этот тест выдержит рефакторинг: можно переименовать `isOpen`, заменить method, изменить Composition API на Options API, а пользовательский сценарий останется прежним.

## Как понять, что тест привязан к реализации?

Тревожные сигналы:

- частое обращение к `wrapper.vm`;
- проверка приватных методов;
- проверка точной структуры HTML без необходимости;
- тест падает после переименования CSS-класса;
- тест повторяет внутренний алгоритм.

## Что проверять вместо этого?

Проверяй:

- текст, который видит пользователь;
- наличие или отсутствие элементов;
- disabled/loading/error states;
- emitted events;
- вызовы внешних зависимостей;
- переходы по router;
- изменения store, если это часть сценария.

## Мини-шпаргалка

- Поведение - то, что видно снаружи.
- Реализация - внутренние методы, переменные и детали.
- Чем меньше тест знает о внутренностях, тем он стабильнее.
- `wrapper.vm` используй осторожно.
- Сначала думай как пользователь, потом как разработчик.
