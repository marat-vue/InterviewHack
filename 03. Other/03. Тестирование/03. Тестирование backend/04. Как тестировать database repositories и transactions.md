# Как тестировать database, repositories и transactions?

> [!summary]
> Работу с базой тестируют на уровне repositories, services или endpoints. Важно изолировать данные между тестами, проверять реальные constraints и отдельно покрывать транзакции, rollback и сложные запросы.

## Почему базу нельзя всегда мокать?

Моки полезны для unit tests, но они не проверяют:

- SQL-запросы;
- ORM mapping;
- unique constraints;
- foreign keys;
- cascade behavior;
- transaction rollback;
- индексы и сортировку;
- реальные ошибки драйвера.

Поэтому важные сценарии базы лучше проверять на тестовой БД.

## Как готовить тестовую БД?

Типичные подходы:

- отдельная database/schema для тестов;
- миграции перед запуском;
- очистка таблиц после теста;
- transaction rollback после каждого теста;
- Testcontainers для изолированных БД в CI.

## Пример repository test

```ts
test('finds active users by company', async () => {
  await prisma.company.create({
    data: {
      id: 1,
      name: 'Acme',
      users: {
        create: [
          { email: 'active@example.com', isActive: true },
          { email: 'blocked@example.com', isActive: false },
        ],
      },
    },
  });

  const users = await repository.findActiveByCompanyId(1);

  expect(users).toHaveLength(1);
  expect(users[0].email).toBe('active@example.com');
});
```

## Как тестировать transaction rollback?

Сценарий: создаем order и order items. Если создание item падает, order не должен остаться в базе.

```ts
await expect(service.createOrder(invalidInput)).rejects.toThrow();

const orders = await prisma.order.findMany();
expect(orders).toHaveLength(0);
```

## Мини-шпаргалка

- Моки не проверяют реальное поведение БД.
- Для repositories полезна тестовая database.
- Очищай данные между тестами.
- Проверяй constraints, relations и transactions.
- Rollback надо проверять через итоговое состояние базы.
