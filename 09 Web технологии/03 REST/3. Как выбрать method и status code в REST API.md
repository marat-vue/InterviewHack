# Как выбрать method и status code в REST API?

> [!summary]
> В REST method показывает намерение, а status code показывает результат. Хороший API последовательно связывает `GET/POST/PATCH/DELETE` с `200/201/204/400/401/403/404/409/422`.

## Таблица выбора

| Endpoint | Успех | Ошибки |
|---|---|---|
| `GET /users` | `200` + array/page | `401`, `403` |
| `GET /users/:id` | `200` + object | `401`, `403`, `404` |
| `POST /users` | `201` + object | `400`, `409`, `422` |
| `PATCH /users/:id` | `200` + object или `204` | `400`, `401`, `403`, `404`, `422` |
| `DELETE /users/:id` | `204` | `401`, `403`, `404` |

## Создание

```http
POST /api/users

HTTP/1.1 201 Created
Location: /api/users/42
```

Если email уже занят:

```http
HTTP/1.1 409 Conflict
```

Если email невалидный:

```http
HTTP/1.1 422 Unprocessable Content
```

## Обновление

`PATCH` обычно лучше для частичного обновления:

```http
PATCH /api/users/42

{
  "name": "Ann"
}
```

Ответ может быть:

- `200` + обновленный объект;
- `204` без body.

В одном API лучше выбрать единый стиль.

## Удаление

```http
DELETE /api/users/42

HTTP/1.1 204 No Content
```

Если ресурс уже удален, команды могут выбрать:

- `404`, потому что ресурса нет;
- `204`, если delete считают idempotent и не хотят раскрывать детали.

Главное - зафиксировать это в контракте.

## Мини-шпаргалка

- Method отвечает за действие.
- Status code отвечает за результат.
- `POST` creation -> часто `201`.
- `DELETE` -> часто `204`.
- `401` и `403` не взаимозаменяемы.
- `409` хорош для conflicts, `422` - для domain validation.
