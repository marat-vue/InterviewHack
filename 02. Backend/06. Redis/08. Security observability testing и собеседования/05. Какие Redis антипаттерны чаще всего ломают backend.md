# Какие Redis антипаттерны чаще всего ломают backend?

> [!NOTE]
> Redis ломают не сложные фичи, а простые ошибки: ключи без TTL, `KEYS *`, client на каждый request, огромные JSON, Pub/Sub вместо reliable queue и отсутствие fallback.

## Антипаттерн 1: `KEYS *` в production

Плохо:

```redis
KEYS session:*
```

Лучше:

```redis
SCAN 0 MATCH session:* COUNT 100
```

## Антипаттерн 2: cache без TTL

Плохо:

```redis
SET cache:user:1 value
```

Лучше:

```redis
SET cache:user:1 value EX 300
```

## Антипаттерн 3: один общий key для private data

Плохо:

```txt
cache:dashboard
```

Если dashboard зависит от user/tenant, это риск утечки данных.

Лучше:

```txt
cache:tenant:42:user:1:dashboard
```

## Антипаттерн 4: Redis client на каждый request

Создание connection на каждый запрос приводит к latency и maxclients проблемам.

Лучше: singleton на процесс.

## Антипаттерн 5: огромный JSON string

Плохо:

```txt
cache:all-products -> 100 MB JSON
```

Лучше:

- pagination;
- sharding by category/page;
- smaller payload;
- search/index layer;
- `UNLINK` для удаления больших keys.

## Антипаттерн 6: Pub/Sub для важных jobs

Pub/Sub не хранит сообщения. Worker offline - сообщение потеряно.

Для reliable processing используй Streams или очередь.

## Антипаттерн 7: lock без TTL

Плохо:

```redis
SET lock:job:42 locked NX
```

Если worker упадет, lock останется навсегда.

Лучше:

```redis
SET lock:job:42 token NX PX 30000
```

## Мини-шпаргалка

- Не используй `KEYS` в production.
- TTL для cache обязателен.
- User/tenant входят в private cache key.
- Client создается один раз.
- Big keys режутся на части.
- Pub/Sub не reliable queue.
- Locks всегда с TTL и token.
