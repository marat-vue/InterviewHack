# Как тестировать controllers, routes и HTTP endpoints?

> [!summary]
> HTTP endpoints тестируют через запросы к приложению: method, URL, body, headers, status code и response body. Такие тесты проверяют маршрутизацию, validation, guards, interceptors, filters и связь controller с application layer.

## Что проверяет endpoint test?

Endpoint test отвечает:

- правильный ли route выбран;
- корректно ли разобран body/query/params;
- сработала ли validation;
- сработала ли authentication;
- вернулся ли правильный status code;
- вернулся ли правильный response body;
- изменилась ли база, если endpoint что-то создает.

## Пример HTTP-теста

```ts
await request(app.getHttpServer())
  .post('/users')
  .send({ email: 'ann@example.com', password: 'secret123' })
  .expect(201)
  .expect(({ body }) => {
    expect(body.id).toEqual(expect.any(Number));
    expect(body.email).toBe('ann@example.com');
    expect(body.password).toBeUndefined();
  });
```

## Что проверять в status codes?

| Ситуация | Status |
|---|---|
| создан ресурс | `201` |
| успешное чтение | `200` |
| неверный input | `400` |
| нет authentication | `401` |
| нет permissions | `403` |
| ресурс не найден | `404` |
| конфликт данных | `409` |
| ошибка сервера | `500` |

## Нужно ли мокать service?

Есть два подхода.

В unit-тесте controller можно замокать service:

```ts
usersService.create.mockResolvedValue({ id: 1, email: 'ann@example.com' });
```

В integration-тесте лучше поднять больше настоящих частей приложения и проверить путь ближе к реальности.

## Мини-шпаргалка

- Endpoint test отправляет реальный HTTP-запрос в тестовое приложение.
- Проверяй status, body, headers и side effects.
- Validation, auth и permissions важно проверять отдельно.
- Controller unit test дешевле, integration endpoint test реалистичнее.
- Не возвращай sensitive fields вроде password.
