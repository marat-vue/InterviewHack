# Как масштабировать Redis: hot keys, big keys и performance?

> [!NOTE]
> Redis performance проблемы часто связаны не с Redis как таковым, а с моделью ключей: один горячий ключ, огромные структуры, команды O(N), отсутствие TTL или слишком много connections.

## Что такое hot key?

Hot key - ключ, к которому обращаются слишком часто:

```txt
cache:homepage
feature-flags:global
leaderboard:global
```

Риски:

- один key/node становится bottleneck;
- в Cluster hot key не распределяется;
- latency растет;
- cache rebuild вызывает stampede.

## Как бороться с hot keys?

- локальный in-process LRU cache поверх Redis;
- TTL jitter;
- SWR;
- sharding hot key вручную;
- precompute;
- CDN для public data;
- уменьшить payload.

Пример local cache:

```ts
const localCache = new Map<string, {
  value: unknown;
  expiresAt: number;
}>();
```

## Что такое big key?

Big key - ключ, который занимает много памяти или содержит очень много элементов.

Примеры:

```txt
hash на 1 000 000 fields
list на 5 000 000 items
string на 50 MB
stream без trimming
```

## Как бороться с big keys?

- разбить по времени: `events:2026-08-06`;
- разбить по tenant/user;
- ограничить list через `LTRIM`;
- stream через `XTRIM`;
- sorted set cleanup через `ZREMRANGEBYSCORE`;
- не хранить огромный JSON;
- удалять через `UNLINK`.

## Connections

Слишком много clients тоже проблема.

Смотри:

```redis
INFO clients
CLIENT LIST
```

В Node.js не создавай client на каждый request.

## Pipelining

Используй batching, когда много мелких команд:

```ts
await Promise.all(keys.map((key) => redis.expire(key, 300)));
```

Но не отправляй огромный batch одним куском.

## Мини-шпаргалка

- Hot key = слишком популярный ключ.
- Big key = слишком большой ключ.
- Cluster не спасает от одного hot key.
- O(N) команды на big key опасны.
- Лимитируй размер структур.
- Используй pipelining умеренно.
