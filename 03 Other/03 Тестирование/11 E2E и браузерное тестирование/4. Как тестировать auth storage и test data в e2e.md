# Как тестировать auth, storage и test data в e2e?

> [!summary]
> E2E-тесты должны иметь надежный способ входа и подготовки данных. Для auth часто используют setup-проект и сохраненный storage state, а test data создают через API, seed helper или отдельную тестовую БД.

## Почему нельзя логиниться в каждом тесте?

Если каждый тест открывает login page, вводит email/password и ждет redirect, весь набор становится:

- медленнее;
- более flaky;
- зависимым от login UI;
- сложнее для debug.

Login flow нужно покрыть отдельным e2e-тестом, а для остальных тестов можно переиспользовать auth state.

## Storage state

Идея:

1. Один setup-тест логинится.
2. Playwright сохраняет cookies/localStorage.
3. Остальные тесты стартуют уже авторизованными.

```ts
// auth.setup.ts
import { test as setup } from '@playwright/test';

setup('authenticate', async ({ page }) => {
  await page.goto('/login');
  await page.getByLabel('Email').fill('ann@example.com');
  await page.getByLabel('Password').fill('secret123');
  await page.getByRole('button', { name: 'Войти' }).click();

  await page.context().storageState({ path: 'playwright/.auth/user.json' });
});
```

## Test data

Хорошие варианты:

- создать данные через API перед тестом;
- seed database;
- использовать factory endpoint только в test environment;
- очищать данные после теста;
- делать уникальные email/id.

## Network mocking в e2e

Иногда можно перехватить запрос:

```ts
await page.route('**/api/products', async (route) => {
  await route.fulfill({
    json: [{ id: 1, title: 'Keyboard' }],
  });
});
```

Но если e2e должен проверить настоящий backend, network лучше не мокать.

## Мини-шпаргалка

- Login flow тестируй отдельно.
- Для остальных e2e используй storage state.
- Test data должна быть изолированной.
- Уникальные значения уменьшают конфликты.
- Network mocking в e2e используй осознанно.
