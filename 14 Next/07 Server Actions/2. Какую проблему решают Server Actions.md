# Какую проблему решают Server Actions?

> [!summary]
> Server Actions уменьшают boilerplate вокруг внутренних мутаций: не нужно вручную создавать endpoint, писать client `fetch`, парсить request body и синхронизировать типы для каждой формы. Серверная функция становится частью UI flow.

## Как было через API endpoint?

Клиент:

```tsx
async function handleSubmit(event: React.FormEvent<HTMLFormElement>) {
  event.preventDefault()

  const formData = new FormData(event.currentTarget)

  await fetch('/api/posts', {
    method: 'POST',
    body: formData,
  })
}
```

Endpoint:

```ts
export async function POST(request: Request) {
  const formData = await request.formData()
  await createPost(formData)

  return Response.json({ ok: true })
}
```

## Как стало через Server Action?

```tsx
<form action={createPost}>
  <input name="title" />
  <button>Create</button>
</form>
```

```ts
'use server'

export async function createPost(formData: FormData) {
  await db.post.create({
    data: { title: String(formData.get('title')) },
  })
}
```

Меньше промежуточного кода.

## Что Server Actions дают?

- меньше ручного `fetch`;
- проще формы;
- серверная типизация ближе к UI;
- удобная revalidation после mutation;
- интеграция с `redirect`;
- возможность использовать `useActionState`, `useFormStatus`, `useOptimistic`.

## Что они не решают?

Server Actions не отменяют:

- авторизацию;
- валидацию;
- обработку ошибок;
- транзакции;
- rate limiting;
- CSRF/security considerations;
- бизнес-архитектуру.

## Что отвечать на собеседовании?

Server Actions решают проблему лишней HTTP-прослойки для внутренних мутаций. Они позволяют связать форму или компонент с серверной функцией напрямую, но это не освобождает от безопасности, валидации и правильной revalidation.

## Частые ошибки

- Убирать всю архитектуру в один action-файл.
- Не проверять пользователя внутри action.
- Возвращать сырые ошибки пользователю.
- Использовать action вместо public API для внешних клиентов.
- Забывать invalidation cache.

## Мини-шпаргалка

- Меньше boilerplate для forms.
- Нет ручного client `fetch`.
- Удобно для internal mutations.
- После mutation часто нужен revalidate.
- Security остается обязательной.
- Для внешнего доступа нужен Route Handler.
