# Как React принимает решение о перерисовке компонента?

> [!summary]
> React запускает render компонента, когда меняются его state, props, context или когда перерендерился родитель. Но render компонента не всегда означает изменение DOM: React сначала вычисляет новое дерево, затем применяет только необходимые изменения.

## Что может вызвать render?

Основные причины:

- обновился state компонента;
- изменились props от родителя;
- изменилось значение context;
- родительский компонент отрендерился;
- внешний store уведомил подписчиков;
- в development Strict Mode может вызывать render повторно для проверок.

## Пример со state

```jsx
function Counter() {
  const [count, setCount] = useState(0)

  return (
    <button onClick={() => setCount(count + 1)}>
      {count}
    </button>
  )
}
```

`setCount` планирует обновление. React вызывает компонент снова и получает новый JSX.

## Render не равен DOM update

Компонент может отрендериться, но DOM не изменится:

```jsx
function Title({ text }) {
  return <h1>{text}</h1>
}
```

Если `text` остался тем же, React может не менять DOM, хотя функция компонента была вызвана.

## Почему рендерится ребенок?

```jsx
function Parent() {
  const [count, setCount] = useState(0)

  return (
    <>
      <button onClick={() => setCount(count + 1)}>+</button>
      <Child />
    </>
  )
}
```

Когда `Parent` рендерится, React обычно заново рассматривает и `Child`. Если это дорого, можно использовать `memo`, но только после понимания причины и измерений.

## Как уменьшать лишние render?

- Разделять компоненты.
- Держать state ближе к месту использования.
- Не создавать тяжелые вычисления в render без нужды.
- Использовать `memo` для стабильных props.
- Использовать `useMemo` и `useCallback` там, где это реально помогает.
- Профилировать через React DevTools.

## Мини-шпаргалка

- Render вызывается из-за state, props, context или render родителя.
- Render - это вычисление UI, а не обязательно изменение DOM.
- React применяет изменения на commit-этапе.
- Оптимизацию стоит делать после профилирования.
- Хорошая структура state часто важнее случайной мемоизации.
