# Как передача callback-функций влияет на рендер?

> [!summary]
> Callback-функции часто передают детям через props, чтобы ребенок мог сообщить родителю о событии. Новая функция создается на каждом render, и это нормально само по себе. Проблемой это становится, если callback ломает мемоизацию дорогих дочерних компонентов.

## Базовый пример

```jsx
function TodoItem({ todo, onToggle }) {
  return (
    <label>
      <input
        type="checkbox"
        checked={todo.done}
        onChange={() => onToggle(todo.id)}
      />
      {todo.title}
    </label>
  )
}
```

`onToggle` - callback prop. Ребенок вызывает его, родитель обновляет state.

## Почему новая функция может быть проблемой?

```jsx
<SlowList onSelect={(id) => selectItem(id)} />
```

На каждом render создается новая функция:

```text
prevOnSelect !== nextOnSelect
```

Если `SlowList` обернут в `memo`, новый callback может заставить его рендериться снова.

## Когда нужен useCallback?

```jsx
const handleSelect = useCallback((id) => {
  selectItem(id)
}, [selectItem])

return <SlowList onSelect={handleSelect} />
```

`useCallback` полезен, если:

- дочерний компонент дорогой;
- он обернут в `memo`;
- остальные props стабильны;
- Profiler показывает проблему.

## Когда useCallback не нужен?

```jsx
<button onClick={() => setCount(count + 1)}>
  +
</button>
```

Для обычного DOM-элемента такая inline-функция обычно нормальна. Не нужно мемоизировать каждый handler.

## Как избежать лишних dependencies?

Для обновления state от предыдущего значения:

```jsx
const increment = useCallback(() => {
  setCount((count) => count + 1)
}, [])
```

Updater function позволяет не зависеть от `count`.

## Мини-шпаргалка

- Callback props нужны для связи ребенка с родителем.
- Новая функция на render - нормально.
- Проблема возникает с дорогими memo-компонентами.
- `useCallback` стабилизирует ссылку на функцию.
- Не используй `useCallback` механически.
