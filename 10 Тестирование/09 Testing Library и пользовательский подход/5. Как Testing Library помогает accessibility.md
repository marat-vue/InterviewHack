# Как Testing Library помогает accessibility?

> [!summary]
> Testing Library не заменяет полноценный accessibility audit, но заставляет писать тесты через роли, label и accessible name. Если элемент трудно найти через пользовательский query, это часто сигнал, что интерфейс плохо доступен.

## Почему `getByRole` важен?

```ts
screen.getByRole('button', { name: 'Закрыть' });
```

Такой query проверяет, что:

- элемент действительно является кнопкой;
- у него есть понятное accessible name;
- пользователь вспомогательных технологий сможет его найти.

## Пример плохого UI

```html
<div class="button" @click="save">Save</div>
```

Такой элемент может выглядеть как кнопка, но для accessibility это не настоящая кнопка.

Лучше:

```html
<button type="button">Save</button>
```

## Labels для inputs

Плохо:

```html
<input placeholder="Email" />
```

Лучше:

```html
<label for="email">Email</label>
<input id="email" />
```

Тогда тест:

```ts
screen.getByLabelText('Email');
```

## Keyboard navigation

```ts
const user = userEvent.setup();

await user.tab();
expect(screen.getByRole('button', { name: 'Закрыть' })).toHaveFocus();
```

Так можно проверять focus order и доступность без мыши.

## Мини-шпаргалка

- Testing Library подталкивает к accessible UI.
- `getByRole` проверяет семантику и accessible name.
- `getByLabelText` требует нормальной связи label/input.
- `user.tab` помогает проверять keyboard navigation.
- Accessibility tests не заменяют ручную проверку, но ловят много проблем.
