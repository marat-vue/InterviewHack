# SRP в React-компонентах

> [!summary]
> SRP, или Single Responsibility Principle, означает, что у компонента должна быть одна понятная причина для изменения. В React это помогает разделять UI, данные, бизнес-логику, side effects и композицию страницы.

## Как понять SRP в React?

Не обязательно, что компонент должен делать "только одну строку JSX". Важно, чтобы у него была одна ответственность.

Хорошие ответственности:

- `Button` - отрисовать кнопку;
- `UserCard` - показать пользователя;
- `useUserProfile` - получить и подготовить данные профиля;
- `ProfilePage` - собрать страницу профиля;
- `CheckoutForm` - управлять формой оформления заказа.

## Признаки нарушения SRP

Компонент становится проблемным, если он одновременно:

- делает API-запросы;
- содержит сложную бизнес-логику;
- управляет большим количеством unrelated state;
- рисует крупный JSX;
- форматирует данные;
- знает детали роутинга;
- управляет модалками, таблицами и формами сразу.

## Плохой пример

```jsx
function UserProfilePage() {
  const [user, setUser] = useState(null)
  const [isEditing, setIsEditing] = useState(false)
  const [error, setError] = useState(null)

  useEffect(() => {
    fetch('/api/user')
      .then((response) => response.json())
      .then(setUser)
      .catch(setError)
  }, [])

  async function deleteUser() {
    await fetch(`/api/users/${user.id}`, { method: 'DELETE' })
    setUser(null)
  }

  if (error) return <p>Error</p>
  if (!user) return <p>Loading</p>

  return (
    <main>
      <h1>{user.name}</h1>
      <button onClick={() => setIsEditing(true)}>Edit</button>
      <button onClick={deleteUser}>Delete</button>
      {isEditing && <EditUserForm user={user} />}
    </main>
  )
}
```

Компонент отвечает почти за все.

## Более аккуратное разделение

Логика данных:

```jsx
function useUserProfile() {
  const { data, error, isLoading } = useUserQuery()
  const deleteUser = useDeleteUserMutation()

  return {
    user: data,
    error,
    isLoading,
    deleteUser,
  }
}
```

UI:

```jsx
function UserProfileView({ user, onDelete, onEdit }) {
  return (
    <main>
      <h1>{user.name}</h1>
      <button onClick={onEdit}>Edit</button>
      <button onClick={onDelete}>Delete</button>
    </main>
  )
}
```

Композиция:

```jsx
function UserProfilePage() {
  const profile = useUserProfile()
  const [isEditing, setIsEditing] = useState(false)

  if (profile.error) return <ErrorMessage error={profile.error} />
  if (profile.isLoading) return <ProfileSkeleton />

  return (
    <>
      <UserProfileView
        user={profile.user}
        onDelete={profile.deleteUser}
        onEdit={() => setIsEditing(true)}
      />
      {isEditing && <EditUserForm user={profile.user} />}
    </>
  )
}
```

## Не дробить механически

SRP не требует создавать 10 файлов для каждой кнопки. Иногда один компонент с небольшим state и JSX абсолютно нормален.

Хороший вопрос:

```text
Какая причина заставит этот компонент измениться?
```

Если ответов слишком много, компонент пора разделить.

## Мини-шпаргалка

- SRP = одна понятная причина для изменения.
- UI, data fetching и бизнес-логику часто лучше разделять.
- Custom hooks хорошо подходят для логики.
- Presentational components хорошо подходят для UI.
- Не нужно дробить код ради самого дробления.
