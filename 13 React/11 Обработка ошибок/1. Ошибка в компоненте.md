# Ошибка в компоненте

> [!summary]
> Ошибка в React-компоненте может сломать часть дерева или все приложение, если рядом нет Error Boundary. React не может безопасно продолжать render поврежденного поддерева, поэтому ошибку нужно локализовать и показать запасной UI.

## Пример ошибки render

```jsx
function UserCard({ user }) {
  return <h2>{user.name}</h2>
}
```

Если `user` равен `null`, компонент выбросит ошибку:

```text
Cannot read properties of null
```

Без Error Boundary ошибка поднимется выше по дереву.

## Почему React не оставляет старый UI?

Render должен приводить UI к консистентному состоянию. Если компонент упал, React не знает:

- какие части дерева уже корректны;
- какие эффекты должны выполниться;
- какие children безопасно показывать;
- не повреждены ли данные дальше.

Поэтому React требует явной границы восстановления.

## Error Boundary как предохранитель

```jsx
<ErrorBoundary fallback={<WidgetError />}>
  <UserWidget />
</ErrorBoundary>
```

Если `UserWidget` упадет во время render, boundary покажет fallback вместо этого поддерева, а остальная страница продолжит работать.

## Где ставить Error Boundary?

Хорошие места:

- вокруг route/page;
- вокруг независимых widgets;
- вокруг lazy-loaded chunks;
- вокруг сложных сторонних компонентов;
- вокруг областей с нестабильными данными.

Плохая стратегия - иметь только одну границу на все приложение. Тогда любой маленький виджет может заменить весь экран на fallback.

## Что еще важно?

Error Boundary не заменяет проверки данных.

```jsx
if (!user) {
  return <UserSkeleton />
}

return <UserCard user={user} />
```

Если отсутствие данных - ожидаемое состояние, это не ошибка, а нормальная ветка UI.

## Мини-шпаргалка

- Ошибка render может сломать React tree.
- Error Boundary локализует падение.
- Fallback должен быть понятным пользователю.
- Ожидаемые состояния нужно обрабатывать через обычный UI.
- Не полагайся на одну boundary на все приложение.
