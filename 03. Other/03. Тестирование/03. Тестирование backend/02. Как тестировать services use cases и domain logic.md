# Как тестировать services, use cases и domain logic?

> [!summary]
> Services и use cases тестируют через входные данные, зависимости и ожидаемый результат. Хороший тест проверяет бизнес-правило: что создается, что запрещается, какие ошибки выбрасываются и какие зависимости вызываются.

## Что такое domain logic?

Domain logic - это правила предметной области.

Примеры:

- заказ нельзя оплатить дважды;
- скидка не может быть больше суммы заказа;
- пользователь не может изменить чужой документ;
- email должен быть уникальным;
- товар нельзя купить, если его нет на складе.

## Пример сервиса

```ts
class OrderService {
  constructor(private readonly products: ProductRepository) {}

  async calculateTotal(items: OrderItemInput[]) {
    const ids = items.map((item) => item.productId);
    const products = await this.products.findManyByIds(ids);

    return items.reduce((sum, item) => {
      const product = products.find((p) => p.id === item.productId);

      if (!product) {
        throw new Error('Product not found');
      }

      return sum + product.price * item.quantity;
    }, 0);
  }
}
```

## Тест happy path

```ts
test('calculates total by product prices and quantities', async () => {
  const products = {
    findManyByIds: vi.fn().mockResolvedValue([
      { id: 1, price: 100 },
      { id: 2, price: 50 },
    ]),
  };

  const service = new OrderService(products);

  await expect(service.calculateTotal([
    { productId: 1, quantity: 2 },
    { productId: 2, quantity: 1 },
  ])).resolves.toBe(250);
});
```

## Тест ошибки

```ts
test('throws if product does not exist', async () => {
  const products = {
    findManyByIds: vi.fn().mockResolvedValue([]),
  };

  const service = new OrderService(products);

  await expect(service.calculateTotal([
    { productId: 1, quantity: 1 },
  ])).rejects.toThrow('Product not found');
});
```

## Что проверять?

- результат;
- выброшенные ошибки;
- вызовы зависимостей;
- что опасное действие не произошло;
- edge cases;
- идемпотентность, если она важна.

## Мини-шпаргалка

- Service tests должны проверять бизнес-правила.
- Репозитории и API удобно подменять mocks/fakes.
- Ошибочные сценарии так же важны, как happy path.
- Не тестируй private methods напрямую.
- Проверяй итоговое поведение use case.
