# Клиентский VS серверный роутинг

> [!summary]
> Серверный роутинг запрашивает новую HTML-страницу у сервера при переходе. Клиентский роутинг меняет URL и UI в браузере без полной перезагрузки страницы.

## Серверный роутинг

```text
Click link -> browser sends request -> server returns HTML -> page reloads
```

Пример:

```js
app.get('/about', (req, res) => {
  res.sendFile('about.html')
})
```

Плюсы:

- контент сразу приходит в HTML;
- хорошо для SEO;
- проще первая загрузка;
- работает без большого JS bundle.

Минусы:

- переходы могут быть медленнее;
- состояние страницы обычно сбрасывается;
- больше работы на сервере;
- UX может быть менее плавным.

## Клиентский роутинг

```text
Click Link -> JS changes history -> React renders another component
```

Пример:

```jsx
<Link to="/about">About</Link>

<Routes>
  <Route path="/about" element={<AboutPage />} />
</Routes>
```

Плюсы:

- быстрые переходы после загрузки приложения;
- состояние приложения может сохраняться;
- UX похож на нативное приложение;
- удобно для dashboard, admin, complex SPA.

Минусы:

- initial bundle может быть тяжелым;
- без SSR/SSG SEO хуже;
- сервер нужно настроить на fallback;
- данные надо догружать отдельно.

## Современный гибрид

Фреймворки вроде Next.js, Remix и React Router framework mode могут совмещать:

- серверный render;
- клиентскую навигацию;
- data loading;
- streaming;
- hydration;
- prefetch.

То есть выбор не всегда "или сервер, или клиент". Часто первая загрузка серверная, а последующие переходы клиентские.

## Что сказать на собеседовании?

```text
При серверном роутинге каждый URL обрабатывает сервер и возвращает HTML.
При клиентском роутинге приложение уже загружено, а JavaScript меняет URL
и показывает другой компонент без полной перезагрузки.
```

## Мини-шпаргалка

- Серверный роутинг = новый request и новый HTML.
- Клиентский роутинг = History API и новый React-компонент.
- SPA требует fallback на `index.html`.
- SSR/SSG улучшают SEO и first paint.
- Современные фреймворки часто используют гибридную модель.
