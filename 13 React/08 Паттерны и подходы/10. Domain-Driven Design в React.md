# Domain-Driven Design в React

> [!summary]
> Domain-Driven Design в React означает, что структура и названия в коде отражают предметную область продукта: пользователей, заказы, платежи, корзину, тарифы, роли. UI перестает быть просто набором компонентов и начинает выражать бизнес-модель.

## Зачем DDD фронтенду?

Frontend давно не только "нарисовать кнопку". В крупных приложениях на клиенте есть:

- бизнес-правила;
- роли и права;
- формы с валидацией;
- сложные сценарии;
- кеш серверных данных;
- отображение разных состояний домена.

DDD помогает организовать этот код вокруг смысла, а не вокруг технических папок.

## Плохой технический разрез

```text
src/
  components/
    CartButton.tsx
    ProductCard.tsx
  hooks/
    useCart.ts
    useProducts.ts
  utils/
    calculateCartTotal.ts
  api/
    cartApi.ts
```

Код корзины размазан по проекту.

## Разрез по доменам

```text
src/
  domains/
    cart/
      ui/
        CartButton.tsx
        CartSummary.tsx
      model/
        cart.types.ts
        cart.selectors.ts
        calculateCartTotal.ts
      api/
        cartApi.ts
      index.ts
    product/
      ui/
        ProductCard.tsx
      model/
        product.types.ts
      api/
        productApi.ts
      index.ts
```

Теперь все, что относится к корзине, лежит внутри `cart`.

## Ubiquitous Language

Названия в коде должны совпадать с языком продукта.

Плохо:

```ts
function addItem(data: Item) {}
```

Лучше:

```ts
function addProductToCart(product: Product) {}
```

Так код проще обсуждать с командой, аналитиком и бизнесом.

## Bounded Context

Один термин может иметь разный смысл в разных частях продукта.

Например, `User`:

- в домене авторизации - учетная запись;
- в домене billing - плательщик;
- в админке - управляемая сущность с ролями;
- в CRM - клиент.

Не всегда стоит делать один универсальный тип `User` на все приложение.

```text
domains/auth/model/AuthUser.ts
domains/billing/model/BillingCustomer.ts
domains/admin/model/ManagedUser.ts
```

## DDD и FSD

DDD отвечает на вопрос: "какие бизнес-области есть в продукте?"

FSD отвечает на вопрос: "как организовать frontend-код по слоям и публичным API?"

Они хорошо сочетаются:

```text
entities/user/
features/add-product-to-cart/
widgets/cart-summary/
pages/checkout/
```

## Мини-шпаргалка

- DDD группирует код вокруг предметной области.
- Названия должны говорить языком продукта.
- Bounded Context защищает от слишком универсальных моделей.
- Домен должен иметь публичное API.
- DDD полезен, когда бизнес-логика на frontend стала заметной.
