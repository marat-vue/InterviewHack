# Как подключить Redis к Nitro cache, storage, sessions и WebSocket pub/sub?

> [!NOTE]
> Redis в Nitro чаще всего нужен не как основная доменная база, а как быстрый общий backend для cache, KV storage, rate limiting, одноразовых токенов, session-adjacent данных и realtime pub/sub между несколькими инстансами.

## Зачем Redis в Nitro?

Redis полезен, когда нужно:

- вынести cache из памяти процесса;
- разделить cache между несколькими Node/container инстансами;
- хранить короткоживущие значения с TTL;
- делать rate limiting;
- хранить одноразовые коды, nonce, magic-link state;
- координировать WebSocket broadcast между инстансами;
- использовать очереди или lightweight jobs;
- держать счетчики, locks, feature flags.

Для основных доменных данных лучше SQL через Prisma. Redis хорош как инфраструктурное хранилище: быстро, атомарно, удобно с TTL, но не заменяет relational model, constraints и migrations.

## Что установить?

Nitro storage построен на `unstorage`. Redis driver `unstorage` использует `ioredis`, поэтому в Node runtime установи:

```bash
pnpm add ioredis
```

или:

```bash
npm i ioredis
```

Для edge-окружений TCP Redis client может не подойти. Там часто используют HTTP-based Redis, например Upstash driver:

```bash
pnpm add @upstash/redis
```

## Какие env нужны?

```bash
REDIS_URL="redis://default:password@localhost:6379"
```

Для TLS-managed Redis URL может отличаться:

```bash
REDIS_URL="rediss://default:password@redis.example.com:6380"
```

Не коммить `REDIS_URL` в репозиторий. Храни его в `.env.local`, CI secrets или platform secrets.

## Как подключить Redis как Nitro storage?

```ts
// nitro.config.ts
import { defineConfig } from 'nitro';

export default defineConfig({
  storage: {
    redis: {
      driver: 'redis',
      url: process.env.REDIS_URL,
      base: 'interviewhack',
      ttl: 60 * 60,
    },
  },
});
```

Использование:

```ts
// routes/api/feature-flags.get.ts
import { defineHandler } from 'nitro';
import { useStorage } from 'nitro/storage';

export default defineHandler(async () => {
  const storage = useStorage('redis');

  await storage.setItem('features:beta-dashboard', true, {
    ttl: 60 * 10,
  });

  return {
    enabled: await storage.getItem<boolean>('features:beta-dashboard'),
  };
});
```

`base` добавляет prefix к ключам. Это удобно, чтобы разные приложения или окружения не смешивали данные.

## Как подключить Redis именно для Nitro cache?

Nitro cache использует mount point `cache`. Чтобы cached handlers и route rules жили в Redis:

```ts
// nitro.config.ts
import { defineConfig } from 'nitro';

export default defineConfig({
  storage: {
    cache: {
      driver: 'redis',
      url: process.env.REDIS_URL,
      base: 'interviewhack:cache',
    },
  },
});
```

Cached handler:

```ts
// routes/api/stats.get.ts
import { defineCachedHandler } from 'nitro/cache';

export default defineCachedHandler(async () => {
  const stats = await loadExpensiveStats();

  return {
    stats,
    generatedAt: new Date().toISOString(),
  };
}, {
  maxAge: 60,
  staleMaxAge: 300,
});
```

Route rules cache:

```ts
// nitro.config.ts
import { defineConfig } from 'nitro';

export default defineConfig({
  storage: {
    redis: {
      driver: 'redis',
      url: process.env.REDIS_URL,
    },
  },
  routeRules: {
    '/api/catalog/**': {
      cache: {
        maxAge: 60 * 5,
        base: 'redis',
      },
    },
  },
});
```

`base` в cache options указывает, какой storage mount point использовать. Если не указать, Nitro использует `cache`.

## Как настроить development storage?

Если production Redis недоступен локально:

```ts
// nitro.config.ts
import { defineConfig } from 'nitro';

export default defineConfig({
  storage: {
    cache: {
      driver: 'redis',
      url: process.env.REDIS_URL,
    },
  },
  devStorage: {
    cache: {
      driver: 'fs',
      base: './.data/cache',
    },
  },
});
```

Так production использует Redis, а development пишет cache в файловую систему.

## Как смонтировать Redis динамически в plugin?

Если credentials известны только в runtime, можно смонтировать driver в plugin:

```ts
// plugins/storage.ts
import { definePlugin } from 'nitro';
import { useStorage } from 'nitro/storage';
import redisDriver from 'unstorage/drivers/redis';

export default definePlugin(() => {
  const storage = useStorage();

  storage.mount(
    'redis',
    redisDriver({
      base: 'interviewhack',
      url: process.env.REDIS_URL,
      ttl: 60 * 60,
    }),
  );
});
```

Обычно проще объявить storage в `nitro.config.ts`. Plugin полезен, если URL приходит из secret manager или платформенного binding.

## Какие методы `useStorage('redis')` использовать?

| Метод | Зачем нужен в Redis-сценариях |
|---|---|
| `getItem(key)` | прочитать JSON/string значение |
| `setItem(key, value, options?)` | записать значение, можно передать `{ ttl }` |
| `hasItem(key)` | проверить существование ключа |
| `removeItem(key)` | удалить ключ |
| `getKeys(base?)` | найти ключи по prefix, осторожно на больших объемах |
| `clear(base?)` | очистить prefix, опасно без строгого namespace |
| `getItemRaw(key)` | прочитать binary/raw значение |
| `setItemRaw(key, value, options?)` | записать binary/raw значение |
| `getMeta(key)` | получить metadata, если driver ее поддерживает |
| `mount(base, driver)` | подключить Redis driver вручную |
| `unmount(base)` | отключить mount |

Пример TTL:

```ts
const storage = useStorage('redis');

await storage.setItem('otp:user_1', '482911', {
  ttl: 60 * 5,
});

const code = await storage.getItem<string>('otp:user_1');
```

## Какие Redis commands важно знать backend-разработчику?

| Команда | Для чего нужна |
|---|---|
| `GET` | прочитать string value |
| `SET` | записать string value, часто с `EX` для TTL |
| `DEL` | удалить ключ |
| `EXISTS` | проверить наличие ключа |
| `EXPIRE` | задать TTL ключу |
| `TTL` | узнать оставшееся время жизни |
| `INCR` | атомарный счетчик |
| `HGET` / `HSET` | hash fields, удобно для session-like объектов |
| `LPUSH` / `BRPOP` | простая очередь на list |
| `SADD` / `SREM` / `SMEMBERS` | sets, например online users |
| `ZADD` / `ZRANGE` | sorted sets, leaderboards/ranking |
| `PUBLISH` / `SUBSCRIBE` | pub/sub для realtime fan-out |
| `XADD` / `XREAD` | Redis Streams для событий и job-like потоков |
| `EVAL` | Lua script для атомарной сложной операции |

В Nitro через `useStorage` ты работаешь не с командами Redis напрямую, а с KV abstraction. Если нужны `INCR`, Pub/Sub, Streams или Lua, используй `ioredis` client отдельно.

## Как создать singleton Redis client?

```ts
// server/utils/redis.ts
import Redis from 'ioredis';

const globalForRedis = globalThis as unknown as {
  redis?: Redis;
};

export const redis =
  globalForRedis.redis ??
  new Redis(process.env.REDIS_URL!, {
    maxRetriesPerRequest: 2,
    enableReadyCheck: true,
  });

if (process.env.NODE_ENV !== 'production') {
  globalForRedis.redis = redis;
}
```

Singleton помогает не создавать новый TCP connection на каждый request в dev и long-lived Node runtime.

## Как сделать rate limit через Redis?

```ts
// server/middleware/02.rate-limit.ts
import { defineHandler } from 'nitro';
import { createError, getRequestIP } from 'nitro/h3';
import { redis } from '../utils/redis';

export default defineHandler(async (event) => {
  const ip = getRequestIP(event) || 'unknown';
  const key = `rate:${ip}`;

  const count = await redis.incr(key);

  if (count === 1) {
    await redis.expire(key, 60);
  }

  if (count > 100) {
    throw createError({
      statusCode: 429,
      statusMessage: 'Too Many Requests',
    });
  }
});
```

Почему Redis здесь хорош:

- `INCR` атомарный;
- TTL очищает ключи автоматически;
- все инстансы видят один счетчик;
- нет зависимости от памяти одного процесса.

Для production добавь user-based keys, route-specific limits, trusted proxy config и allowlist для внутренних сервисов.

## Как использовать Redis для Better Auth session-adjacent данных?

Better Auth обычно хранит пользователей, accounts и sessions в базе через adapter, например Prisma. Redis можно использовать рядом:

- rate limit login attempts;
- хранить одноразовые verification state;
- кешировать public profile или permissions;
- хранить short-lived device/session metadata, если выбранный Better Auth plugin это поддерживает;
- координировать logout/session invalidation между инстансами.

Не переноси основную auth-модель в Redis без ясной причины. Для audit, relations и migrations SQL надежнее.

## Как использовать Redis Pub/Sub для WebSocket?

Для одного Node-инстанса достаточно `peer.publish()`. Для нескольких инстансов нужен общий broker. Redis Pub/Sub - простой вариант.

```ts
// server/utils/ws-bus.ts
import Redis from 'ioredis';

export const wsPub = new Redis(process.env.REDIS_URL!);
export const wsSub = new Redis(process.env.REDIS_URL!);
```

```ts
// routes/ws/notifications.ts
import { defineWebSocketHandler } from 'nitro';
import { wsPub, wsSub } from '../../server/utils/ws-bus';

const peers = new Set<any>();
let subscribed = false;

async function subscribeOnce() {
  if (subscribed) {
    return;
  }

  subscribed = true;
  await wsSub.subscribe('notifications');

  wsSub.on('message', (_channel, payload) => {
    for (const peer of peers) {
      peer.send(payload);
    }
  });
}

export default defineWebSocketHandler({
  async open(peer) {
    peers.add(peer);
    await subscribeOnce();
  },
  async message(_peer, message) {
    await wsPub.publish('notifications', message.text());
  },
  close(peer) {
    peers.delete(peer);
  },
});
```

Production-версия должна учитывать:

- auth в `upgrade`;
- tenant/user-specific channels;
- лимит размера payload;
- reconnect Redis клиента;
- graceful shutdown;
- idempotency, если сообщение может прийти повторно;
- переход на Redis Streams, если нужна доставка с replay.

## Redis Pub/Sub или Redis Streams?

| Механизм | Когда выбрать |
|---|---|
| Pub/Sub | realtime broadcast, потеря сообщения при offline допустима |
| Streams | нужна история, consumer groups, replay, более надежная обработка |
| Lists | простая очередь без сложного routing |
| Sorted sets | delayed jobs, rankings, scheduled cleanup |

Для чата и уведомлений online-пользователям часто хватает Pub/Sub. Для фоновых задач и важных событий лучше Streams или полноценная очередь.

## Что важно в production?

Проверь:

- TLS и private network;
- password/ACL;
- отдельные prefixes на окружения: `dev`, `staging`, `prod`;
- eviction policy;
- memory limit;
- TTL для временных ключей;
- monitoring latency, memory, connected clients;
- backup, если Redis используется не только как disposable cache;
- cluster hash tags, если используешь Redis Cluster и операции по нескольким ключам;
- graceful disconnect на shutdown;
- fallback behavior, если Redis временно недоступен.

Cache может быть disposable. Auth/rate-limit/realtime state уже влияет на user experience, поэтому для него нужен отдельный reliability plan.

## Мини-шпаргалка

- Nitro cache хранится в mount point `cache`.
- Redis подключается через `storage.cache` или отдельный mount, например `storage.redis`.
- Для `unstorage` Redis driver нужен `ioredis`.
- Для edge чаще нужен HTTP-based Redis driver, например Upstash.
- `useStorage('redis')` подходит для KV + TTL.
- Для Redis commands, Pub/Sub и Streams используй `ioredis` напрямую.
- Rate limit лучше делать через атомарный `INCR` + `EXPIRE`.
- WebSocket на нескольких инстансах требует external broker.
- Redis не заменяет Prisma/SQL для основной доменной модели.
