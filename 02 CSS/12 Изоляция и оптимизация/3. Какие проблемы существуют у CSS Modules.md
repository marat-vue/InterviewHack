# Какие проблемы существуют у CSS Modules

> [!summary]
> CSS Modules хорошо изолируют классы, но не решают все задачи CSS-архитектуры: остаются проблемы композиции, глобальных стилей, темизации, переиспользования, динамических состояний и читаемости class names.

## Главное

CSS Modules превращают локальные классы в уникальные имена.

```css
/* Card.module.css */
.card {
  padding: 16px;
}
```

```js
import styles from "./Card.module.css";

const className = styles.card;
```

Это снижает риск конфликтов, но добавляет свои ограничения.

## Сложная композиция

Если компонент имеет много вариантов, className может быстро стать громоздким.

```js
const className = [
  styles.button,
  isPrimary && styles.primary,
  isLoading && styles.loading,
  isWide && styles.wide,
].filter(Boolean).join(" ");
```

Нужны соглашения или утилиты для сборки классов.

## Глобальные стили все равно нужны

CSS Modules не отменяют:

- reset/base styles;
- CSS-переменные;
- стили `body`;
- стили типографики;
- интеграцию с third-party HTML;
- utility classes, если проект их использует.

## Темизация

Темы часто удобнее строить через CSS custom properties, а не через дублирование module-классов.

```css
.card {
  background: var(--surface);
  color: var(--text);
}
```

## Переопределение дочерних компонентов

Локальность классов усложняет ситуацию, когда родителю нужно повлиять на внутренний класс дочернего компонента. Обычно лучше передавать props, CSS-переменные или специально предусмотренные slots/API.

## Мини-шпаргалка

- CSS Modules изолируют class names.
- Они не заменяют архитектуру стилей.
- Глобальные base/reset styles все равно нужны.
- Для тем лучше подходят CSS-переменные.
- Сложные варианты требуют соглашений.
- Не стоит ломать инкапсуляцию дочернего компонента через внутренние классы.
