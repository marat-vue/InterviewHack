# Как делать proxy и internal fetch в Nitro?

> [!NOTE]
> В Nitro можно проксировать запросы декларативно через `routeRules.proxy`, вручную через H3 proxy utilities или делать internal sub-request через `fetchWithEvent`. Важно не пересылать cookies/authorization во внешние домены случайно.

## Proxy через routeRules

```ts
export default defineConfig({
  routeRules: {
    '/api/legacy/**': {
      proxy: 'https://legacy.example.com/**',
    },
  },
});
```

Это удобно, когда нужно:

- временно поддержать старый backend;
- сделать BFF endpoint;
- спрятать origin;
- вынести proxy из handler-кода.

## Proxy handler вручную

Для сложной логики можно написать отдельный handler:

```ts
export default defineHandler(async (event) => {
  const target = new URL('https://api.example.com/users');
  target.search = event.url.search;

  return fetch(target, {
    headers: {
      accept: 'application/json',
    },
  });
});
```

Так проще добавить:

- auth to upstream;
- request mapping;
- response filtering;
- custom error handling;
- rate limit;
- cache.

## `fetchWithEvent`

`fetchWithEvent(event, url, init?)` делает fetch с учетом event context.

```ts
import { fetchWithEvent } from 'h3';

export default defineHandler(async (event) => {
  const response = await fetchWithEvent(event, '/api/internal/profile');

  return response;
});
```

Для internal URL, который начинается с `/`, request может быть обработан внутри приложения как sub-request. Это не уходит по сети как обычный внешний fetch.

## Когда использовать internal fetch?

Можно использовать, если:

- нужно переиспользовать существующий endpoint;
- строишь BFF composition;
- хочешь пройти тот же routing/middleware;
- нужен response-compatible результат.

Но часто лучше вынести общую логику в service:

```txt
server/services/userService.ts
  -> используется двумя routes
```

Так быстрее и проще тестировать, чем дергать свой же HTTP endpoint.

## Безопасность proxy

Не делай так:

```ts
const target = getQuery(event).url;
return fetch(String(target));
```

Это SSRF-риск: пользователь сможет заставить сервер сходить куда угодно.

Лучше:

```ts
const allowedHosts = new Set(['api.example.com']);
const target = new URL(String(getQuery(event).url));

if (!allowedHosts.has(target.host)) {
  throw createError({
    statusCode: 400,
    statusMessage: 'Invalid target',
  });
}
```

## Cookies и authorization

Для external fetch не пересылай входные headers blindly:

```ts
return fetch('https://third-party.example.com', {
  headers: event.req.headers,
});
```

Это может утечь:

- cookies;
- bearer tokens;
- internal headers;
- CSRF headers;
- tracing IDs.

Передавай только нужное:

```ts
return fetch('https://api.example.com', {
  headers: {
    authorization: `Bearer ${useRuntimeConfig().apiToken}`,
    accept: 'application/json',
  },
});
```

## Мини-шпаргалка

- Простое проксирование - `routeRules.proxy`.
- Сложное проксирование - custom handler.
- Internal sub-request - `fetchWithEvent(event, '/api/...')`.
- Общую бизнес-логику лучше выносить в service.
- Не делай proxy на произвольный URL от пользователя.
- Не пересылай все request headers во внешний сервис.
