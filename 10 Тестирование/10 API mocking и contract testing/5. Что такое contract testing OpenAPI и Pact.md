# Что такое contract testing, OpenAPI и Pact?

> [!summary]
> Contract testing проверяет, что consumer и provider одинаково понимают API-контракт. OpenAPI фиксирует контракт как спецификацию, а Pact позволяет consumer-driven подход: потребитель описывает ожидания, provider проверяет, что может их выполнить.

## Зачем нужны contract tests?

Интеграционный тест с настоящим frontend и backend дорогой. Но часто проблема проще:

```text
Frontend ожидает поле email.
Backend переименовал его в login.
```

Contract test должен поймать такую поломку до релиза.

## Consumer и provider

- **Consumer** - тот, кто вызывает API.
- **Provider** - тот, кто реализует API.

Например:

```text
Frontend app -> consumer
Users API -> provider
```

## OpenAPI как контракт

OpenAPI описывает:

- paths;
- methods;
- request body;
- response body;
- status codes;
- headers;
- schemas.

По OpenAPI можно генерировать types, clients и проверки соответствия response schema.

## Pact

Pact работает в стиле consumer-driven contract testing:

1. Consumer-тест описывает запрос и ожидаемый ответ.
2. Pact сохраняет контракт.
3. Provider-тест берет контракт и проверяет настоящий provider.
4. Pact Broker помогает обмениваться контрактами между командами.

## Когда contract tests особенно нужны?

- microservices;
- frontend и backend в разных командах;
- публичный API;
- частые изменения схем;
- много consumers;
- нельзя поднимать всю систему в e2e для каждого PR.

## Мини-шпаргалка

- Contract testing проверяет API-договор.
- Consumer вызывает API, provider реализует API.
- OpenAPI - спецификация контракта.
- Pact - consumer-driven contract testing.
- Contract tests не заменяют e2e полностью, но закрывают важный класс интеграционных багов.
