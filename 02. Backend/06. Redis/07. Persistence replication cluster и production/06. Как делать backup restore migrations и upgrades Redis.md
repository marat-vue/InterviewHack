# Как делать backup, restore, migrations и upgrades Redis?

> [!NOTE]
> Если Redis используется только как disposable cache, backup может быть не нужен. Если Redis хранит sessions, streams, queues или данные, потеря которых важна, backup и restore нужно проверять заранее.

## Что backup-ить?

Зависит от роли Redis:

| Роль Redis | Backup нужен? |
|---|---|
| Только cache | часто нет |
| Sessions | зависит от требований |
| Streams/jobs | да, если потеря критична |
| Leaderboard | да, если нельзя пересчитать |
| Feature flags | да или хранить source of truth в БД |
| Primary database | обязательно |

## RDB backup

RDB snapshot удобно копировать как backup artifact:

```txt
dump.rdb
```

Важно:

- хранить вне Redis node;
- шифровать;
- проверять restore;
- контролировать частоту snapshots.

## AOF backup

AOF дает более свежие writes, но файл может быть больше.

Проверь:

- rewrite policy;
- disk usage;
- fsync mode;
- recovery time.

## Restore drill

Минимальный drill:

1. Взять backup.
2. Поднять новый Redis instance.
3. Подложить RDB/AOF в `/data`.
4. Запустить Redis.
5. Проверить ключи.
6. Прогнать smoke tests.

Backup без проверенного restore - почти не backup.

## Migrations в Redis

Redis не имеет schema migrations как SQL, но changes все равно бывают:

- переименование keys;
- смена serialization format;
- смена TTL;
- перенос структуры String -> Hash;
- versioned cache keys;
- stream naming changes.

Лучше использовать versioned keys:

```txt
cache:v1:user:1
cache:v2:user:1
```

Старый cache исчезнет по TTL.

## Upgrades

Перед upgrade:

- прочитай release notes;
- проверь client compatibility;
- сделай backup;
- протестируй staging;
- проверь persistence config;
- проверь modules/Redis Stack compatibility.

## Мини-шпаргалка

- Cache Redis можно восстановить прогревом.
- Stateful Redis требует backup.
- Проверяй restore, не только создание backup.
- Redis migrations чаще делают через key versioning.
- Перед upgrade нужны backup и staging test.
