# Почему при обновлении состояния нужен новый объект?

> [!summary]
> React state нужно обновлять иммутабельно. Если состояние - объект, при изменении поля нужно создать новый объект, а не менять старый. Новая ссылка помогает React и разработчику явно видеть, что данные изменились.

## Плохой пример

```jsx
const [user, setUser] = useState({
  name: 'Анна',
  city: 'Москва',
})

function changeCity() {
  user.city = 'Казань'
  setUser(user)
}
```

Здесь объект мутируется напрямую. Ссылка остается прежней.

## Правильный пример

```jsx
function changeCity() {
  setUser({
    ...user,
    city: 'Казань',
  })
}
```

`...user` копирует старые поля, а `city` перезаписывается новым значением.

## Обновление вложенного объекта

```jsx
const [profile, setProfile] = useState({
  name: 'Анна',
  address: {
    city: 'Москва',
    street: 'Тверская',
  },
})
```

Правильно:

```jsx
setProfile({
  ...profile,
  address: {
    ...profile.address,
    city: 'Казань',
  },
})
```

Нужно копировать каждый уровень, который меняется.

## Почему глубокие объекты неудобны?

Чем глубже структура state, тем сложнее обновления:

```text
profile.settings.notifications.email.enabled
```

В таких случаях можно:

- сделать state более плоским;
- разбить state на несколько частей;
- использовать reducer;
- использовать Immer, если проект уже принял такой подход.

## Как связаны новый объект и memo?

`React.memo` и похожие оптимизации часто сравнивают props по ссылке. Если мутировать старый объект, ссылка не меняется, и компонент может не обновиться. Если создавать новый объект без необходимости на каждом render, наоборот, memo может терять пользу.

## Мини-шпаргалка

- Объекты в state нужно считать read-only.
- Для изменения поля создавай новый объект.
- Вложенные объекты копируются по каждому изменяемому уровню.
- Глубокий state часто лучше нормализовать или упростить.
- Иммутабельность помогает React-обновлениям и отладке.
