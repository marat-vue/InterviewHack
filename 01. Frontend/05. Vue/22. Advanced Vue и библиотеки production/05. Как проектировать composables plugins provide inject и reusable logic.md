# Как проектировать composables, plugins, provide/inject и reusable logic?

> [!NOTE]
> Composable - это не просто функция с `ref`. Хороший composable управляет жизненным циклом, не прячет неожиданный global state, имеет понятный контракт и не превращается в store без причины.

## Вопрос

Как проектировать composables, plugins, `provide`/`inject` и переиспользуемую логику во Vue?

## Базовая идея

Vue дает несколько уровней переиспользования:

- обычная функция - чистая логика без Vue;
- composable - функция, использующая Composition API;
- component - переиспользуемый UI;
- Pinia store - общее состояние приложения;
- plugin - установка функциональности на уровень app;
- `provide`/`inject` - dependency injection внутри component tree.

Правильный выбор уровня важнее, чем конкретный синтаксис.

## Хороший composable

Пример:

```typescript
import { computed, ref } from "vue";

export function usePagination(initialPage = 1, initialPageSize = 20) {
  const page = ref(initialPage);
  const pageSize = ref(initialPageSize);

  const offset = computed(() => (page.value - 1) * pageSize.value);

  function next() {
    page.value += 1;
  }

  function reset() {
    page.value = 1;
  }

  return {
    page,
    pageSize,
    offset,
    next,
    reset,
  };
}
```

Признаки хорошего composable:

- имя начинается с `use`;
- входные параметры явные;
- возвращаемые значения понятны;
- есть cleanup, если composable создает подписку;
- не мутирует внешнее состояние без явного контракта;
- легко тестируется.

## Local state и shared state

State внутри функции создается на каждый вызов:

```typescript
export function useLocalCounter() {
  const count = ref(0);
  return { count };
}
```

State снаружи функции общий для всех вызовов:

```typescript
const count = ref(0);

export function useSharedCounter() {
  return { count };
}
```

Shared state не плох сам по себе, но его нужно делать осознанно. Если shared state растет, появляются actions, persistence, SSR-нюансы и devtools-потребность - скорее всего, нужен Pinia store.

## Cleanup через `onScopeDispose`

Если composable подписывается на внешний ресурс, он должен убирать подписку.

```typescript
import { onScopeDispose, ref } from "vue";

export function useOnlineStatus() {
  const isOnline = ref(navigator.onLine);

  const update = () => {
    isOnline.value = navigator.onLine;
  };

  window.addEventListener("online", update);
  window.addEventListener("offline", update);

  onScopeDispose(() => {
    window.removeEventListener("online", update);
    window.removeEventListener("offline", update);
  });

  return { isOnline };
}
```

`onScopeDispose` привязан к текущему effect scope. В компоненте он отработает при unmount. В ручных scopes - при `scope.stop()`.

## `effectScope`

`effectScope` позволяет сгруппировать effects, watchers и computed, чтобы остановить их вместе.

```typescript
import { effectScope, ref, watch } from "vue";

const scope = effectScope();

scope.run(() => {
  const count = ref(0);

  watch(count, (value) => {
    console.log("count", value);
  });
});

scope.stop();
```

Где нужно:

- сложные composables;
- plugins;
- временные подписки;
- reusable modules вне компонента;
- тесты, где нужно вручную остановить реактивность.

## `toValue`, `unref` и MaybeRef

Composable часто должен принимать и обычное значение, и `ref`, и getter.

```typescript
import { computed, toValue, type MaybeRefOrGetter } from "vue";

export function useSearchUrl(query: MaybeRefOrGetter<string>) {
  return computed(() => {
    const value = toValue(query);
    return `/search?q=${encodeURIComponent(value)}`;
  });
}
```

`unref()` раскрывает ref или возвращает значение как есть. `toValue()` дополнительно вызывает getter.

Это удобно для универсальных composables:

```typescript
const url1 = useSearchUrl("vue");
const url2 = useSearchUrl(searchQueryRef);
const url3 = useSearchUrl(() => route.query.q?.toString() ?? "");
```

## `provide` и `inject`

`provide`/`inject` передают зависимость вниз по component tree без prop drilling.

```typescript
// keys.ts
import type { InjectionKey, Ref } from "vue";

export interface AuthContext {
  userId: Ref<number | null>;
  logout: () => Promise<void>;
}

export const authKey: InjectionKey<AuthContext> = Symbol("auth");
```

Provider:

```vue
<script setup lang="ts">
import { provide, ref } from "vue";
import { authKey } from "./keys";

const userId = ref<number | null>(1);

async function logout() {
  userId.value = null;
}

provide(authKey, {
  userId,
  logout,
});
</script>

<template>
  <slot />
</template>
```

Consumer:

```vue
<script setup lang="ts">
import { inject } from "vue";
import { authKey } from "./keys";

const auth = inject(authKey);

if (!auth) {
  throw new Error("Auth context is not provided");
}
</script>
```

Где применять:

- form context;
- theme context;
- feature flags;
- modal manager;
- table/list context;
- зависимости библиотеки компонентов.

Где не применять:

- вместо всех props;
- для глобального состояния всего приложения;
- для скрытых зависимостей, которые трудно отследить.

## `app.provide`

Зависимость можно дать всему приложению:

```typescript
import { createApp } from "vue";
import { apiClientKey } from "@/shared/api";
import App from "./App.vue";

const app = createApp(App);

app.provide(apiClientKey, createApiClient());

app.mount("#app");
```

Это удобно для клиентов API, feature flags, config, analytics adapters.

## Plugins

Vue plugin - объект или функция с методом `install(app, options)`.

```typescript
import type { App, InjectionKey } from "vue";

export interface Analytics {
  track: (event: string, payload?: Record<string, unknown>) => void;
}

export const analyticsKey: InjectionKey<Analytics> = Symbol("analytics");

export function createAnalyticsPlugin(analytics: Analytics) {
  return {
    install(app: App) {
      app.provide(analyticsKey, analytics);
      app.config.globalProperties.$analytics = analytics;
    },
  };
}
```

Подключение:

```typescript
import { createApp } from "vue";
import App from "./App.vue";
import { createAnalyticsPlugin } from "./plugins/analytics";

createApp(App)
  .use(createAnalyticsPlugin(createAnalytics()))
  .mount("#app");
```

В компонентах лучше получать зависимость через `inject`, а не через `globalProperties`, потому что так проще типизировать и тестировать.

## Где хранить reusable logic

Пример структуры:

```text
src/
  composables/
    usePagination.ts
    useDebouncedRef.ts
  plugins/
    analytics.ts
    api-client.ts
  providers/
    auth/
      AuthProvider.vue
      keys.ts
      useAuth.ts
  stores/
    user.store.ts
```

Удобный wrapper над `inject`:

```typescript
import { inject } from "vue";
import { authKey } from "./keys";

export function useAuth() {
  const auth = inject(authKey);

  if (!auth) {
    throw new Error("useAuth must be used inside AuthProvider");
  }

  return auth;
}
```

## Когда composable, а когда Pinia

Composable:

- локальная reusable logic;
- работа с browser API;
- вычисления;
- форма внутри одного feature;
- подписки и cleanup;
- не нужен devtools state timeline.

Pinia:

- состояние нужно многим независимым частям приложения;
- есть actions и бизнес-сценарии;
- нужна devtools-интеграция;
- нужен SSR state transfer;
- нужен plugin/persistence/testing ecosystem.

## Частые ошибки

- Делать composable с неявным singleton state и удивляться, что все компоненты делят данные.
- Не очищать `setInterval`, event listeners, WebSocket subscriptions.
- Прятать сетевые запросы внутри composable без возможности mock/test.
- Использовать `provide`/`inject` как глобальный store.
- Добавлять plugin там, где хватило обычной функции.
- Использовать `globalProperties` для всего, ухудшая типизацию.

## Что отвечать на собеседовании

Composable - это функция, которая переиспользует Composition API логику. Важно различать local и shared state, делать cleanup через `onScopeDispose`, принимать `MaybeRef`/getter через `toValue`, а зависимости передавать явно. `provide`/`inject` подходит для dependency injection внутри component tree, plugin - для установки функциональности на app level, Pinia - для общего состояния приложения.

## Мини-шпаргалка

- `useSomething` - стандартное имя composable.
- State внутри composable - новый на каждый вызов.
- State снаружи composable - общий singleton.
- `onScopeDispose` - cleanup.
- `effectScope` - группа reactive effects.
- `toValue` - значение из raw/ref/getter.
- `provide`/`inject` - dependency injection.
- `app.use()` - подключение plugin.
- `app.provide()` - зависимость на уровне приложения.
