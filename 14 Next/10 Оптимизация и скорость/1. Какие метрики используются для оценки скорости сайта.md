# Какие метрики используются для оценки скорости сайта?

> [!summary]
> Скорость сайта оценивают не одной цифрой, а набором метрик: загрузка контента, отзывчивость, визуальная стабильность, скорость ответа сервера и стоимость JavaScript. Главный пользовательский стандарт - Core Web Vitals: LCP, INP и CLS.

## Зачем нужно несколько метрик?

Сайт может быть быстрым в одном смысле и медленным в другом.

Например:

- HTML пришел быстро, но главный баннер появился поздно;
- контент виден, но кнопки нажимаются с задержкой;
- страница загрузилась, но элементы прыгают;
- Lighthouse хороший, а реальные пользователи на слабых телефонах страдают.

Поэтому производительность измеряют слоями.

## Core Web Vitals

| Метрика | Что измеряет | Хороший ориентир |
| --- | --- | --- |
| LCP | Когда появился главный крупный контент | до 2.5 с |
| INP | Как быстро страница отвечает на взаимодействия | до 200 мс |
| CLS | Насколько сильно прыгает layout | до 0.1 |

Google оценивает Core Web Vitals по реальному пользовательскому опыту. Обычно смотрят 75-й перцентиль по мобильным и десктопным пользователям.

## LCP

LCP, Largest Contentful Paint, показывает, когда пользователь увидел главный крупный элемент страницы:

- hero image;
- крупный заголовок;
- основной текстовый блок;
- большое видео или изображение.

Что ухудшает LCP:

- медленный TTFB;
- тяжелая hero-картинка;
- блокирующий CSS;
- слишком много клиентского JS;
- загрузка главного контента только после API-запроса на клиенте.

В Next.js LCP часто улучшают через:

- Server Components;
- SSR/SSG/ISR;
- `next/image`;
- `priority` для главного изображения;
- кэширование данных;
- отказ от лишнего CSR на первом экране.

## INP

INP, Interaction to Next Paint, измеряет отзывчивость страницы после действий пользователя.

Плохой INP выглядит так:

- нажал кнопку, а реакция через секунду;
- ввел текст, а поле тормозит;
- открыл меню, а оно подвисло;
- скролл дергается.

Что ухудшает INP:

- большой JS-бандл;
- тяжелая гидратация;
- длинные задачи в main thread;
- сложные вычисления в Client Components;
- слишком много обработчиков и перерендеров.

В Next.js помогает стратегия: Server Components по умолчанию, Client Components только там, где нужна интерактивность.

## CLS

CLS, Cumulative Layout Shift, измеряет неожиданные сдвиги layout.

Плохие примеры:

- картинка загрузилась и вытолкнула текст вниз;
- рекламный блок появился над кнопкой;
- шрифт загрузился и изменил размеры текста;
- skeleton не совпал по размеру с итоговым контентом.

В Next.js CLS снижают через:

- `next/image` с известными размерами;
- резервирование места под рекламу и embeds;
- аккуратные skeleton-компоненты;
- `next/font`, который уменьшает проблемы со шрифтами;
- стабильную верстку без поздних вставок сверху страницы.

## Дополнительные метрики

| Метрика | Что показывает |
| --- | --- |
| TTFB | Время до первого байта ответа сервера |
| FCP | Когда появился первый видимый контент |
| TBT | Сколько времени main thread был заблокирован в lab-тесте |
| TTI | Когда страница стала полноценно интерактивной |
| Bundle size | Сколько JS нужно скачать, распарсить и выполнить |

TBT особенно полезен в Lighthouse как лабораторный proxy для проблем, которые могут ухудшать INP.

## Чем field-данные отличаются от lab-данных?

Lab-данные:

- Lighthouse;
- локальные замеры;
- controlled throttling;
- удобно проверять до релиза.

Field-данные:

- реальные пользователи;
- реальные устройства;
- реальные сети;
- Chrome UX Report;
- Search Console;
- RUM-аналитика.

На собеседовании важно сказать: Lighthouse полезен, но не заменяет реальные данные.

## Что отвечать на собеседовании?

Скорость сайта измеряется набором метрик. Главные пользовательские метрики - Core Web Vitals: LCP для загрузки основного контента, INP для отзывчивости и CLS для визуальной стабильности. Дополнительно смотрят TTFB, FCP, TBT, TTI и размер JS-бандла. Важно отличать lab-замеры от field-данных реальных пользователей.

## Частые ошибки

- Оценивать скорость только по Lighthouse score.
- Путать FCP и LCP.
- Продолжать говорить про FID вместо INP.
- Не учитывать слабые мобильные устройства.
- Улучшать TTFB, но забывать про тяжелый JS.
- Не проверять CLS после добавления картинок, баннеров и рекламных блоков.

## Мини-шпаргалка

- LCP - главный контент до 2.5 с.
- INP - реакция на действия до 200 мс.
- CLS - сдвиги layout до 0.1.
- TTFB - скорость ответа сервера.
- FCP - первый видимый контент.
- TBT - блокировка main thread в lab.
- Field-данные важнее одного Lighthouse-прогона.
