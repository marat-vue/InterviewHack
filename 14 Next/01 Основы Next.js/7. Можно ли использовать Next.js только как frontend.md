# Можно ли использовать Next.js только как frontend?

> [!summary]
> Да, Next.js можно использовать как frontend/BFF слой поверх внешнего backend API. В этом случае Next.js отвечает за UI, роутинг, SSR/SSG, SEO и оптимизацию, а бизнес-логика и база данных остаются во внешнем backend.

## Как это выглядит?

Архитектура:

```text
Browser -> Next.js -> external API -> database
```

Next.js может:

- рендерить страницы;
- запрашивать данные у внешнего API;
- формировать metadata;
- кешировать публичные данные;
- проксировать запросы;
- отдавать статические assets.

## Пример Server Component с внешним API

```tsx
export default async function UsersPage() {
  const users = await fetch('https://api.example.com/users', {
    headers: {
      Authorization: `Bearer ${process.env.API_TOKEN}`,
    },
  }).then((res) => res.json())

  return <UserList users={users} />
}
```

`API_TOKEN` остается на сервере, если код не попадает в Client Component.

## Next.js как BFF

BFF, или Backend For Frontend, адаптирует backend под нужды frontend.

Route Handler может скрыть внутренний API:

```ts
export async function GET() {
  const response = await fetch(`${process.env.API_URL}/internal/products`)
  const products = await response.json()

  return Response.json(products)
}
```

Frontend обращается к `/api/products`, а реальная backend-структура остается скрытой.

## Когда это хороший подход?

- backend уже существует;
- нужна SEO-страница поверх API;
- frontend-команда контролирует presentation layer;
- нужен BFF для aggregation;
- важно не раскрывать внутренние API URL;
- нужен SSR с backend data.

## Когда можно выбрать обычный SPA?

Если:

- SEO не нужно;
- приложение только после логина;
- вся загрузка данных идет на клиенте;
- нет SSR/SSG требований;
- важнее простота деплоя;
- команда не хочет server runtime.

## Что отвечать на собеседовании?

Next.js можно использовать только как frontend, подключенный к внешнему API. Он будет отвечать за UI, роутинг, рендеринг, SEO и оптимизацию. При этом может выполнять роль BFF, но не обязан хранить бизнес-логику и базу данных внутри проекта.

## Частые ошибки

- Считать, что Next.js всегда должен напрямую работать с БД.
- Выносить секретные токены в Client Components.
- Дублировать всю backend-логику в Route Handlers.
- Использовать SSR без кеширования для медленного внешнего API.
- Выбирать Next.js только "потому что модно".

## Мини-шпаргалка

- Next.js может быть frontend layer.
- Внешний API может быть Nest, Django, Laravel, Go.
- Server Components могут безопасно читать server env.
- Route Handlers удобны для BFF.
- Для закрытых SPA иногда достаточно Vite.
