# Как глубже читать EXPLAIN ANALYZE BUFFERS?

> [!NOTE]
> `EXPLAIN` показывает план, а `EXPLAIN ANALYZE` выполняет запрос и показывает фактическое время. В PostgreSQL для реальной диагностики часто добавляют `BUFFERS`, чтобы увидеть работу с памятью и диском.

## Базовая команда

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT *
FROM orders
WHERE user_id = 42
ORDER BY created_at DESC
LIMIT 20;
```

Осторожно: `ANALYZE` реально выполняет запрос. Для `UPDATE/DELETE/INSERT` используй транзакцию и `ROLLBACK`.

## На что смотреть?

| Поле | Что значит |
|---|---|
| `cost` | оценка planner-а, не миллисекунды |
| `actual time` | фактическое время |
| `rows` | фактические строки |
| `loops` | сколько раз node выполнялся |
| `Buffers: shared hit` | страницы взяты из shared buffers |
| `Buffers: shared read` | страницы читались с диска |
| `Planning Time` | время планирования |
| `Execution Time` | время выполнения |

## Estimates vs actual

Проблема:

```txt
rows=10 estimated
actual rows=100000
```

Это значит, что planner сильно ошибся. Частые причины:

- устаревшая статистика;
- correlated columns;
- плохая селективность;
- expression без статистики;
- сложный predicate.

Помогает:

```sql
ANALYZE orders;
```

или extended statistics.

## Частые plan nodes

| Node | Что значит |
|---|---|
| `Seq Scan` | чтение таблицы целиком |
| `Index Scan` | чтение через индекс + table access |
| `Index Only Scan` | данные взяты из индекса, если visibility map позволяет |
| `Bitmap Index Scan` | собрать matching pages через индекс |
| `Bitmap Heap Scan` | читать страницы после bitmap |
| `Nested Loop` | вложенный цикл, хорош для малых наборов |
| `Hash Join` | join через hash table |
| `Merge Join` | join отсортированных потоков |
| `Sort` | явная сортировка |

## Мини-шпаргалка

- `EXPLAIN ANALYZE` выполняет запрос.
- `BUFFERS` показывает memory/disk поведение.
- Сравни estimated rows и actual rows.
- Большой `shared read` может указывать на I/O.
- Плохие оценки часто лечатся `ANALYZE` и статистикой.
