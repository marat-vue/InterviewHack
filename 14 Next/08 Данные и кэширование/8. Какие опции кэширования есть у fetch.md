# Какие опции кэширования есть у fetch?

> [!summary]
> Next.js расширяет server-side `fetch`: через `cache`, `next.revalidate` и `next.tags` можно управлять кешированием, свежестью и on-demand invalidation данных.

## cache: force-cache

```tsx
await fetch('https://api.example.com/posts', {
  cache: 'force-cache',
})
```

Используется для данных, которые можно кешировать.

Подходит:

- документация;
- статьи;
- категории;
- CMS-контент;
- публичные справочники.

## cache: no-store

```tsx
await fetch('https://api.example.com/account', {
  cache: 'no-store',
})
```

Отключает кеширование для запроса.

Подходит:

- user-specific данные;
- live dashboard;
- данные, которые должны быть свежими на каждый request;
- sensitive request-specific content.

## next.revalidate

```tsx
await fetch('https://api.example.com/products', {
  next: { revalidate: 600 },
})
```

Кеширует данные, но позволяет обновлять их по времени.

## next.tags

```tsx
await fetch('https://api.example.com/posts', {
  next: { tags: ['posts'] },
})
```

Позволяет позже вызвать:

```ts
revalidateTag('posts')
```

## Как выбирать?

| Данные | Опция |
|---|---|
| редко меняются | `force-cache` |
| должны обновляться раз в N секунд | `next.revalidate` |
| нужно обновить после mutation | `next.tags` + `revalidateTag` |
| всегда свежие | `no-store` |

## Что отвечать на собеседовании?

В Next.js `fetch` на сервере поддерживает cache options. `force-cache` кеширует, `no-store` отключает кеш, `next.revalidate` задает время обновления, `next.tags` позволяет инвалидировать данные через `revalidateTag`.

## Частые ошибки

- Ставить `no-store` везде.
- Кешировать private user data.
- Не добавлять tags для будущей invalidation.
- Путать browser cache и Next Data Cache.
- Не проверять production behavior.

## Мини-шпаргалка

- `cache: 'force-cache'`.
- `cache: 'no-store'`.
- `next: { revalidate: 60 }`.
- `next: { tags: ['posts'] }`.
- Tags обновляются через `revalidateTag`.
- Path обновляется через `revalidatePath`.
