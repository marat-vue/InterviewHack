# Что такое Row Level Security и политики доступа?

> [!NOTE]
> Row Level Security, или RLS, ограничивает доступ к строкам на уровне самой БД. Это особенно важно для multi-tenant приложений, где один physical table хранит данные разных tenants.

## Зачем RLS?

Без RLS приложение должно всегда помнить:

```sql
WHERE tenant_id = current_tenant_id
```

Одна забытая проверка может привести к утечке данных.

RLS переносит часть защиты в БД.

## Как включить RLS?

```sql
CREATE TABLE projects (
  id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  tenant_id uuid NOT NULL,
  name text NOT NULL
);

ALTER TABLE projects ENABLE ROW LEVEL SECURITY;
```

## Policy для чтения

```sql
CREATE POLICY tenant_isolation_select
ON projects
FOR SELECT
USING (tenant_id = current_setting('app.tenant_id')::uuid);
```

Перед запросами приложение задает tenant:

```sql
SET app.tenant_id = '00000000-0000-0000-0000-000000000001';
```

## Policy для insert/update

```sql
CREATE POLICY tenant_isolation_write
ON projects
FOR INSERT
WITH CHECK (tenant_id = current_setting('app.tenant_id')::uuid);
```

`USING` отвечает за видимость существующих строк. `WITH CHECK` отвечает за допустимость новых/измененных строк.

## Чем RLS опасен?

Риски:

- забыли включить RLS на таблице;
- superuser/owner bypass;
- connection pool переиспользовал `app.tenant_id`;
- policy слишком широкая;
- tests не проверяют cross-tenant leakage.

В pool-е лучше использовать transaction-local setting:

```sql
SET LOCAL app.tenant_id = '...';
```

## Когда использовать?

Хорошо:

- multi-tenant SaaS;
- internal admin/user separation;
- per-user data isolation;
- defense in depth.

Не заменяет:

- auth в приложении;
- authorization rules;
- audit;
- правильную модель ролей.

## Мини-шпаргалка

- RLS ограничивает строки на уровне БД.
- `ENABLE ROW LEVEL SECURITY` включает механизм.
- `USING` - какие строки видны.
- `WITH CHECK` - какие строки можно вставлять/изменять.
- В connection pool осторожно с session variables.
