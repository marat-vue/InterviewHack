# Почему тестирование важно в больших проектах

> [!summary]
> Тестирование важно в больших проектах, потому что оно снижает риск регрессий, помогает безопасно менять код и фиксирует ожидаемое поведение приложения.

## Главное

Чем больше проект, тем сложнее держать все сценарии в голове. Изменение в одном компоненте может сломать форму, стор, роутинг или интеграцию с API. Тесты становятся страховочной сеткой.

```text
change code
  -> run tests
  -> catch broken behavior early
  -> refactor with confidence
```

## Что дают тесты

- Защиту от регрессий.
- Документацию поведения через примеры.
- Быструю обратную связь при рефакторинге.
- Уверенность при обновлении зависимостей.
- Возможность проверять edge cases без ручного кликанья.

## Пример проблемы

```vue
<template>
  <button :disabled="isSubmitting" @click="submit">
    Отправить
  </button>
</template>
```

Кажется, что компонент простой. Но важно проверить:

- кнопка блокируется во время отправки;
- повторный клик не запускает второй запрос;
- ошибка показывается пользователю;
- успешная отправка очищает форму или переводит на другую страницу.

## Какие уровни тестов бывают

| Уровень | Что проверяет |
| --- | --- |
| Unit | Отдельную функцию, composable или компонент |
| Component | Поведение компонента как UI-единицы |
| Integration | Связку нескольких частей: компонент, store, router, API mock |
| E2E | Реальный пользовательский сценарий в браузере |

## Vue-пример unit/component теста

```js
import { mount } from "@vue/test-utils";
import SubmitButton from "./SubmitButton.vue";

test("disables button while submitting", () => {
  const wrapper = mount(SubmitButton, {
    props: {
      isSubmitting: true,
    },
  });

  expect(wrapper.get("button").attributes("disabled")).toBeDefined();
});
```

## Важный принцип

Тест должен проверять поведение, а не внутреннюю реализацию. Лучше проверять, что пользователь видит ошибку, чем то, как называется внутренний метод компонента.

## Мини-шпаргалка

- Тесты защищают от регрессий.
- В больших проектах они ускоряют изменения, а не замедляют.
- Unit-тесты проверяют маленькие части.
- E2E-тесты проверяют реальные сценарии.
- Хороший тест смотрит на поведение, а не на приватные детали.
