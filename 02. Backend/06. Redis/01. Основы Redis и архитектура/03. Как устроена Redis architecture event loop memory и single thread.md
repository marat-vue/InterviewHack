# Как устроена Redis architecture, event loop, memory и single thread?

> [!NOTE]
> Redis часто называют single-threaded, но это упрощение. Команды над данными исторически выполняются последовательно в основном event loop, а вокруг могут быть фоновые потоки для I/O, persistence и внутренних задач.

## Что значит single-threaded?

Для backend-разработчика главное:

- одна команда Redis выполняется атомарно относительно других команд;
- долгие команды блокируют обработку следующих команд;
- Redis не делает привычные SQL-locks на каждую строку;
- latency зависит не только от CPU, но и от размера ключей, slow commands и network RTT.

Пример проблемы:

```redis
KEYS *
```

На маленькой базе команда кажется безобидной. На production с миллионами ключей она может заблокировать сервер.

## Как проходит команда?

Упрощенно:

```txt
client -> TCP connection -> Redis event loop -> command execution -> response
```

Redis принимает команду, выполняет ее над in-memory структурами и возвращает ответ. Если команда O(1), все быстро. Если команда O(N) по большому ключу, event loop занят дольше.

## Почему атомарность команд важна?

Команды выполняются последовательно, поэтому:

```redis
INCR rate:ip:1.2.3.4
```

атомарна. Два клиента не “потеряют” increment.

Плохо:

```txt
GET counter
counter + 1 в приложении
SET counter newValue
```

Между `GET` и `SET` другой клиент может изменить значение.

Лучше:

```redis
INCR counter
```

или Lua script, если операция сложнее.

## Как Redis использует memory?

Redis хранит dataset в памяти. Это дает скорость, но требует контроля:

- `maxmemory`;
- eviction policy;
- TTL;
- monitoring `used_memory`;
- защита от big keys;
- bounded streams/lists;
- осторожность с JSON blobs.

Если memory закончилась, Redis начинает вести себя согласно `maxmemory-policy`: удалять ключи, отказывать в write-командах или применять другую заданную стратегию.

## Что такое latency в Redis?

Latency складывается из:

- network round trip;
- времени выполнения команды;
- serialization/deserialization;
- queueing внутри клиента;
- persistence spikes;
- fork при RDB/AOF rewrite;
- CPU pressure;
- swap, если Redis вытеснен из RAM.

## Как уменьшать latency?

Практики:

- использовать pipelining для пачек команд;
- избегать `KEYS`, больших `SMEMBERS`, больших `LRANGE`;
- дробить большие значения;
- ставить TTL и memory limits;
- включать slowlog и latency monitoring;
- держать Redis рядом с приложением по сети;
- использовать правильный data type.

## Что значит “Redis быстрый, но не магический”?

Redis быстро выполняет подходящие операции. Но если использовать его как мусорный бак для огромных JSON, делать scan на каждый request или писать бесконечные Streams без trimming, он станет bottleneck-ом.

## Мини-шпаргалка

- Команды атомарны, потому что выполняются последовательно.
- Долгая команда блокирует другие команды.
- Скорость Redis зависит от command complexity и размера данных.
- Memory нужно ограничивать и мониторить.
- Для больших выборок используй incremental подход: `SCAN`, pagination, trimming.
