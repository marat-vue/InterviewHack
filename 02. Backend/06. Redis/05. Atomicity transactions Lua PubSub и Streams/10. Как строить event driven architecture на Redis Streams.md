# Как строить event-driven architecture на Redis Streams?

> [!NOTE]
> Redis Streams позволяют построить простой event-driven backend без отдельного Kafka/RabbitMQ. Это хороший вариант для умеренных нагрузок, background jobs и внутренних событий, если команда понимает pending, retries, trimming и idempotency.

## Базовая схема

```txt
API -> XADD events
worker group -> XREADGROUP
worker -> handle
worker -> XACK
```

## Producer

```ts
await redis.xAdd('events:user', '*', {
  type: 'user.created',
  userId: user.id,
  email: user.email,
});
```

## Consumer group

```ts
try {
  await redis.xGroupCreate('events:user', 'email-workers', '$', {
    MKSTREAM: true,
  });
} catch (error) {
  if (!String(error).includes('BUSYGROUP')) {
    throw error;
  }
}
```

## Worker loop

```ts
while (true) {
  const result = await redis.xReadGroup(
    'email-workers',
    'email-worker-1',
    {
      key: 'events:user',
      id: '>',
    },
    {
      COUNT: 10,
      BLOCK: 5000,
    },
  );

  if (!result) {
    continue;
  }

  for (const stream of result) {
    for (const item of stream.messages) {
      await handleEvent(item.message);
      await redis.xAck('events:user', 'email-workers', item.id);
    }
  }
}
```

## Retry и dead letter

Если сообщение много раз зависает:

- проверяй `XPENDING`;
- забирай через `XAUTOCLAIM`;
- считай attempts;
- после лимита отправляй в `events:user:dlq`.

Пример DLQ:

```redis
XADD events:user:dlq * originalId 1786000000000-0 reason failed
```

## Trimming

```redis
XADD events:user MAXLEN ~ 100000 * type user.created userId 1
```

Без retention stream будет расти бесконечно.

## Когда Redis Streams недостаточно?

Может понадобиться Kafka/RabbitMQ/SQS, если нужны:

- очень большой throughput;
- long retention;
- сложная routing topology;
- cross-region durability;
- mature dead-letter tooling;
- строгие enterprise guarantees.

## Мини-шпаргалка

- Streams подходят для internal event-driven backend.
- `XADD` -> producer.
- `XREADGROUP` -> workers.
- `XACK` -> success.
- `XPENDING`/`XAUTOCLAIM` -> recovery.
- Idempotency обязательна.
- Trimming обязательный production-вопрос.
