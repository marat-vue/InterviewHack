# Как проектировать pagination, filtering и sorting?

> [!summary]
> Списочные REST endpoints почти всегда должны поддерживать pagination, filtering и sorting. Это защищает базу от огромных выборок и дает frontend предсказуемый контракт для таблиц, каталогов и админок.

## Offset pagination

```http
GET /api/products?page=2&limit=20
```

Ответ:

```json
{
  "items": [],
  "meta": {
    "page": 2,
    "limit": 20,
    "total": 135
  }
}
```

Плюсы: просто реализовать. Минусы: на больших таблицах может быть медленно, а при изменении данных между запросами возможны дубли или пропуски.

## Cursor pagination

```http
GET /api/products?cursor=prd_100&limit=20
```

Ответ:

```json
{
  "items": [],
  "nextCursor": "prd_120"
}
```

Cursor pagination лучше для бесконечной ленты и больших данных.

## Filtering

```http
GET /api/products?categoryId=10&minPrice=100&inStock=true
```

Фильтры должны быть явно поддержаны API. Не стоит позволять клиенту передавать произвольный SQL-like filter без контроля.

## Sorting

```http
GET /api/products?sortBy=price&sortOrder=asc
```

Whitelist сортируемых полей обязателен:

```ts
const allowedSortFields = ['createdAt', 'price', 'title'];
```

Иначе можно получить ошибки, утечки внутренних полей или дорогие запросы без индексов.

## Мини-шпаргалка

- Списки должны иметь `limit`.
- Offset pagination проста, cursor pagination лучше для больших потоков.
- Filters должны быть whitelisted.
- Sorting fields должны быть whitelisted.
- Response должен возвращать `items` и metadata.
