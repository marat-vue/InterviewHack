# Как dockerize Nuxt Nitro проект для production?

> [!NOTE]
> Production Nuxt/Nitro image должен собрать проект, положить в final stage только `.output` и запустить `node .output/server/index.mjs`. Для SSR-приложения это не static Nginx-сайт, а Node.js server.

## Что именно собирает Nuxt?

Команда:

```bash
pnpm build
```

создает папку:

```text
.output/
  public/
  server/
    index.mjs
```

`index.mjs` - entrypoint Nitro server. В Docker контейнере его обычно запускают так:

```bash
node .output/server/index.mjs
```

## Production Dockerfile для pnpm

```dockerfile
# syntax=docker/dockerfile:1.7

FROM node:22-bookworm-slim AS base
WORKDIR /app
ENV PNPM_HOME=/pnpm
ENV PATH=$PNPM_HOME:$PATH
RUN corepack enable

FROM base AS deps
COPY package.json pnpm-lock.yaml ./
RUN pnpm install --frozen-lockfile

FROM base AS build
COPY --from=deps /app/node_modules ./node_modules
COPY . .
RUN pnpm build

FROM node:22-bookworm-slim AS runner
WORKDIR /app
ENV NODE_ENV=production
ENV NITRO_HOST=0.0.0.0
ENV NITRO_PORT=3000

RUN groupadd --system --gid 1001 nodejs \
  && useradd --system --uid 1001 --gid nodejs nuxt

COPY --from=build --chown=nuxt:nodejs /app/.output ./.output

USER nuxt
EXPOSE 3000
CMD ["node", ".output/server/index.mjs"]
```

## Почему `NITRO_HOST=0.0.0.0`?

Внутри контейнера приложение должно слушать все интерфейсы контейнера. Если оно слушает только `127.0.0.1`, порт может быть доступен только внутри самого контейнера.

Правильно:

```env
NITRO_HOST=0.0.0.0
NITRO_PORT=3000
```

## Вариант для npm

```dockerfile
FROM node:22-bookworm-slim AS deps
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci

FROM node:22-bookworm-slim AS build
WORKDIR /app
COPY --from=deps /app/node_modules ./node_modules
COPY . .
RUN npm run build

FROM node:22-bookworm-slim AS runner
WORKDIR /app
ENV NODE_ENV=production
ENV NITRO_HOST=0.0.0.0
ENV NITRO_PORT=3000
COPY --from=build /app/.output ./.output
EXPOSE 3000
CMD ["node", ".output/server/index.mjs"]
```

## Что положить в `.dockerignore`?

```dockerignore
.git
.nuxt
.output
node_modules
npm-debug.log
pnpm-debug.log
.env
.env.*
coverage
dist
```

Идея простая: build context не должен тащить локальные зависимости, старую сборку, секреты и мусор.

## Alpine или Debian slim?

`node:22-alpine` меньше, но использует musl libc. Для простого Nuxt-приложения это часто нормально.

`node:22-bookworm-slim` обычно спокойнее для проектов с native dependencies:

- Prisma engines;
- image processing;
- bcrypt/argon2;
- sharp;
- canvas;
- системные OpenSSL/libc зависимости.

Если в проекте есть Prisma, я бы начинал с Debian slim и уменьшал image уже после стабильной сборки.

## Как собрать и запустить?

```bash
docker build -t my-nuxt-app .
docker run --rm -p 3000:3000 my-nuxt-app
```

Проверка:

```bash
curl http://localhost:3000
```

## Что отвечать на собеседовании?

Nuxt с Nitro в SSR-режиме собирается в `.output`, а production container запускает `node .output/server/index.mjs`. Dockerfile обычно multi-stage: сначала устанавливаются зависимости и выполняется `pnpm build`, потом в final image копируется только `.output`. Для Docker важно выставить `NITRO_HOST=0.0.0.0`, иначе сервер может слушать только loopback внутри контейнера.

## Частые ошибки

- Запускать Nuxt production через `pnpm dev`.
- Копировать весь проект и `node_modules` в final image.
- Забывать `NITRO_HOST=0.0.0.0`.
- Пытаться раздавать SSR Nuxt только через Nginx как static folder.
- Использовать Alpine с native dependency, которая не собрана под musl.
- Класть `.env` в image.

## Мини-шпаргалка

- Build: `pnpm build`.
- Output: `.output`.
- Start: `node .output/server/index.mjs`.
- Host: `NITRO_HOST=0.0.0.0`.
- Port: `NITRO_PORT=3000`.
- Final image: только runtime минимум.
