# Как проектировать ключи, namespaces и naming convention в Redis?

> [!NOTE]
> В Redis нет таблиц как в SQL. Главная единица моделирования - ключ. Хорошие имена ключей делают систему понятной, безопасной для очистки и удобной для мониторинга.

## Почему naming важен?

Плохой ключ:

```txt
123
data
cache
```

Хороший ключ:

```txt
prod:api:user:123:profile
prod:api:rate-limit:ip:192.0.2.1
prod:api:session:abc
```

Хороший ключ сразу отвечает:

- какое приложение;
- какое окружение;
- какая сущность;
- какой id;
- какая цель данных;
- можно ли ключ удалить по prefix.

## Базовый формат

```txt
<env>:<app>:<domain>:<entity>:<id>:<field>
```

Примеры:

```txt
prod:shop:cache:product:42
prod:shop:cart:user:123
staging:shop:rate:ip:203.0.113.10
dev:interviewhack:stream:orders
```

## Нужно ли добавлять env в ключ?

Да, если несколько окружений используют один Redis instance или cluster.

```txt
dev:api:...
staging:api:...
prod:api:...
```

Если у каждого окружения отдельный Redis, env prefix все равно полезен для safety и диагностики.

## Как именовать cache keys?

```txt
cache:user:<id>
cache:post:<id>
cache:catalog:v1:<category>:<page>
```

Версионирование:

```txt
cache:v1:catalog:phones:1
cache:v2:catalog:phones:1
```

Это позволяет invalidation через смену версии без массового удаления ключей.

## Как именовать locks?

```txt
lock:job:<jobId>
lock:user:<userId>:billing
```

Значение lock лучше делать уникальным token:

```redis
SET lock:job:42 worker-7 NX PX 30000
```

Удалять lock нужно только если token совпадает, иначе один worker может удалить lock другого.

## Как именовать streams и consumer groups?

Stream:

```txt
stream:orders
stream:emails
stream:audit
```

Consumer group:

```txt
billing-service
email-worker
analytics-pipeline
```

Consumer:

```txt
email-worker-1
email-worker-2
```

## Как не ошибиться с multi-tenant keys?

Добавляй tenant:

```txt
tenant:<tenantId>:user:<userId>:profile
tenant:<tenantId>:rate:user:<userId>
```

Не кешируй tenant-specific данные без tenant в ключе. Это может привести к утечке данных между клиентами.

## Как работать с Redis Cluster hash tags?

В Redis Cluster multi-key операции работают только когда ключи попадают в один hash slot. Hash tag фиксирует часть ключа для hash slot:

```txt
cart:{user:123}:items
cart:{user:123}:total
```

Оба ключа попадут в один slot, потому что hash считается по `user:123`.

## Мини-шпаргалка

- Используй `:` как разделитель.
- Добавляй env/app/domain.
- Для tenant data добавляй tenant id.
- Для cache удобно version prefix.
- Для Cluster multi-key операций используй hash tags.
- Не используй `KEYS prefix:*` в production, проектируй так, чтобы массовые операции были редкими.
