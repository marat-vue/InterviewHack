# Какие ограничения Redis важно знать?

> [!NOTE]
> Redis очень быстрый, но у него есть ограничения. Сильный backend-разработчик умеет объяснить не только преимущества Redis, но и риски: memory, durability, blocking commands, cluster constraints, at-most-once Pub/Sub и operational complexity.

## Redis хранит данные в памяти

Главное ограничение:

```txt
dataset должен помещаться в memory budget
```

Даже при persistence Redis работает как in-memory system. Если хранить слишком много:

- начнется eviction;
- writes могут получить OOM error;
- latency вырастет;
- OS может начать swap, что крайне плохо для Redis.

## Большие ключи опасны

Big key - ключ с большим значением или огромной коллекцией:

```txt
list на миллионы элементов
hash с сотнями тысяч fields
string на десятки MB
stream без trimming
```

Риски:

- медленное чтение;
- медленное удаление;
- network spikes;
- блокировка event loop;
- сложный resharding.

## Некоторые команды блокируют event loop

Опасные команды или паттерны:

```redis
KEYS *
SMEMBERS huge:set
LRANGE huge:list 0 -1
HGETALL huge:hash
DEL huge:key
```

Часто лучше:

```redis
SCAN
SSCAN
HSCAN
ZSCAN
UNLINK
```

`UNLINK` удаляет ключ асинхроннее, чем `DEL`, и лучше подходит для больших объектов.

## Pub/Sub не гарантирует доставку offline-подписчикам

Redis Pub/Sub имеет at-most-once semantics. Если подписчик отключен, сообщение потеряно.

Если нужна история, retry и replay, выбирай Streams:

```redis
XADD events * type user.created id 1
XREADGROUP GROUP workers worker-1 STREAMS events >
```

## Transactions не как в SQL

`MULTI/EXEC` группирует команды, но:

- нет автоматического rollback как в SQL;
- ошибки команд нужно обрабатывать;
- optimistic locking делается через `WATCH`;
- сложную атомарную логику часто проще писать Lua script.

## Cluster имеет ограничения multi-key операций

В Redis Cluster ключи распределяются по hash slots. Multi-key операции возможны только когда ключи в одном slot.

Правильно:

```txt
cart:{user:1}:items
cart:{user:1}:total
```

Плохо:

```txt
cart:user:1:items
cart:user:1:total
```

Во втором случае ключи могут оказаться в разных slots.

## Persistence не делает Redis равным SQL

RDB/AOF помогают пережить restart, но:

- есть trade-off между speed и durability;
- при async replication возможна потеря последних writes;
- AOF rewrite может давать нагрузку;
- backups и restore нужно проверять заранее.

## Мини-шпаргалка

- Redis ограничен памятью.
- Big keys и O(N) команды опасны.
- Pub/Sub не хранит сообщения.
- Streams лучше для durable events.
- Transactions не дают SQL-style rollback.
- Cluster требует думать о hash slots.
- Persistence нужно настраивать под допустимую потерю данных.
