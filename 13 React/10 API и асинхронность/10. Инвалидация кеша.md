# Инвалидация кеша

> [!summary]
> Инвалидация кеша - это пометка cached data как устаревшей после изменения данных на сервере. После `POST`, `PUT`, `PATCH` или `DELETE` нужно обновить или инвалидировать связанные query, иначе пользователь увидит старый UI.

## Почему кеш устаревает?

Пример:

```text
1. Кеш: ['users'] содержит список пользователей
2. Пользователь изменил имя
3. Сервер сохранил новое имя
4. Кеш ['users'] все еще содержит старое имя
```

Без инвалидации разные части UI могут показывать разные данные.

## Инвалидация в TanStack Query

```jsx
const queryClient = useQueryClient()

const mutation = useMutation({
  mutationFn: updateUser,
  onSuccess: (_, variables) => {
    queryClient.invalidateQueries({
      queryKey: ['user', variables.userId],
    })

    queryClient.invalidateQueries({
      queryKey: ['users'],
    })
  },
})
```

`invalidateQueries` помечает query как stale и может запустить refetch, если query активна.

## Когда использовать setQueryData?

Если сервер вернул свежий объект, можно обновить кеш напрямую:

```jsx
const mutation = useMutation({
  mutationFn: updateUser,
  onSuccess: (updatedUser) => {
    queryClient.setQueryData(['user', updatedUser.id], updatedUser)
  },
})
```

Если изменение затрагивает списки, счетчики и связанные сущности, часто проще инвалидировать связанные query.

## Инвалидация в SWR

```jsx
import { mutate } from 'swr'

await updateUser(userId, values)
mutate(`/api/users/${userId}`)
mutate('/api/users')
```

Ключ должен совпадать с ключом, который использует `useSWR`.

## Какие query инвалидировать?

После изменения пользователя:

```text
['user', id]
['users']
['current-user']
['permissions', id]
```

После добавления комментария:

```text
['comments', postId]
['post', postId]
['posts']
```

Думай не про endpoint, а про все UI-данные, которые стали потенциально устаревшими.

## Мини-шпаргалка

- Мутация на сервере почти всегда требует работы с кешем.
- `invalidateQueries` помечает данные как stale.
- `setQueryData` обновляет кеш напрямую.
- Инвалидируй связанные списки и детали.
- Query key должен быть стабильным и предсказуемым.
