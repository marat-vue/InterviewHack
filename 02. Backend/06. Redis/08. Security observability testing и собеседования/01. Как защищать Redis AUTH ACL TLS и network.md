# Как защищать Redis: AUTH, ACL, TLS и network?

> [!NOTE]
> Redis нельзя выставлять публично в интернет. Безопасность Redis начинается с сети, затем добавляются AUTH/ACL, TLS, secrets management, ограничение команд и мониторинг доступа.

## Главное правило

```txt
Redis должен быть доступен только приложению и администраторам
```

Не делай:

```txt
0.0.0.0:6379 открыт публично
```

Даже с паролем это плохая идея.

## Network security

Используй:

- private subnet;
- security groups/firewall;
- VPC peering;
- Kubernetes NetworkPolicy;
- managed Redis private endpoint;
- запрет public access.

## AUTH

Простой пароль:

```txt
requirepass strong_password
```

Подключение:

```bash
REDIS_URL="redis://default:strong_password@redis.internal:6379"
```

AUTH лучше, чем ничего, но современный Redis позволяет делать ACL users с разными правами.

## TLS

TLS нужен, если traffic проходит через недоверенную сеть или это требует compliance.

URL:

```bash
REDIS_URL="rediss://default:password@redis.example.com:6380"
```

Managed providers часто включают TLS через `rediss://`.

## Команды, которые стоит ограничить

Опасные команды:

- `FLUSHALL`;
- `FLUSHDB`;
- `CONFIG`;
- `SHUTDOWN`;
- `EVAL`, если не нужен;
- `KEYS`, если можно ограничить;
- dangerous module commands.

Ограничение делается через ACL.

## Secrets

Не коммить:

- Redis password;
- TLS private keys;
- managed provider tokens;
- `.env`;
- production URLs.

Храни в:

- platform secrets;
- CI/CD secrets;
- secret manager;
- Kubernetes Secrets с нормальной политикой доступа.

## Мини-шпаргалка

- Redis port не должен быть публичным.
- AUTH/ACL обязательны.
- TLS нужен вне trusted network.
- Secrets не коммитятся.
- Опасные команды ограничиваются.
- Logs не должны содержать Redis URL с паролем.
