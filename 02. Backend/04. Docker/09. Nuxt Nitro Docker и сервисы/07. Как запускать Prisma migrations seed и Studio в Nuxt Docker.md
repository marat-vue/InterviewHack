# Как запускать Prisma migrations, seed и Studio в Nuxt Docker?

> [!NOTE]
> В Nuxt/Nitro проекте с Prisma важно разделить `prisma generate`, migrations и запуск приложения. `generate` нужен при сборке, `migrate deploy` запускают один раз перед релизом, а seed и Studio обычно нужны только в dev.

## Что где выполняется?

| Команда | Где обычно запускается | Зачем |
| --- | --- | --- |
| `prisma generate` | build stage | Сгенерировать Prisma Client под окружение сборки/runtime. |
| `prisma migrate dev` | dev container | Создать и применить новую migration локально. |
| `prisma migrate deploy` | CI/CD или one-off container | Применить уже созданные migrations в production/stage. |
| `prisma db seed` | dev или controlled seed job | Заполнить базу начальными данными. |
| `prisma studio` | dev profile | Открыть UI для локальной базы. |

## Dockerfile с Prisma

```dockerfile
FROM node:22-bookworm-slim AS base
WORKDIR /app
ENV PNPM_HOME=/pnpm
ENV PATH=$PNPM_HOME:$PATH
RUN corepack enable

FROM base AS deps
COPY package.json pnpm-lock.yaml ./
RUN pnpm install --frozen-lockfile

FROM base AS build
COPY --from=deps /app/node_modules ./node_modules
COPY package.json pnpm-lock.yaml ./
COPY prisma ./prisma
RUN pnpm prisma generate
COPY . .
RUN pnpm build

FROM node:22-bookworm-slim AS runner
WORKDIR /app
ENV NODE_ENV=production
ENV NITRO_HOST=0.0.0.0
ENV NITRO_PORT=3000
COPY --from=build /app/.output ./.output
EXPOSE 3000
CMD ["node", ".output/server/index.mjs"]
```

Почему `prisma generate` до `pnpm build`? Потому что server code может импортировать `@prisma/client` во время build.

## Migration service в Compose

```yaml
services:
  migrate:
    build:
      context: .
      target: build
    command: pnpm prisma migrate deploy
    environment:
      DATABASE_URL: postgresql://app:secret@db:5432/app
    depends_on:
      db:
        condition: service_healthy

  app:
    build:
      context: .
    environment:
      DATABASE_URL: postgresql://app:secret@db:5432/app
    depends_on:
      migrate:
        condition: service_completed_successfully
```

Этот подход удобен для локального stage. В реальном production migrations часто запускают отдельным CI/CD job.

## One-off запуск migrations

```bash
docker compose run --rm migrate
docker compose up -d app
```

Или через app container в dev:

```bash
docker compose exec app pnpm prisma migrate dev
docker compose exec app pnpm prisma db seed
```

## Почему не запускать migration в каждой реплике?

Плохая идея:

```dockerfile
CMD ["sh", "-c", "pnpm prisma migrate deploy && node .output/server/index.mjs"]
```

Проблемы:

- несколько replicas могут одновременно попытаться применить migrations;
- startup приложения зависит от состояния базы;
- migration failure превращается в restart loop;
- сложнее наблюдать и откатывать релиз;
- приложение смешивает runtime и release-management ответственность.

## Seed

Dev seed:

```bash
docker compose exec app pnpm prisma db seed
```

Seed должен быть:

- idempotent;
- безопасен для повторного запуска;
- явно отделен от production startup;
- защищен от случайного запуска в production.

Пример package.json:

```json
{
  "scripts": {
    "db:migrate": "prisma migrate deploy",
    "db:seed": "prisma db seed",
    "db:studio": "prisma studio --hostname 0.0.0.0"
  }
}
```

## Prisma Studio через profile

```yaml
services:
  prisma-studio:
    build:
      context: .
      target: build
    command: pnpm prisma studio --hostname 0.0.0.0 --port 5555
    environment:
      DATABASE_URL: postgresql://app:secret@db:5432/app
    ports:
      - "5555:5555"
    depends_on:
      db:
        condition: service_healthy
    profiles:
      - tools
```

Запуск:

```bash
docker compose --profile tools up prisma-studio
```

## Что отвечать на собеседовании?

В Docker-проекте с Nuxt и Prisma я генерирую Prisma Client на build stage, а migrations запускаю отдельно: one-off service, CI/CD job или release command. Для production используется `prisma migrate deploy`, а не `migrate dev`. Seed и Prisma Studio обычно относятся к dev/tools профилю.

## Частые ошибки

- Забыть `pnpm prisma generate` перед build.
- Использовать `migrate dev` в production.
- Запускать migrations из каждой app replica.
- Не копировать папку `prisma` в build stage.
- Генерировать Prisma Client под одну ОС, а запускать под другой несовместимой средой.
- Открывать Prisma Studio в production.

## Мини-шпаргалка

- Build: `prisma generate`.
- Dev migration: `prisma migrate dev`.
- Prod migration: `prisma migrate deploy`.
- Seed: controlled and idempotent.
- Studio: только tools/dev profile.
- Migrations: один раз перед app rollout.
