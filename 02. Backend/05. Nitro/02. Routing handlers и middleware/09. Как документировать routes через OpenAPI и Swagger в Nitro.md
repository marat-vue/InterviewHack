# Как документировать routes через OpenAPI и Swagger в Nitro?

> [!NOTE]
> Nitro умеет генерировать OpenAPI 3.1.0 спецификацию из route metadata и показывать интерактивную документацию через Scalar и Swagger UI. Это экспериментальная возможность Nitro v3, но для учебного backend-раздела ее важно знать: она превращает набор handlers в понятный API contract.

## Зачем OpenAPI в Nitro?

OpenAPI нужен, чтобы:

- описывать endpoints рядом с кодом;
- фиксировать contract между backend и frontend;
- видеть query/path/header параметры;
- описывать body, responses, status codes и error-сценарии;
- подключать Swagger UI или Scalar для ручной проверки API;
- генерировать typed clients;
- проверять изменения API на code review;
- документировать auth requirements.

Без OpenAPI API быстро превращается в набор устных договоренностей. На маленьком проекте это терпимо, но на реальном backend-е frontend, QA, mobile и интеграции должны видеть один источник правды.

## Что именно дает Nitro?

Nitro:

- сканирует route handlers;
- читает `defineRouteMeta`;
- извлекает `openAPI` metadata на build-time;
- генерирует OpenAPI 3.1.0 JSON;
- поднимает dev endpoints для документации;
- умеет показывать Swagger UI;
- умеет показывать Scalar UI;
- позволяет настроить route, meta, UI и production behavior.

Важно: `defineRouteMeta` - build-time macro. Metadata извлекается статически и не добавляет runtime overhead в handler.

## Как включить OpenAPI?

В standalone Nitro:

```ts
// nitro.config.ts
import { defineConfig } from 'nitro';

export default defineConfig({
  experimental: {
    openAPI: true,
  },
});
```

После включения в development доступны:

| Endpoint | Что открывает |
|---|---|
| `/_openapi.json` | OpenAPI 3.1.0 JSON specification |
| `/_scalar` | Scalar API reference UI |
| `/_swagger` | Swagger UI |

`/_openapi.json` нужен машинам и генераторам клиентов. `/_swagger` и `/_scalar` нужны людям: открыть в браузере, посмотреть route, отправить пробный запрос.

## Как настроить title, version, Swagger route и Scalar route?

```ts
// nitro.config.ts
import { defineConfig } from 'nitro';

export default defineConfig({
  experimental: {
    openAPI: true,
  },
  openAPI: {
    route: '/_docs/openapi.json',
    meta: {
      title: 'InterviewHack API',
      description: 'Backend API на Nitro',
      version: '1.0.0',
    },
    ui: {
      scalar: {
        route: '/_docs/scalar',
        theme: 'blue',
      },
      swagger: {
        route: '/_docs/swagger',
      },
    },
  },
});
```

После такой настройки:

```txt
/_docs/openapi.json
/_docs/scalar
/_docs/swagger
```

## Как отключить Swagger UI?

Если нужен только JSON и Scalar:

```ts
// nitro.config.ts
import { defineConfig } from 'nitro';

export default defineConfig({
  experimental: {
    openAPI: true,
  },
  openAPI: {
    ui: {
      swagger: false,
    },
  },
});
```

Это полезно, если команда стандартизировалась на Scalar или если Swagger UI не должен быть доступен даже в dev.

## Как включить OpenAPI в production?

По умолчанию OpenAPI endpoints доступны только в development. Для production нужно явно указать `production`:

```ts
// nitro.config.ts
import { defineConfig } from 'nitro';

export default defineConfig({
  experimental: {
    openAPI: true,
  },
  openAPI: {
    production: 'prerender',
  },
});
```

Режимы:

| Значение | Поведение |
|---|---|
| `false` | выключено в production, это default |
| `'runtime'` | спецификация генерируется на runtime request |
| `'prerender'` | спецификация генерируется на build time и отдается как static file |

Обычно выбирают `prerender`: быстрее, проще кешировать, меньше runtime-рисков. `runtime` нужен, если документация зависит от runtime данных.

Если включаешь docs в production, защищай endpoints через auth, IP allowlist, internal network или отдельный deployment. Public Swagger может раскрыть приватные routes, схемы ошибок и internal naming.

## Как добавить route meta?

```ts
// routes/api/users/[id].get.ts
import { defineHandler, defineRouteMeta } from 'nitro';
import { getRouterParam, getQuery } from 'nitro/h3';

defineRouteMeta({
  openAPI: {
    tags: ['users'],
    summary: 'Получить пользователя',
    description: 'Возвращает пользователя по id. Query параметр include добавляет связанные сущности.',
    parameters: [
      {
        in: 'query',
        name: 'include',
        required: false,
        description: 'Comma-separated список связей: profile,roles',
        schema: {
          type: 'string',
          example: 'profile,roles',
        },
      },
    ],
    responses: {
      200: {
        description: 'Пользователь найден',
        content: {
          'application/json': {
            schema: {
              $ref: '#/components/schemas/User',
            },
          },
        },
      },
      404: {
        description: 'Пользователь не найден',
      },
    },
  },
});

export default defineHandler(async (event) => {
  const id = getRouterParam(event, 'id');
  const query = getQuery(event);

  return {
    id,
    email: 'admin@example.com',
    include: query.include,
  };
});
```

Path parameter `id` Nitro может вывести из route pattern. Query/header/cookie параметры лучше описывать явно.

## Как описать POST body?

```ts
// routes/api/users.post.ts
import { defineHandler, defineRouteMeta } from 'nitro';
import { createError } from 'nitro/h3';

defineRouteMeta({
  openAPI: {
    tags: ['users'],
    summary: 'Создать пользователя',
    requestBody: {
      required: true,
      content: {
        'application/json': {
          schema: {
            type: 'object',
            required: ['email', 'name'],
            properties: {
              email: {
                type: 'string',
                format: 'email',
                example: 'new-user@example.com',
              },
              name: {
                type: 'string',
                minLength: 2,
                example: 'Marat',
              },
            },
          },
        },
      },
    },
    responses: {
      201: {
        description: 'Пользователь создан',
      },
      400: {
        description: 'Некорректный body',
      },
      409: {
        description: 'Email уже занят',
      },
    },
  },
});

export default defineHandler(async (event) => {
  const body = await event.req.json();

  if (!body.email) {
    throw createError({
      statusCode: 400,
      statusMessage: 'Email is required',
    });
  }

  return {
    id: 'user_1',
    email: body.email,
  };
});
```

OpenAPI schema не заменяет runtime validation. Она документирует contract. Проверять body все равно нужно через Zod, Valibot, собственные guards или сервисный слой.

## Как вынести общие schemas в components?

Через `$global` можно добавить reusable schemas в `components`:

```ts
// routes/api/users.get.ts
import { defineHandler, defineRouteMeta } from 'nitro';

defineRouteMeta({
  openAPI: {
    tags: ['users'],
    summary: 'Список пользователей',
    responses: {
      200: {
        description: 'Список пользователей',
        content: {
          'application/json': {
            schema: {
              type: 'array',
              items: {
                $ref: '#/components/schemas/User',
              },
            },
          },
        },
      },
    },
    $global: {
      components: {
        schemas: {
          User: {
            type: 'object',
            required: ['id', 'email'],
            properties: {
              id: {
                type: 'string',
              },
              email: {
                type: 'string',
                format: 'email',
              },
              name: {
                type: 'string',
                nullable: true,
              },
            },
          },
        },
      },
    },
  },
});

export default defineHandler(() => {
  return [
    {
      id: 'user_1',
      email: 'admin@example.com',
      name: 'Admin',
    },
  ];
});
```

Так один `User` можно переиспользовать в разных routes через `$ref`.

## Как описать auth через security?

```ts
defineRouteMeta({
  openAPI: {
    tags: ['posts'],
    summary: 'Создать пост',
    security: [
      {
        sessionCookie: [],
      },
    ],
    responses: {
      201: {
        description: 'Пост создан',
      },
      401: {
        description: 'Пользователь не авторизован',
      },
    },
    $global: {
      components: {
        securitySchemes: {
          sessionCookie: {
            type: 'apiKey',
            in: 'cookie',
            name: 'better-auth.session_token',
          },
        },
      },
    },
  },
});
```

Для Bearer token схема обычно такая:

```ts
securitySchemes: {
  bearerAuth: {
    type: 'http',
    scheme: 'bearer',
  },
}
```

## Какие поля OpenAPI Operation Object чаще всего использовать?

| Поле | Зачем нужно |
|---|---|
| `tags` | группирует routes в Swagger/Scalar |
| `summary` | короткий заголовок операции |
| `description` | подробное описание поведения |
| `operationId` | стабильное имя для client generation |
| `parameters` | path/query/header/cookie параметры |
| `requestBody` | JSON/form/multipart body |
| `responses` | status codes, content types и schemas |
| `security` | требования к auth |
| `deprecated` | помечает route как устаревший |
| `$global` | добавляет reusable `components` |

## Как совместить Zod validation и OpenAPI?

Частый подход:

```txt
server/
  schemas/
    user.ts
  routes/
    api/
      users.post.ts
```

`server/schemas/user.ts`:

```ts
import { z } from 'zod';

export const createUserSchema = z.object({
  email: z.string().email(),
  name: z.string().min(2),
});
```

В route:

```ts
import { defineHandler } from 'nitro';
import { createError } from 'nitro/h3';
import { createUserSchema } from '../../schemas/user';

export default defineHandler(async (event) => {
  const result = createUserSchema.safeParse(await event.req.json());

  if (!result.success) {
    throw createError({
      statusCode: 400,
      statusMessage: 'Validation failed',
      data: result.error.flatten(),
    });
  }

  return result.data;
});
```

А OpenAPI schema можно:

- описать вручную;
- сгенерировать из Zod через отдельный инструмент;
- держать snapshot OpenAPI в tests, чтобы замечать расхождения.

Nitro сам по себе не превращает любую Zod schema в идеальную OpenAPI schema без дополнительного слоя.

## Как проверить Swagger руками?

1. Включи `experimental.openAPI`.
2. Запусти `nitro dev`.
3. Открой `http://localhost:3000/_swagger`.
4. Проверь, что route виден в правильном tag.
5. Открой `http://localhost:3000/_openapi.json`.
6. Проверь `paths`, `components.schemas`, `securitySchemes`.
7. Отправь пробный запрос через Swagger UI.

## Что спрашивают на собеседовании?

Могут спросить:

- чем OpenAPI отличается от Swagger;
- где в Nitro лежит route metadata;
- зачем нужен `operationId`;
- почему OpenAPI не заменяет validation;
- как описать auth;
- что делать с docs в production;
- как не дублировать schemas;
- почему `defineRouteMeta` не должен зависеть от runtime values.

Короткий ответ: OpenAPI - это спецификация contract, Swagger UI - интерфейс для просмотра и тестирования этой спецификации.

## Мини-шпаргалка

- Включение: `experimental.openAPI: true`.
- JSON: `/_openapi.json`.
- Swagger UI: `/_swagger`.
- Scalar UI: `/_scalar`.
- Route metadata: `defineRouteMeta({ openAPI: ... })`.
- Path params могут выводиться из route pattern.
- Query/header/body/responses лучше описывать явно.
- Production docs по умолчанию выключены.
- Для production обычно выбирай `production: 'prerender'` и защищай docs.
