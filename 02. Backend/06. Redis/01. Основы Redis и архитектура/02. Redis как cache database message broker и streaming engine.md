# Redis как cache, database, message broker и streaming engine

> [!NOTE]
> Redis часто называют cache, но документация описывает его шире: Redis может быть cache, database, streaming engine и message broker. Важно понимать, какой режим ты используешь, потому что от этого зависят TTL, persistence, надежность и модель ошибок.

## Redis как cache

Cache хранит копию данных, которые можно восстановить из primary source:

```txt
PostgreSQL -> source of truth
Redis -> быстрый временный слой чтения
```

Пример:

```redis
SET product:42 '{"id":42,"price":100}' EX 300
GET product:42
```

Зачем:

- снизить нагрузку на БД;
- ускорить повторяющиеся чтения;
- защититься от всплесков трафика;
- кешировать external API responses.

Риск:

- stale data;
- cache stampede;
- неправильная invalidation;
- зависимость приложения от cache, который должен быть disposable.

## Redis как database

Redis может быть primary storage для некоторых типов данных:

- leaderboard;
- counters;
- user presence;
- short-lived tokens;
- queue state;
- feature flags;
- realtime state.

Пример счетчика:

```redis
INCR views:post:42
EXPIRE views:post:42 86400
```

Если Redis - database, нужно включить:

- persistence;
- replication;
- backups;
- monitoring;
- memory policy;
- recovery plan.

## Redis как message broker

Redis поддерживает Pub/Sub:

```redis
SUBSCRIBE notifications
PUBLISH notifications '{"type":"user.created","id":"1"}'
```

Pub/Sub подходит для:

- WebSocket fan-out;
- cache invalidation signals;
- online notifications;
- low-latency ephemeral messages.

Но Pub/Sub не хранит сообщения. Если подписчик offline, сообщение потеряно.

## Redis как streaming engine

Streams - append-only log:

```redis
XADD orders * type created orderId 42
XREAD COUNT 10 STREAMS orders 0
```

Streams подходят для:

- durable event log;
- consumer groups;
- background processing;
- retry после падения consumer;
- replay событий.

В отличие от Pub/Sub, Streams хранят историю и имеют pending entries.

## Как выбрать режим?

| Задача | Redis-режим |
|---|---|
| Быстро отдать карточку товара | Cache |
| Хранить session/token с TTL | KV database |
| Разослать online-событие | Pub/Sub |
| Обработать событие надежно | Streams |
| Посчитать rate limit | Atomic counter |
| Сделать leaderboard | Sorted set |
| Найти online users | Set |

## Что отвечать на собеседовании?

Хороший ответ:

> Redis может играть разные роли. Для cache важнее TTL и invalidation. Для database - persistence и backup. Для Pub/Sub - latency и online-доставка. Для Streams - durable log, consumer groups и retries. Нельзя переносить требования одного режима на другой.

## Мини-шпаргалка

- Cache можно потерять.
- Database нельзя потерять без последствия.
- Pub/Sub быстрый, но ephemeral.
- Streams устойчивее, потому что сообщения сохраняются.
- Выбор Redis data type важнее, чем просто “положить JSON строкой”.
