# Глобальный стейт и производительность

> [!summary]
> Глобальный state удобен для данных, которые действительно нужны многим частям приложения. Но если складывать туда все подряд, каждое изменение может затрагивать слишком большую часть дерева и усложнять оптимизацию.

## Что такое глобальный state?

Глобальный state - это данные, доступные из разных частей приложения:

- текущий пользователь;
- тема;
- язык;
- корзина;
- feature flags;
- права доступа;
- server cache;
- состояние авторизации.

В React его часто делают через Context, Redux, Zustand, Jotai, MobX или TanStack Query.

## Почему избыточный глобальный state вреден?

Проблема не в самом глобальном state, а в ширине подписки.

```jsx
const AppContext = createContext(null)

function AppProvider({ children }) {
  const [state, setState] = useState({
    theme: 'dark',
    search: '',
    cart: [],
    user: null,
  })

  return (
    <AppContext.Provider value={{ state, setState }}>
      {children}
    </AppContext.Provider>
  )
}
```

Если изменится `search`, новое значение context получат все потребители `AppContext`, даже если им нужна только `theme`.

## Как сделать лучше?

Разделить независимые данные:

```jsx
<ThemeProvider>
  <AuthProvider>
    <CartProvider>
      <App />
    </CartProvider>
  </AuthProvider>
</ThemeProvider>
```

И держать локальное состояние локально:

```jsx
function SearchBox() {
  const [query, setQuery] = useState('')

  return <input value={query} onChange={(event) => setQuery(event.target.value)} />
}
```

Если `query` нужен только поиску, ему не место в глобальном store.

## Селекторы

State managers часто позволяют подписаться только на конкретный кусок state.

```jsx
const userName = useUserStore((state) => state.user.name)
const setTheme = useSettingsStore((state) => state.setTheme)
```

Это лучше, чем подписывать компонент на весь store:

```jsx
const state = useUserStore()
```

## Server state - отдельная категория

Данные с сервера не всегда стоит хранить как обычный client state. Для них важны:

- загрузка;
- ошибка;
- кеш;
- повторная загрузка;
- инвалидация;
- синхронизация между вкладками;
- stale data.

Поэтому для server state часто используют TanStack Query, SWR или возможности фреймворка.

## Мини-шпаргалка

- Глобальный state нужен для реально общих данных.
- Локальные данные лучше держать ближе к UI.
- Большой context value вызывает широкие обновления.
- Селекторы уменьшают лишние render.
- Server state лучше отделять от client state.
