# Как SSR работает с маршрутизацией SPA?

> [!summary]
> SSR и SPA-роутинг часто работают вместе: первый request рендерится на сервере по текущему URL, затем после hydration клиентский роутер берет управление переходами на себя и меняет страницы без полной перезагрузки.

## Первый заход на страницу

```text
User opens /products/42
-> server matches route /products/:id
-> server loads product
-> server renders HTML
-> browser shows page
-> React hydrates
```

Это дает SEO и быстрый первый content.

## После hydration

Пользователь кликает внутреннюю ссылку:

```jsx
<Link to="/products/43">Next product</Link>
```

Клиентский роутер:

- перехватывает click;
- меняет URL через History API;
- загружает нужные данные;
- рендерит новый route;
- не перезагружает весь HTML-документ.

## Прямой переход и refresh

Если пользователь нажал refresh на `/products/43`, все начинается заново:

```text
browser requests /products/43
server renders /products/43
client hydrates /products/43
```

Поэтому сервер должен уметь обработать любой публичный route, а не только `/`.

## Единое описание routes

SSR-приложению нужно согласовать маршруты на сервере и клиенте.

Возможные подходы:

- фреймворк сам управляет routes;
- route config используется и сервером, и клиентом;
- file-based routing;
- data router с loaders;
- ручная синхронизация server/client маршрутов.

## Частые ошибки

- сервер не знает frontend route и возвращает 404;
- клиент и сервер используют разные route guards;
- данные на сервере и клиенте загружаются по-разному;
- redirect выполняется только на клиенте, и бот видит закрытую страницу;
- hydration mismatch из-за разных route params или cookies.

## Мини-шпаргалка

- SSR рендерит текущий route при первом request.
- После hydration работает client-side navigation.
- Refresh снова идет на сервер.
- Сервер должен знать routes или иметь fallback/фреймворковый routing.
- Redirect/auth лучше решать до render, если это влияет на HTML.
