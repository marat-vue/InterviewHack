# Как делать distributed locks и какие есть риски Redlock?

> [!NOTE]
> Distributed lock в Redis обычно делают через `SET key value NX PX ttl`. Это полезно для защиты редких critical sections, но lock - не замена транзакциям БД и не магическая гарантия consistency.

## Минимальный lock

```redis
SET lock:job:42 worker-1 NX PX 30000
```

Options:

- `NX` - только если ключа нет;
- `PX` - TTL в миллисекундах.

Если команда вернула OK, lock получен.

## Почему value должен быть уникальным?

Плохо:

```redis
SET lock:job:42 locked NX PX 30000
DEL lock:job:42
```

Если lock истек и его получил другой worker, старый worker может удалить чужой lock.

Лучше:

```ts
const token = crypto.randomUUID();

const locked = await redis.set(lockKey, token, {
  NX: true,
  PX: 30_000,
});
```

Удалять через Lua:

```ts
await redis.eval(
  `
  if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("DEL", KEYS[1])
  end
  return 0
  `,
  {
    keys: [lockKey],
    arguments: [token],
  },
);
```

## Когда lock полезен?

- cache rebuild;
- singleton background job;
- scheduled task deduplication;
- защита от двойного запуска expensive operation;
- миграции/maintenance scripts.

## Когда lock не подходит?

Не используй Redis lock как единственную защиту для:

- денежных операций;
- строгой inventory consistency;
- distributed transactions;
- critical writes без idempotency;
- задач, где нарушение lock недопустимо.

Там нужны DB constraints, transactions, idempotency keys и domain-level checks.

## Что такое Redlock?

Redlock - алгоритм distributed lock на нескольких независимых Redis instances. Вокруг него есть известные споры: он может быть полезен, но требует понимания clocks, network partitions и lease semantics.

Практическое правило:

- для best-effort coordination Redis lock нормален;
- для строгой correctness lock недостаточен без дополнительных гарантий.

## Мини-шпаргалка

- Lock: `SET key token NX PX ttl`.
- Token должен быть уникальным.
- Release через Lua compare-and-delete.
- Lock должен иметь TTL.
- Redis lock - coordination, не замена SQL transaction.
