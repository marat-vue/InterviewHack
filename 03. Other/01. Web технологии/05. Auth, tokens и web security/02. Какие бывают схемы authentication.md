# Какие бывают схемы authentication?

> [!summary]
> Authentication может строиться на server sessions, bearer tokens, JWT, OAuth/OIDC, magic links, passkeys или API keys. Выбор зависит от типа клиента, уровня риска, требований к logout и инфраструктуры.

## Session-based auth

```txt
Browser хранит cookie sid
Server хранит session sid -> userId
```

Плюсы:

- легко отозвать session;
- token не доступен JS, если cookie `HttpOnly`;
- хорошо подходит browser apps.

Минусы:

- нужен session store;
- нужно думать о CSRF;
- сложнее для mobile/non-browser clients.

## Bearer token

```http
Authorization: Bearer access_token
```

Клиент сам добавляет token в header. Подходит для API clients, mobile apps, service-to-service.

Главный риск: кто получил bearer token, тот может использовать его до истечения срока или отзыва.

## JWT

JWT - формат token с claims и подписью.

```json
{
  "sub": "42",
  "role": "admin",
  "exp": 1790000000
}
```

JWT удобно проверять без похода в database, но сложнее мгновенно отозвать.

## OAuth и OIDC

OAuth 2.0 - про delegated access. OpenID Connect поверх OAuth - про login и identity.

Пример: "Войти через Google".

## API keys

```http
X-API-Key: key_123
```

API keys часто используют для server-to-server интеграций. Для пользовательского browser-login это обычно плохой вариант.

## Мини-шпаргалка

- Browser apps часто используют sessions/cookies или token pair.
- Bearer token нужно защищать как пароль.
- JWT самодостаточный, но его отзыв требует стратегии.
- OAuth/OIDC подходят для внешних identity providers.
- API keys - для интеграций, не для обычного user login.
