# Как проектировать Pinia stores в реальном приложении?

> [!summary]
> Хороший Pinia store хранит только действительно разделяемое состояние, имеет понятную границу ответственности и не превращается в склад всего приложения. Store должен быть ближе к domain state, а не к случайным UI-флагам.

## Что стоит хранить в Pinia?

Подходящие данные:

- текущий пользователь;
- permissions;
- корзина;
- выбранная организация;
- глобальные filters;
- состояние onboarding;
- данные, которые нужны нескольким независимым экранам;
- кэш справочников.

## Что не стоит хранить в Pinia?

Часто лучше оставить локально:

- открыт ли маленький dropdown;
- значение input внутри одного компонента;
- hover state;
- временный флаг анимации;
- данные, которые нужны только parent-child паре.

Если state нужен одному компоненту, Pinia обычно лишняя.

## Деление по фичам

```txt
src/
  stores/
    auth.store.ts
    cart.store.ts
    products.store.ts
    settings.store.ts
```

Не делай один `global.store.ts` на все приложение. Его сложно тестировать и поддерживать.

## Store и API layer

Хорошая схема:

```txt
Component -> Pinia action -> API service -> HTTP client
```

```typescript
async loadProducts() {
  this.isLoading = true;

  try {
    this.items = await productsApi.findAll();
  } finally {
    this.isLoading = false;
  }
}
```

Store не обязан знать детали `fetch` headers и base URL. Это можно вынести в API client.

## Auth store пример

```typescript
export const useAuthStore = defineStore("auth", {
  state: () => ({
    user: null as User | null,
    isLoading: false,
  }),
  getters: {
    isAuthenticated: (state) => Boolean(state.user),
    isAdmin: (state) => state.user?.role === "admin",
  },
  actions: {
    async loadMe() {
      this.user = await authApi.me();
    },
    logout() {
      this.user = null;
    },
  },
});
```

## Типичные ошибки

| Ошибка | Почему плохо |
|---|---|
| хранить все формы в Pinia | store раздувается |
| хранить секретные токены без threat model | XSS-риск |
| делать store зависимым от router без необходимости | сложнее тестировать |
| писать бизнес-логику в компонентах и store одновременно | ответственность размазана |
| создавать циклические зависимости между stores | трудно отлаживать |

## Мини-шпаргалка

- Pinia нужна для shared state.
- Локальный UI state оставляй в компоненте.
- Делай stores по фичам.
- API детали лучше вынести в API service.
- Store должен иметь понятную ответственность.
- Не превращай Pinia в глобальную свалку.
