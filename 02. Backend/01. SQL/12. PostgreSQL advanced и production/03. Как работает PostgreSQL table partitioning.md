# Как работает PostgreSQL table partitioning?

> [!NOTE]
> Partitioning делит одну логическую таблицу на физические части. В PostgreSQL declarative partitioning помогает работать с очень большими таблицами, time-series данными, архивированием и быстрым удалением старых периодов.

## Зачем partitioning?

Partitioning полезен, когда:

- таблица очень большая;
- запросы почти всегда фильтруют по дате/tenant/region;
- нужно быстро удалять старые данные;
- нужно хранить старые partitions на другом tablespace;
- индексы одной большой таблицы перестали помещаться в memory.

## Range partitioning

```sql
CREATE TABLE events (
  id bigint GENERATED ALWAYS AS IDENTITY,
  created_at timestamptz NOT NULL,
  payload jsonb NOT NULL
) PARTITION BY RANGE (created_at);

CREATE TABLE events_2026_08 PARTITION OF events
FOR VALUES FROM ('2026-08-01') TO ('2026-09-01');

CREATE TABLE events_2026_09 PARTITION OF events
FOR VALUES FROM ('2026-09-01') TO ('2026-10-01');
```

Range partitioning часто используют для logs/events/orders by date.

## List partitioning

```sql
CREATE TABLE accounts (
  id bigint GENERATED ALWAYS AS IDENTITY,
  region text NOT NULL
) PARTITION BY LIST (region);

CREATE TABLE accounts_eu PARTITION OF accounts
FOR VALUES IN ('eu');
```

## Hash partitioning

```sql
CREATE TABLE user_events (
  user_id bigint NOT NULL,
  payload jsonb NOT NULL
) PARTITION BY HASH (user_id);

CREATE TABLE user_events_p0 PARTITION OF user_events
FOR VALUES WITH (MODULUS 4, REMAINDER 0);
```

Hash partitioning помогает распределить данные, когда нет удобного range/list ключа.

## Partition pruning

Если query фильтрует по partition key, planner может читать только нужные partitions:

```sql
SELECT *
FROM events
WHERE created_at >= '2026-08-01'
  AND created_at < '2026-09-01';
```

Это называется partition pruning.

## Удаление старых данных

Вместо тяжелого:

```sql
DELETE FROM events WHERE created_at < '2025-01-01';
```

можно:

```sql
DROP TABLE events_2024_12;
```

или:

```sql
ALTER TABLE events DETACH PARTITION events_2024_12;
```

## Ограничения

- unique/primary key должны учитывать partition key;
- нужно заранее создавать новые partitions;
- indexes создаются на parent или отдельно на partitions;
- плохо выбранный partition key не поможет;
- слишком много partitions усложняет planning/maintenance.

## Мини-шпаргалка

- Partitioning нужен для больших таблиц.
- Range - даты/диапазоны.
- List - регионы/категории.
- Hash - равномерное распределение.
- Partition pruning работает только при фильтре по partition key.
- Старые данные удобно удалять через drop/detach partition.
