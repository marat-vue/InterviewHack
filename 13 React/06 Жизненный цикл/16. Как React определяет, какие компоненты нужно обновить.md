# Как React определяет, какие компоненты нужно обновить?

> [!summary]
> React не "следит" за каждой переменной в компоненте. Он запускает render при изменении state, props, context или external store, затем строит новое дерево React-элементов и через reconciliation решает, какие части DOM нужно изменить.

## Что запускает обновление?

Основные причины:

- вызов setter из `useState`;
- `dispatch` из `useReducer`;
- новые props от родителя;
- изменение context value;
- обновление external store;
- render родительского компонента;
- изменение `key`.

Пример:

```jsx
function Counter() {
  const [count, setCount] = useState(0)

  return <button onClick={() => setCount(count + 1)}>{count}</button>
}
```

`setCount` сообщает React, что нужно запланировать render.

## Что происходит дальше?

```text
1. Update попадает в очередь
2. React вызывает компонент
3. Компонент возвращает новый JSX
4. React сравнивает новое дерево со старым
5. React применяет минимальные изменения к DOM
```

Render компонента не означает, что DOM обязательно изменится.

## Как React сравнивает элементы?

React смотрит на:

- тип элемента;
- позицию в дереве;
- `key` в списках;
- props;
- children.

Если тип компонента на той же позиции не изменился, React обычно сохраняет состояние. Если тип или `key` изменился, состояние может быть сброшено.

## Почему ребенок может обновиться вместе с родителем?

```jsx
function Parent() {
  const [count, setCount] = useState(0)

  return (
    <>
      <button onClick={() => setCount(count + 1)}>+</button>
      <Child />
    </>
  )
}
```

Когда `Parent` рендерится, React заново рассматривает его поддерево. `Child` может быть вызван снова, даже если props не изменились. Если это реально дорого, используют `memo`, но сначала лучше измерить.

## Мини-шпаргалка

- React обновляет UI после state/props/context/store updates.
- Render - вычисление нового UI.
- Reconciliation решает, что изменилось.
- DOM меняется только на commit-этапе.
- `key` влияет на сопоставление элементов и сохранение state.
