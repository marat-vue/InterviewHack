# Как использовать Storybook в CI и design system?

> [!summary]
> В design system Storybook становится живой документацией компонентов. В CI его можно собирать, проверять stories, запускать interaction/accessibility/visual tests и публиковать статическую версию для команды.

## Storybook как design system

Для дизайн-системы Storybook показывает:

- какие компоненты есть;
- какие props поддерживаются;
- какие состояния предусмотрены;
- как компонент выглядит на разных viewport;
- какие ограничения есть у API компонента.

Пример структуры:

```text
src/shared/ui/Button/Button.vue
src/shared/ui/Button/Button.stories.ts
src/shared/ui/Button/Button.test.ts
```

## Что проверять в CI?

Обычно CI может:

- установить зависимости;
- запустить unit/component tests;
- собрать Storybook;
- запустить interaction tests;
- запустить accessibility checks;
- отправить visual snapshots во внешний сервис;
- опубликовать `storybook-static`.

## Сборка Storybook

```bash
npm run build-storybook
```

Если сборка падает, значит stories или конфигурация сломаны.

## Какие stories нужны design system?

Для каждого компонента полезны:

- Default;
- states: hover/focus/disabled/loading;
- variants;
- sizes;
- invalid/error;
- with long text;
- responsive examples;
- accessibility-critical examples.

## Как не превратить Storybook в мусорную полку?

- Давай stories реальные имена.
- Удаляй устаревшие состояния.
- Не пиши бизнес-логику внутри stories.
- Используй одинаковые данные.
- Поддерживай документацию рядом с компонентом.

## Мини-шпаргалка

- Storybook в CI хотя бы должен собираться.
- Design system нуждается в stories для всех важных states.
- Interaction и accessibility tests можно запускать автоматически.
- Visual tests особенно полезны для UI-kit.
- Storybook должен отражать реальный API компонентов.
