# Production checklist Docker для Nuxt Nitro проекта

> [!NOTE]
> Этот checklist помогает проверить, что Nuxt/Nitro приложение, PostgreSQL, Redis и вспомогательные сервисы готовы к production-like запуску в Docker.

## Image

- Dockerfile использует multi-stage build.
- Final image содержит `.output`, а не весь source tree.
- Приложение запускается командой `node .output/server/index.mjs`.
- Установлены `NODE_ENV=production`, `NITRO_HOST=0.0.0.0`, `NITRO_PORT=3000`.
- `.dockerignore` исключает `.env`, `.git`, `node_modules`, `.nuxt`, `.output`, coverage и logs.
- Base image зафиксирован хотя бы по major/minor, а не `latest`.
- Native dependencies проверены на выбранном base image.
- Container не запускается под root, если приложению не нужны root-права.

## Compose

- Nuxt app, Postgres, Redis и reverse proxy описаны отдельными services.
- App подключается к Postgres по `db:5432`.
- App подключается к Redis по `redis:6379`.
- Наружу опубликован только app или reverse proxy.
- Postgres/Redis ports не открыты наружу в production без необходимости.
- Для Postgres есть named volume.
- Для Redis есть volume и persistence, если Redis хранит важные данные.
- У stateful services есть healthchecks.
- `depends_on.condition: service_healthy` используется для базы и Redis.
- Для app задана restart policy.

## Env и secrets

- Secrets не попадают в Docker image.
- Production secrets не лежат в git.
- `NUXT_PUBLIC_*` содержит только публичные значения.
- Database password не находится в клиентском bundle.
- `DATABASE_URL` и `NUXT_DATABASE_URL` согласованы, если нужны оба.
- Env валидируется на старте приложения.
- Для Docker secrets или secret manager есть понятный способ чтения.

## PostgreSQL

- Есть `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB`.
- Data directory хранится в volume.
- `pg_isready` используется для healthcheck.
- Migrations запускаются один раз controlled step-ом.
- `prisma migrate deploy` используется для production migrations.
- Backup/restore сценарий известен и проверен.
- `5432` не опубликован наружу без причины.

## Redis

- Есть healthcheck через `redis-cli ping`.
- Persistence включена только если нужна.
- Password/ACL настроены для не-dev окружения.
- `6379` не опубликован наружу без причины.
- Client code умеет обрабатывать errors/reconnect.
- Для cache есть TTL и invalidation strategy.
- Для sessions/queues продумана durability.

## Nuxt/Nitro

- Server слушает `0.0.0.0`, а не только loopback.
- Runtime config не смешивает public и private значения.
- API routes используют server-only secrets.
- Health endpoint не раскрывает секреты.
- Если есть WebSocket, reverse proxy передает Upgrade headers.
- Если есть file upload, reverse proxy и Nitro limits согласованы.
- Logs пишутся в stdout/stderr.

## Nginx/reverse proxy

- Передаются `Host`, `X-Forwarded-For`, `X-Forwarded-Proto`.
- Для WebSocket настроены `Upgrade` и `Connection`.
- TLS termination понятен: Nginx, load balancer или внешний provider.
- Static assets можно кешировать, HTML/API - осторожно.
- `client_max_body_size` соответствует требованиям upload.
- Postgres/Redis не доступны через proxy.

## Dev/test

- Dev compose использует bind mount для source code.
- `node_modules` не затирается host mount-ом.
- Test database изолирована от dev/prod.
- Integration tests поднимают отдельные `test-db` и `test-redis`.
- Test DB можно держать на `tmpfs`.
- pgAdmin, RedisInsight, Mailpit, MinIO включаются через profiles.

## Что отвечать на собеседовании?

Я проверяю Nuxt/Nitro Docker-проект по нескольким слоям: image, Compose topology, env/secrets, Postgres, Redis, migrations, reverse proxy и observability. Главные признаки правильной настройки: приложение запускается из `.output`, слушает `0.0.0.0`, зависимости доступны по service names, stateful services имеют volumes и healthchecks, secrets не попадают в image, migrations запускаются отдельно.

## Красные флаги

- `CMD ["pnpm", "dev"]` в production image.
- `DATABASE_URL=postgresql://...@localhost:5432/...` внутри Compose.
- Нет volume для Postgres.
- Все ports открыты наружу.
- `NUXT_PUBLIC_DATABASE_URL`.
- Migration command встроена в каждую app replica.
- Admin tools опубликованы без защиты.
- Redis используется как durable storage без persistence/backup понимания.

## Мини-шпаргалка

- Start: `node .output/server/index.mjs`.
- Host: `NITRO_HOST=0.0.0.0`.
- DB: `db:5432` + volume + healthcheck.
- Redis: `redis:6379` + TTL/persistence decision.
- Migrations: one controlled step.
- Secrets: runtime only, never public.
