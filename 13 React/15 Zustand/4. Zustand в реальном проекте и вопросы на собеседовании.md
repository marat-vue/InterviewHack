# Zustand в реальном проекте и вопросы на собеседовании

> [!summary]
> В реальном проекте Zustand важно использовать умеренно: разделять stores по доменам, читать state через selectors, не хранить server state, не мутировать данные без immer и аккуратно работать с persist.

## Как организовать store?

Пример структуры:

```text
src/
  stores/
    useAuthUiStore.ts
    useCartUiStore.ts
    useEditorStore.ts
```

Store лучше делать не "один на весь мир", а по смысловым областям.

```tsx
export const useEditorStore = create<EditorStore>()((set) => ({
  selectedBlockId: null,
  zoom: 1,
  selectBlock: (id) => set({ selectedBlockId: id }),
  setZoom: (zoom) => set({ zoom }),
}))
```

## Как не словить лишние rerenders?

Читай только нужное:

```tsx
const zoom = useEditorStore((state) => state.zoom)
```

Если нужно несколько полей, можно использовать shallow comparison:

```tsx
import { useShallow } from 'zustand/react/shallow'

const { zoom, selectedBlockId } = useEditorStore(
  useShallow((state) => ({
    zoom: state.zoom,
    selectedBlockId: state.selectedBlockId,
  })),
)
```

## Типичные вопросы

### Чем Zustand отличается от Redux?

Zustand проще, не требует reducer/action boilerplate и позволяет читать store через hook. Redux Toolkit строже и лучше подходит для больших команд, где важны единые conventions, devtools flow и предсказуемость.

### Почему selector важен?

Selector определяет, на какую часть store подписан компонент. Без selector компонент может ререндериться при любом изменении store.

### Что нельзя хранить в persist?

Не стоит сохранять:

- access token, если есть риск XSS;
- большие списки server data;
- временные pending flags;
- ошибки запросов;
- несериализуемые значения вроде функций, class instances, DOM nodes.

### Как сбросить store?

```tsx
type Store = {
  count: number
  reset: () => void
}

const initialState = {
  count: 0,
}

const useStore = create<Store>()((set) => ({
  ...initialState,
  reset: () => set(initialState),
}))
```

## Частые ошибки

- Хранить server state в Zustand.
- Подписываться на весь store.
- Делать один огромный store на весь проект.
- Сохранять в persist чувствительные данные.
- Мутировать state без immer.
- Создавать actions внутри компонентов вместо store.

## Что отвечать на собеседовании?

В production Zustand используют для client state, разделяют stores по доменам, читают данные через selectors и подключают middleware по необходимости. Для server state лучше TanStack Query. Производительность достигается не магией, а точными подписками и стабильной структурой состояния.

## Мини-шпаргалка

- Stores дели по доменам.
- Selector - база оптимизации.
- `useShallow` помогает выбирать несколько полей.
- `persist` применяй выборочно.
- Server state держи в TanStack Query.
