# Как работает cache в Nitro?

> [!NOTE]
> Nitro cache построен поверх storage layer и powered by `ocache`. Кешировать можно handlers через `defineCachedHandler`, обычные функции через `defineCachedFunction`, а также routes декларативно через `routeRules`.

## Зачем нужен cache?

Cache нужен, когда ответ:

- дорогой для вычисления;
- редко меняется;
- зависит от внешнего API;
- одинаков для многих пользователей;
- подходит для stale-while-revalidate;
- может быть переиспользован между запросами.

Примеры:

- список публичных статей;
- каталог;
- GitHub stars;
- CMS content;
- sitemap;
- expensive aggregation.

## Handler cache

```ts
import { defineCachedHandler } from 'nitro/cache';

export default defineCachedHandler(() => {
  return {
    time: Date.now(),
  };
}, {
  maxAge: 60 * 60,
});
```

Ответ кешируется на час.

## SWR

По умолчанию cached handler может отдавать stale value, пока обновляет cache в фоне. Это называется stale-while-revalidate.

Если нужно ждать свежий ответ:

```ts
export default defineCachedHandler(handler, {
  maxAge: 60,
  swr: false,
});
```

## Cache через routeRules

```ts
export default defineConfig({
  routeRules: {
    '/blog/**': {
      cache: {
        maxAge: 60 * 60,
      },
    },
    '/api/catalog/**': {
      swr: 3600,
    },
  },
});
```

`swr: 3600` - shortcut для cache с `maxAge` в секундах и SWR behavior.

## Где хранится cache?

Nitro использует mount point `cache`.

По умолчанию:

- development - filesystem storage во временной директории;
- production - memory driver.

Для production на нескольких инстансах memory cache часто недостаточен. Лучше подключить внешний storage:

```ts
export default defineConfig({
  storage: {
    cache: {
      driver: 'redis',
      url: process.env.REDIS_URL,
    },
  },
});
```

## Cache key

Для cached handler key обычно строится из URL path и search params. Если результат зависит от headers, нужно явно учитывать headers через options вроде `varies`.

Иначе можно получить опасную ситуацию:

```txt
Первый пользователь получил /api/me
Ответ закешировался
Второй пользователь получил чужой response
```

User-specific endpoints обычно не кешируют глобально.

## Что нельзя кешировать без осторожности?

Опасно кешировать:

- `/api/me`;
- dashboard с приватными данными;
- ответы, зависящие от cookie/session;
- auth endpoints;
- POST/PATCH/DELETE responses;
- данные с персональными правами;
- результаты с секретными headers.

## Мини-шпаргалка

- `defineCachedHandler` - cache для endpoint.
- `defineCachedFunction` - cache для обычной функции.
- `routeRules.cache` - декларативный route cache.
- `swr` - stale-while-revalidate shortcut.
- Production cache лучше выносить в Redis/внешний storage.
- Не кешируй user-specific responses без правильного key и varies.
