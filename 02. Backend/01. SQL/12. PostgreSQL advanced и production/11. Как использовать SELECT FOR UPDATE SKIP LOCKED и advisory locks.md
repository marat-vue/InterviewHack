# Как использовать SELECT FOR UPDATE, SKIP LOCKED и advisory locks?

> [!NOTE]
> PostgreSQL дает инструменты явной конкурентности: row locks через `SELECT FOR UPDATE`, неблокирующий разбор очередей через `SKIP LOCKED` и advisory locks для application-level coordination.

## SELECT FOR UPDATE

```sql
BEGIN;

SELECT *
FROM accounts
WHERE id = 1
FOR UPDATE;

UPDATE accounts
SET balance = balance - 100
WHERE id = 1;

COMMIT;
```

`FOR UPDATE` блокирует выбранные строки от конкурентного изменения до конца транзакции.

## NOWAIT

```sql
SELECT *
FROM accounts
WHERE id = 1
FOR UPDATE NOWAIT;
```

Если строка уже заблокирована, запрос сразу падает, а не ждет.

## SKIP LOCKED

Полезно для job queue:

```sql
WITH next_job AS (
  SELECT id
  FROM jobs
  WHERE status = 'pending'
  ORDER BY created_at
  FOR UPDATE SKIP LOCKED
  LIMIT 1
)
UPDATE jobs
SET status = 'processing'
WHERE id IN (SELECT id FROM next_job)
RETURNING *;
```

Несколько workers могут параллельно забирать jobs, не ожидая друг друга.

## Advisory locks

Advisory lock - lock по числовому ключу, не привязанный к строке.

```sql
SELECT pg_try_advisory_lock(12345);
SELECT pg_advisory_unlock(12345);
```

Используют для:

- singleton job;
- migration guard;
- critical section на уровне приложения;
- coordination без отдельной lock table.

## Осторожно

- держи транзакции короткими;
- не жди внешние HTTP calls внутри transaction;
- всегда обрабатывай deadlock/serialization errors;
- advisory locks требуют дисциплины unlock;
- для денег/stock нужны constraints и idempotency.

## Мини-шпаргалка

- `FOR UPDATE` блокирует строки.
- `NOWAIT` не ждет lock.
- `SKIP LOCKED` полезен для queues.
- Advisory locks - application-level locks.
- Long transactions вредят производительности и vacuum.
