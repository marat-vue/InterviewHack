# Как отлаживать контейнеры?

> [!NOTE]
> Отладка Docker обычно начинается с `docker ps -a`, `docker logs`, `docker inspect`, `docker exec`, проверки env, ports, networks, healthcheck и filesystem mounts. В Compose используют аналогичные команды `docker compose logs`, `ps`, `exec`.

## Базовый алгоритм

```bash
docker ps -a
docker logs api --tail=100
docker inspect api
docker exec -it api sh
```

Для Compose:

```bash
docker compose ps
docker compose logs -f api
docker compose exec api sh
```

## Контейнер сразу падает

Смотри:

```bash
docker ps -a
docker logs api
```

Частые причины:

- неправильный `CMD`;
- отсутствует файл `dist/main.js`;
- не установлены dependencies;
- не хватает env;
- приложение не может подключиться к базе;
- порт уже занят;
- permission denied.

## Проблема с портом

Проверить mapping:

```bash
docker ps
docker inspect api
```

Помни формат:

```text
host:container
```

Если приложение слушает только `127.0.0.1` внутри container, снаружи оно может быть недоступно. Нужно слушать `0.0.0.0`.

## Проблема с сетью

Зайти в container:

```bash
docker compose exec api sh
```

Проверить env:

```bash
printenv | sort
```

Проверить DNS:

```bash
getent hosts db
```

Если в image нет debug tools, можно запустить временный container в той же network.

## Проблема с volume

Проверить mounts:

```bash
docker inspect api
docker volume ls
docker volume inspect pgdata
```

Частые симптомы:

- код не обновляется;
- `node_modules` затерт bind mount-ом;
- база потеряла данные после `down -v`;
- permission denied при записи.

## Что отвечать на собеседовании?

Я отлаживаю Docker по слоям: сначала статус containers через `ps -a`, потом logs, затем `inspect` для env/ports/mounts/network, потом `exec` внутрь running container. Для Compose использую `docker compose logs`, `ps`, `exec`. Отдельно проверяю, слушает ли приложение `0.0.0.0`, правильно ли задан service DNS и не потеряны ли volumes.

## Частые ошибки

- Сразу заходить внутрь контейнера, не посмотрев logs.
- Пытаться `exec` в exited container.
- Не проверять env внутри container.
- Подключаться к базе через `localhost`.
- Не смотреть mounts при проблемах с файлами.
- Не различать build problem и runtime problem.

## Мини-шпаргалка

- `ps -a` - увидеть exited.
- `logs` - причина падения.
- `inspect` - ports/env/mounts/network.
- `exec` - внутрь running container.
- `0.0.0.0` для доступности сервера.
- `db`, а не `localhost`, для service DNS.
