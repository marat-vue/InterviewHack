# Как использовать Pinia plugins, testing, SSR и stores outside components?

> [!NOTE]
> Pinia в production - это не только `state`, `getters`, `actions`. Нужно понимать plugins, subscriptions, testing, SSR, stores вне компонентов, HMR, persistence и границы ответственности store.

## Вопрос

Как использовать продвинутые возможности Pinia: plugins, testing, SSR и stores outside components?

## Быстрое подключение

```typescript
import { createApp } from "vue";
import { createPinia } from "pinia";
import App from "./App.vue";

const app = createApp(App);
const pinia = createPinia();

app.use(pinia);
app.mount("#app");
```

Store:

```typescript
import { defineStore } from "pinia";

export const useAuthStore = defineStore("auth", {
  state: () => ({
    user: null as { id: number; name: string } | null,
  }),
  getters: {
    isAuthenticated: (state) => Boolean(state.user),
  },
  actions: {
    async logout() {
      this.user = null;
    },
  },
});
```

## Методы store

| API | Зачем нужен |
| --- | --- |
| `$patch(object)` | изменить несколько полей state объектом |
| `$patch(fn)` | сгруппировать сложную мутацию |
| `$reset()` | сбросить option store к начальному state |
| `$subscribe(callback)` | подписаться на изменения state |
| `$onAction(callback)` | подписаться на запуск/результат actions |
| `$dispose()` | остановить store scope и удалить store из registry |
| `$state` | получить или заменить state |
| `$id` | id store |
| `storeToRefs(store)` | достать state/getters без потери реактивности |

## `$subscribe`

```typescript
const unsubscribe = store.$subscribe((mutation, state) => {
  console.log(mutation.type);
  console.log(state);
});

unsubscribe();
```

Где использовать:

- persistence;
- audit logs;
- debug;
- analytics;
- синхронизация с external storage.

Не стоит прятать бизнес-логику в `$subscribe`. Actions должны оставаться основным местом сценариев.

## `$onAction`

```typescript
store.$onAction(({ name, args, after, onError }) => {
  const startedAt = performance.now();

  after(() => {
    console.log(`${name} finished`, performance.now() - startedAt);
  });

  onError((error) => {
    console.error(`${name} failed`, args, error);
  });
});
```

Где полезно:

- metrics;
- logging;
- tracing;
- plugins;
- test assertions.

## Pinia plugins

Plugin подключается к Pinia instance:

```typescript
const pinia = createPinia();

pinia.use(({ store }) => {
  store.$subscribe((mutation) => {
    console.log(`[${store.$id}]`, mutation.type);
  });
});
```

Plugin получает context:

- `pinia` - Pinia instance;
- `app` - Vue app;
- `store` - конкретный store;
- `options` - options, переданные в `defineStore`.

Пример plugin для persistence:

```typescript
import type { PiniaPluginContext } from "pinia";

export function persistPlugin({ store }: PiniaPluginContext) {
  const key = `pinia:${store.$id}`;
  const saved = localStorage.getItem(key);

  if (saved) {
    store.$patch(JSON.parse(saved));
  }

  store.$subscribe((_mutation, state) => {
    localStorage.setItem(key, JSON.stringify(state));
  });
}
```

Подключение:

```typescript
const pinia = createPinia();
pinia.use(persistPlugin);
```

В production persistence должен учитывать:

- список разрешенных store/fields;
- миграции структуры state;
- sensitive data;
- SSR, где `localStorage` недоступен;
- размер данных.

## Добавление custom properties

```typescript
pinia.use(({ store }) => {
  store.$api = apiClient;
});
```

Для TypeScript нужна module augmentation:

```typescript
import "pinia";

declare module "pinia" {
  export interface PiniaCustomProperties {
    $api: ApiClient;
  }
}
```

## Stores outside components

Внутри компонентов Pinia сама использует active Pinia:

```typescript
const auth = useAuthStore();
```

Вне компонентов важно, чтобы Pinia уже была создана и установлена.

```typescript
// stores/index.ts
import { createPinia } from "pinia";

export const pinia = createPinia();
```

```typescript
// main.ts
import { createApp } from "vue";
import { pinia } from "@/stores";
import { router } from "@/router";
import App from "./App.vue";

const app = createApp(App);

app.use(pinia);
app.use(router);

app.mount("#app");
```

В router guard:

```typescript
router.beforeEach((to) => {
  const auth = useAuthStore(pinia);

  if (to.meta.requiresAuth && !auth.isAuthenticated) {
    return { name: "login" };
  }
});
```

Явная передача `pinia` делает код устойчивее, особенно если guard объявлен в отдельном модуле.

## SSR

В SSR нельзя использовать один singleton Pinia на все запросы. На каждый запрос создают новый app и новый Pinia instance.

Серверная идея:

```typescript
export function createApp() {
  const app = createSSRApp(App);
  const pinia = createPinia();

  app.use(pinia);

  return { app, pinia };
}
```

После server render state сериализуют:

```typescript
const state = pinia.state.value;
```

На клиенте его восстанавливают до mount:

```typescript
pinia.state.value = window.__PINIA_STATE__;
```

Важно:

- state должен безопасно сериализоваться;
- нельзя класть secrets в client state;
- Date/Map/Set требуют нормализации;
- состояние одного пользователя не должно утечь другому.

## Non-reactive dependencies

Если нужно положить router или API client внутрь store/plugin, иногда используют `markRaw`, чтобы Vue не делал объект reactive.

```typescript
import { markRaw } from "vue";

pinia.use(({ store }) => {
  store.router = markRaw(router);
});
```

Но лучше не превращать store в контейнер всех сервисов. Часто dependency injection или явный импорт проще.

## Testing

Store без компонента:

```typescript
import { createPinia, setActivePinia } from "pinia";
import { beforeEach, describe, expect, it } from "vitest";
import { useCounterStore } from "./counter.store";

describe("counter store", () => {
  beforeEach(() => {
    setActivePinia(createPinia());
  });

  it("increments", () => {
    const store = useCounterStore();

    store.increment();

    expect(store.count).toBe(1);
  });
});
```

Компонент с Pinia:

```typescript
mount(UserMenu, {
  global: {
    plugins: [
      createTestingPinia({
        createSpy: vi.fn,
        initialState: {
          auth: { user: { id: 1, name: "Anna" } },
        },
      }),
    ],
  },
});
```

## HMR для stores

```typescript
import { acceptHMRUpdate, defineStore } from "pinia";

export const useUserStore = defineStore("user", {
  state: () => ({ name: "" }),
});

if (import.meta.hot) {
  import.meta.hot.accept(acceptHMRUpdate(useUserStore, import.meta.hot));
}
```

## Частые ошибки

- Использовать store как свалку всех данных приложения.
- Держать sensitive tokens в persisted Pinia state.
- Создать singleton Pinia в SSR и получить утечку данных между пользователями.
- Destructure-ить state без `storeToRefs`.
- Делать actions слишком тонкими, а бизнес-логику размазывать по компонентам.
- Не тестировать stores отдельно от UI.
- Прятать side effects в `$subscribe`.

## Что отвечать на собеседовании

Pinia store имеет служебные методы `$patch`, `$reset`, `$subscribe`, `$onAction`, `$dispose`, `$state`, `$id`, а для destructuring используют `storeToRefs`. Plugins позволяют добавлять persistence, logging, metrics и custom properties. В SSR нужен новый Pinia instance на каждый запрос и безопасная сериализация state. Вне компонентов store вызывают только после установки Pinia или явно передают Pinia instance. Для тестов используют `setActivePinia(createPinia())` или `createTestingPinia`.

## Мини-шпаргалка

- `pinia.use(plugin)` - plugin.
- `$subscribe` - state changes.
- `$onAction` - action lifecycle.
- `storeToRefs` - безопасный destructuring.
- `setActivePinia` - unit tests stores.
- `createTestingPinia` - component tests.
- SSR - новый Pinia на каждый request.
- Persistence - не хранить sensitive data.
