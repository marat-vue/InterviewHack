# Как работают roles, privileges, GRANT, REVOKE и least privilege?

> [!NOTE]
> В PostgreSQL доступами управляют roles и privileges. Production backend не должен подключаться к БД под superuser: ему нужны минимальные права на конкретные schemas/tables/functions.

## Что такое role?

Role может быть:

- пользователем для login;
- группой прав;
- владельцем объектов;
- сервисной ролью приложения.

```sql
CREATE ROLE app_user LOGIN PASSWORD 'secret';
CREATE ROLE app_readonly;
```

## GRANT

```sql
GRANT CONNECT ON DATABASE app_db TO app_user;
GRANT USAGE ON SCHEMA public TO app_user;
GRANT SELECT, INSERT, UPDATE, DELETE ON TABLE users TO app_user;
```

## REVOKE

```sql
REVOKE DELETE ON TABLE users FROM app_user;
```

## Default privileges

Чтобы новые таблицы автоматически получали права:

```sql
ALTER DEFAULT PRIVILEGES IN SCHEMA public
GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO app_user;
```

## Least privilege

Принцип:

```txt
дать ровно те права, которые нужны, и не больше
```

Практика:

- отдельная role для migrations;
- отдельная role для runtime API;
- readonly role для аналитики;
- отдельная role для background workers, если права отличаются;
- запрет superuser в приложении.

## Плохой вариант

```sql
GRANT ALL PRIVILEGES ON DATABASE app_db TO app_user;
```

Так часто дают лишние права.

## Что важно для Prisma/ORM?

ORM runtime user обычно не должен иметь право:

- drop tables;
- alter schema;
- create extensions;
- bypass RLS;
- менять owners.

Migrations запускают отдельной role в CI/CD.

## Мини-шпаргалка

- Role - субъект прав.
- `GRANT` выдает права.
- `REVOKE` забирает права.
- Runtime user не superuser.
- Migrations role и app role лучше разделять.
- Default privileges нужны для будущих tables.
