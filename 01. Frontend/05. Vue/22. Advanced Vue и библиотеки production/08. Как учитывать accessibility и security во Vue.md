# Как учитывать accessibility и security во Vue?

> [!NOTE]
> Vue помогает безопасно экранировать текст и удобно строить интерфейсы, но не делает приложение автоматически доступным и безопасным. Ответственность за HTML-семантику, focus, пользовательский ввод, `v-html`, URL и внешние данные остается на разработчике.

## Вопрос

Как учитывать accessibility и security во Vue-приложении?

## Accessibility: зачем это нужно

Accessibility нужна не только пользователям скринридеров. Хорошая доступность улучшает:

- клавиатурную навигацию;
- формы;
- автотесты;
- SEO для публичных страниц;
- UX на мобильных и слабых устройствах;
- поддержку пользователей с временными ограничениями, например сломанной мышью или плохим зрением.

## Семантика важнее div-ов

Плохо:

```vue
<div class="button" @click="submit">
  Сохранить
</div>
```

Лучше:

```vue
<button type="button" class="button" @click="submit">
  Сохранить
</button>
```

Почему:

- `button` доступен с клавиатуры;
- у него есть role по умолчанию;
- он корректно работает с `Enter`/`Space`;
- его понимают assistive technologies.

## Формы

Каждое поле должно иметь label.

```vue
<script setup lang="ts">
const email = defineModel<string>({
  required: true,
});

defineProps<{
  error?: string;
}>();
</script>

<template>
  <div class="field">
    <label for="email">Email</label>

    <input
      id="email"
      v-model="email"
      type="email"
      autocomplete="email"
      :aria-invalid="Boolean(error)"
      :aria-describedby="error ? 'email-error' : undefined"
    />

    <p v-if="error" id="email-error" role="alert">
      {{ error }}
    </p>
  </div>
</template>
```

Что важно:

- `label for` связан с `input id`;
- error связан через `aria-describedby`;
- `aria-invalid` показывает состояние ошибки;
- `role="alert"` помогает объявить динамическую ошибку.

## Клавиатура

Если делаете кастомный interactive component, он должен работать с клавиатуры.

```vue
<template>
  <button
    type="button"
    :aria-expanded="isOpen"
    aria-controls="menu"
    @click="toggle"
    @keydown.escape="close"
  >
    Меню
  </button>

  <ul v-if="isOpen" id="menu" role="menu">
    <li role="none">
      <button role="menuitem" type="button">Профиль</button>
    </li>
  </ul>
</template>
```

Не добавляйте `role="button"` на `div`, если можно использовать настоящий `<button>`.

## Focus management

Модалки, drawer, popover и dropdown требуют управления focus.

Минимальные правила:

- при открытии focus попадает внутрь модалки;
- при закрытии focus возвращается на кнопку, которая открыла модалку;
- `Escape` закрывает окно, если это ожидаемо;
- фон не должен быть доступен скринридеру как активная область;
- у dialog есть название через `aria-labelledby` или `aria-label`.

```vue
<template>
  <button ref="openButton" type="button" @click="open">
    Открыть
  </button>

  <Teleport to="body">
    <section
      v-if="isOpen"
      ref="dialog"
      role="dialog"
      aria-modal="true"
      aria-labelledby="settings-title"
      tabindex="-1"
      @keydown.escape="close"
    >
      <h2 id="settings-title">Настройки</h2>
      <button type="button" @click="close">Закрыть</button>
    </section>
  </Teleport>
</template>
```

В production часто используют готовые headless/dialog-компоненты, потому что корректный focus trap сложнее, чем кажется.

## Динамические title и route announcements

В SPA переходы между route не перезагружают страницу, поэтому нужно думать о:

- `document.title`;
- focus после навигации;
- landmark-разметке (`main`, `nav`, `header`);
- понятных заголовках страниц.

```typescript
router.afterEach((to) => {
  document.title = `${to.meta.title ?? "App"} | InterviewHack`;
});
```

## Security: что Vue делает сам

Vue экранирует текстовые интерполяции:

```vue
<template>
  <p>{{ userInput }}</p>
</template>
```

Если `userInput` содержит `<script>`, он будет показан как текст, а не выполнен как HTML.

Vue также безопасно устанавливает большинство dynamic attributes через DOM API:

```vue
<a :title="userInput">Ссылка</a>
```

Но это не значит, что можно доверять любому пользовательскому вводу.

## `v-html`

`v-html` вставляет HTML как HTML.

```vue
<template>
  <div v-html="htmlFromServer" />
</template>
```

Это опасно, если HTML не trusted и не sanitized.

Безопаснее:

```vue
<template>
  <p>{{ plainText }}</p>
</template>
```

Если бизнес-задача требует HTML:

- храните HTML только из доверенного источника;
- санитизируйте на backend;
- используйте проверенную sanitization-библиотеку;
- настройте CSP;
- не разрешайте произвольные scripts/events/styles.

## URL injection

Опасный пример:

```vue
<a :href="userUrl">Открыть</a>
```

Если `userUrl` может быть `javascript:alert(1)`, это проблема.

Лучше нормализовать:

```typescript
function safeExternalUrl(value: string) {
  const url = new URL(value);

  if (!["https:", "http:"].includes(url.protocol)) {
    throw new Error("Unsupported protocol");
  }

  return url.toString();
}
```

Или хранить только относительные route paths, если это внутренние ссылки.

## Style injection

Опасный пример:

```vue
<div :style="userStyles" />
```

Если пользователь контролирует весь style object/string, он может ломать UI или использовать CSS как канал атаки/фишинга.

Лучше whitelist:

```typescript
const allowedColors = new Set(["red", "green", "blue"]);

function normalizeColor(color: string) {
  return allowedColors.has(color) ? color : "blue";
}
```

```vue
<div :style="{ color: normalizeColor(userColor) }" />
```

## Никогда не компилировать untrusted templates

Плохая идея:

```typescript
// Не делать так с пользовательским вводом
const template = userProvidedTemplate;
```

Vue templates компилируются в JavaScript. Если template пришел от пользователя, это потенциальное выполнение кода.

Правило: template должен быть частью вашего source code или доверенного build pipeline.

## SSR и безопасность

При SSR нужно дополнительно думать о:

- безопасной сериализации state;
- отсутствии secrets в client payload;
- XSS через inline state;
- разнице server/client окружения;
- escaping данных, попадающих в HTML.

В Nuxt часть задач закрывается фреймворком, но пользовательские `useHead`, server routes, `v-html` и external scripts все равно требуют внимания.

## Частые ошибки

- Делать clickable `div` вместо `button`.
- Убирать outline без replacement focus style.
- Не связывать label и input.
- Делать модалку без focus management.
- Использовать `v-html` для markdown/user content без sanitization.
- Разрешать любые URL в `href`.
- Хранить JWT/access token в небезопасном месте и выводить sensitive data в client state.
- Считать, что TypeScript защищает от XSS.

## Что отвечать на собеседовании

Vue безопасно экранирует текстовые интерполяции, но `v-html`, untrusted URLs, dynamic styles, external scripts и SSR state требуют отдельной защиты. Accessibility во Vue строится на обычной HTML-семантике: правильные элементы, labels, focus, keyboard, ARIA только там, где она действительно нужна. Для модалок и сложных widgets лучше использовать проверенные headless/UI-компоненты или очень внимательно реализовывать WAI-ARIA patterns.

## Мини-шпаргалка

- Используй `button`, `a`, `label`, `main`, `nav` по назначению.
- `aria-*` дополняет семантику, но не заменяет ее.
- `v-html` только для trusted/sanitized HTML.
- Проверяй URL protocols.
- Не компилируй пользовательские templates.
- Управляй focus у модалок и dropdowns.
- Не убирай focus outline без замены.
- Sensitive data не должна попадать в client state без необходимости.
