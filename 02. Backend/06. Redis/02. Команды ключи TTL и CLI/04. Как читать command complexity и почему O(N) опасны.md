# Как читать command complexity и почему O(N) опасны?

> [!NOTE]
> В документации Redis у каждой команды есть time complexity. Это не академическая деталь, а production-навык: Redis single-threaded для выполнения команд, поэтому дорогая команда задерживает остальные.

## Что такое command complexity?

Complexity показывает, как растет стоимость команды:

```txt
O(1)      почти постоянная
O(log N)  растет медленно
O(N)      растет линейно
O(N+M)    зависит от нескольких размеров
```

Пример:

```redis
GET key
```

обычно O(1).

```redis
SMEMBERS huge:set
```

O(N), потому что возвращает все элементы set.

## Почему O(N) особенно опасны в Redis?

Пока Redis выполняет долгую команду, другие команды ждут. Если один клиент запросил огромный `HGETALL`, остальные клиенты могут получить latency spike.

Опасные паттерны:

```redis
KEYS *
HGETALL huge:hash
LRANGE huge:list 0 -1
SMEMBERS huge:set
ZRANGE huge:zset 0 -1
```

## Что использовать вместо больших выборок?

Incremental scan:

```redis
SCAN 0 MATCH user:* COUNT 100
HSCAN user:1 0 COUNT 100
SSCAN online:users 0 COUNT 100
ZSCAN leaderboard 0 COUNT 100
```

Pagination:

```redis
ZRANGE leaderboard 0 49 REV WITHSCORES
```

Bounded ranges:

```redis
LRANGE events 0 99
```

## Как проектировать ключи под complexity?

Плохо:

```txt
all-user-events -> list на миллионы элементов
```

Лучше:

```txt
user:123:events:2026-08
```

или Redis Streams с retention:

```redis
XADD events MAXLEN ~ 100000 * type login userId 123
```

## Как объяснить это на собеседовании?

Ответ:

> Redis быстрый, но скорость зависит от команды и размера структуры. Команда O(N) по огромному ключу может заблокировать event loop. Поэтому в production нельзя делать `KEYS *`, большие `HGETALL` или `SMEMBERS` без лимитов. Нужно использовать SCAN, pagination, TTL, trimming и правильную модель ключей.

## Мини-шпаргалка

- Всегда смотри complexity в docs.
- O(1) и O(log N) обычно безопаснее.
- O(N) может быть нормальным только при малом N.
- Не возвращай огромные коллекции за один request.
- Big keys и full scans - частая причина latency spikes.
