# Что такое idempotency, deduplication и exactly-once myths в Redis?

> [!NOTE]
> В distributed backend почти всегда нужно проектировать повторную обработку. Redis помогает через `SET NX`, TTL и Streams, но не дает магического exactly-once во всей системе.

## Что такое idempotency?

Idempotent operation можно безопасно выполнить несколько раз, результат не сломается.

Пример:

```txt
создать платеж два раза -> плохо
обработать один и тот же webhook два раза -> плохо
пометить email как sent два раза -> обычно нормально
```

## Idempotency key через Redis

```ts
async function reserveIdempotencyKey(key: string) {
  return redis.set(`idempotency:${key}`, 'processing', {
    NX: true,
    EX: 60 * 10,
  });
}
```

Если `SET NX` вернул `null`, такой request уже обрабатывается или обработан.

## Сохранение результата

```ts
await redis.set(`idempotency:${key}:result`, JSON.stringify(result), {
  EX: 60 * 60,
});
```

Повторный запрос может вернуть сохраненный результат.

## Deduplication для Streams

```ts
const dedupeKey = `processed:${stream}:${message.id}`;

const first = await redis.set(dedupeKey, '1', {
  NX: true,
  EX: 60 * 60 * 24,
});

if (!first) {
  await redis.xAck(stream, group, message.id);
  return;
}
```

## Почему exactly-once - миф?

Сообщение может быть:

- доставлено;
- обработано;
- записано в SQL;
- не подтверждено из-за падения worker;
- обработано повторно после recovery.

Поэтому реальная цель - at-least-once delivery + idempotent handler или transactional outbox в SQL.

## Когда Redis недостаточно?

Если операция критична:

- payment;
- inventory;
- billing;
- legal audit;
- irreversible side effect;

используй SQL constraints, unique keys, transactions, outbox pattern и idempotency на доменном уровне.

## Мини-шпаргалка

- `SET NX EX` - базовый dedupe.
- Redis TTL очищает idempotency keys.
- Streams могут доставить сообщение повторно.
- Exactly-once в distributed systems обычно превращается в idempotency.
- Critical operations защищай в source of truth.
