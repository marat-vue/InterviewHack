# Как проектировать connection pooling, PgBouncer и лимиты подключений?

> [!NOTE]
> PostgreSQL connection - не бесплатный объект. Backend с большим количеством инстансов может исчерпать `max_connections`, поэтому production обычно использует connection pool в приложении и часто PgBouncer между приложением и БД.

## Почему нельзя бесконечно открывать connections?

Каждое подключение потребляет:

- memory;
- backend process;
- file descriptors;
- server resources;
- slot в `max_connections`.

Если у тебя 20 API replicas и каждая держит pool на 20 connections, это уже 400 connections.

## App pool

Node.js `pg` пример:

```js
import pg from 'pg';

const pool = new pg.Pool({
  connectionString: process.env.DATABASE_URL,
  max: 10,
  idleTimeoutMillis: 30_000,
  connectionTimeoutMillis: 5_000,
});
```

## PgBouncer

PgBouncer - внешний lightweight connection pooler.

Он помогает:

- уменьшить число real DB connections;
- переживать spikes;
- быстрее открывать logical connections;
- контролировать лимиты.

## Pooling modes

| Mode | Идея |
|---|---|
| Session pooling | connection закреплен за client session |
| Transaction pooling | server connection возвращается в pool после transaction |
| Statement pooling | еще жестче, подходит не всегда |

Transaction pooling популярен, но ломает код, который полагается на session state.

## Что ломается в transaction pooling?

Осторожно с:

- prepared statements;
- session variables;
- temp tables;
- `LISTEN/NOTIFY`;
- advisory locks на session level;
- `SET` вместо `SET LOCAL`.

## Практический расчет

Сначала оцени:

- сколько API replicas;
- max pool size на replica;
- worker processes;
- migrations;
- admin tools;
- BI/reporting connections;
- резерв для maintenance.

## Мини-шпаргалка

- Connections дорогие.
- App pool обязателен почти всегда.
- PgBouncer помогает при большом числе clients.
- Transaction pooling требует осторожности с session state.
- Pool size считают от общего числа replicas, а не одного процесса.
