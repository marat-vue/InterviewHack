# Что делает “Micro-frontend” подход с React?

> [!summary]
> Micro-frontend - это архитектурный подход, при котором большой frontend делят на несколько независимых приложений или модулей. Для пользователя это один продукт, но внутри разные команды могут разрабатывать, собирать и деплоить части интерфейса отдельно.

## Простое определение

```text
Монолитный frontend:
один репозиторий, один deploy, одно приложение

Micro-frontend:
host/shell + несколько независимых frontend-модулей
```

Пример доменного деления:

- `catalog`;
- `cart`;
- `checkout`;
- `profile`;
- `admin`;
- `support`.

## Shell и remotes

Частая схема:

```text
Shell application -> общая рамка, роутинг, providers, layout
Remote applications -> независимые части продукта
```

Пример использования remote-компонента:

```jsx
import { lazy, Suspense } from 'react'

const ProfilePage = lazy(() => import('profile/ProfilePage'))

export function App() {
  return (
    <Suspense fallback={<PageSkeleton />}>
      <ProfilePage />
    </Suspense>
  )
}
```

В реальном проекте remote может поставляться через Module Federation, import maps, отдельный package, iframe или server-side composition.

## Когда micro-frontends оправданы?

Подход полезен, если:

- над продуктом работают несколько независимых команд;
- разные домены релизятся независимо;
- монолитный frontend стал слишком тяжелым организационно;
- есть legacy-части, которые нельзя быстро переписать;
- нужны независимые deploy pipelines.

## Когда подход вреден?

Для маленького и среднего продукта micro-frontends часто дают больше боли, чем пользы.

Сложности:

- общая дизайн-система;
- единая авторизация;
- маршрутизация между приложениями;
- общий state;
- дублирование зависимостей;
- версионирование контрактов;
- мониторинг и логирование;
- производительность начальной загрузки.

## Как делиться данными?

Варианты:

- URL и query params;
- server API;
- shared auth/session layer;
- events;
- общий пакет с типами;
- host-level store для минимального общего состояния.

Плохая идея - делать один огромный глобальный store на все micro-frontends. Это снова связывает команды в монолит, только сложнее.

## Что сказать на собеседовании?

```text
Micro-frontend нужен прежде всего для масштабирования команд и релизов,
а не для ускорения React. Технически его можно реализовать разными способами,
но главные риски лежат в контрактах, shared dependencies, дизайне и общем состоянии.
```

## Мини-шпаргалка

- Micro-frontend делит UI на независимые приложения.
- Shell собирает remotes в один продукт.
- Подход полезен для больших команд и доменов.
- Основные риски: зависимости, дизайн-система, routing, auth, общий state.
- Для небольшого проекта лучше начать с модульной архитектуры внутри одного приложения.
