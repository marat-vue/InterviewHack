# Какие проблемы производительности есть у CSR?

> [!summary]
> CSR, Client-Side Rendering, переносит рендеринг и загрузку данных в браузер. Это может ухудшать первый экран, SEO, LCP, INP и работу на слабых устройствах, особенно если приложение отправляет большой JS-бандл и грузит данные через цепочки `useEffect`.

## Как работает CSR?

Упрощенная схема:

```text
browser -> HTML shell -> JS bundle -> React starts -> fetch data -> render content
```

Пока JS не загружен, не распарсен и не выполнен, пользователь может видеть пустую страницу или loader.

## 1. Медленный первый экран

CSR часто задерживает появление основного контента:

```html
<div id="root"></div>
```

Браузеру нужно:

1. скачать JS;
2. распарсить JS;
3. выполнить JS;
4. запустить React;
5. сделать API-запрос;
6. отрендерить данные.

Это ухудшает FCP и LCP.

## 2. Большой JS-бандл

В CSR на клиент попадает много кода:

- React;
- роутер;
- состояние;
- UI-kit;
- бизнес-логика;
- страницы;
- валидация;
- графики;
- редакторы;
- аналитика.

На мощном ноутбуке это может быть терпимо, а на бюджетном смартфоне - заметно медленно.

## 3. Hydration и main thread

JavaScript выполняется в основном потоке браузера. Пока main thread занят, страница хуже реагирует:

- клики задерживаются;
- ввод тормозит;
- анимации дергаются;
- скролл становится неровным.

Это напрямую связано с INP.

## 4. Waterfall fetching

CSR часто приводит к цепочке:

```text
load JS -> render component -> useEffect -> fetch user -> render -> fetch orders
```

Каждый шаг ждет предыдущий, хотя часть данных можно было бы запросить раньше или параллельно.

## 5. SEO-риски

Поисковые роботы умеют выполнять JavaScript лучше, чем раньше, но CSR все равно создает риски:

- контент появляется не сразу;
- metadata могут быть неполными;
- робот может не дождаться данных;
- слабее социальные превью;
- сложнее индексировать большие сайты.

Для страниц, где важен органический трафик, лучше отдавать meaningful HTML сразу.

## 6. Зависимость от устройства пользователя

В CSR много работы делает клиент:

- рендеринг;
- вычисления;
- форматирование;
- фильтрация;
- сортировка;
- обработка событий.

Чем слабее устройство, тем сильнее проседает UX.

## Когда CSR нормален?

CSR не зло. Он хорошо подходит для:

- личного кабинета после авторизации;
- интерактивных виджетов;
- небольших внутренних инструментов;
- данных, которые не нужны для SEO;
- интерфейсов, где контент зависит от действий пользователя;
- компонентов с частыми browser-only событиями.

В Next.js обычно выбирают гибрид:

```text
Server Component -> основной контент
Client Component -> интерактивный остров
```

## Что отвечать на собеседовании?

Главные проблемы CSR - позднее появление контента, большой JS-бандл, нагрузка на main thread, waterfall fetching и SEO-риски. Браузер должен скачать и выполнить JavaScript до полноценного рендера, поэтому на слабых устройствах и медленных сетях CSR может сильно проигрывать SSR/SSG/RSC. Но CSR подходит для интерактивных частей, где SEO и первый HTML не критичны.

## Частые ошибки

- Называть CSR плохим всегда.
- Грузить SEO-контент через `useEffect`.
- Отправлять тяжелые библиотеки на первый экран.
- Не делать lazy loading для редких модалок и графиков.
- Игнорировать слабые мобильные устройства.
- Сравнивать CSR и SSR только по серверной скорости, забывая CPU браузера.

## Мини-шпаргалка

- CSR рендерит контент в браузере.
- Главная цена - JS download, parse, execute.
- CSR может ухудшить LCP и SEO.
- Большой JS ухудшает INP.
- Частый риск - waterfall в `useEffect`.
- В Next.js CSR лучше оставлять для интерактивных островов.
