# Как frontend-разработчику говорить про SEO?

> [!summary]
> Frontend-разработчик не обязан быть SEO-стратегом, но должен понимать технические последствия своих решений: рендеринг, routing, HTML, meta tags, status codes, performance, accessibility и structured data.

## Какие зоны ответственности у frontend?

На практике SEO для frontend разработчику важно объяснять через конкретные технические решения, а не через абстрактное "улучшить позиции".

- Семантический HTML.
- Head management.
- SSR/SSG/CSR решения.
- Client-side routing.
- Internal links.
- Lazy loading.
- Image optimization.
- Core Web Vitals.
- Accessibility.
- Structured data.
- Проверка rendered HTML.

## Как звучит зрелый ответ?

```text
Я смотрю на SEO не только как на meta tags. Для frontend важны доступный HTML, корректные маршруты, настоящие ссылки, SSR/SSG для публичных страниц, правильные status codes, canonical, structured data и Core Web Vitals. После релиза нужно проверить rendered HTML и Search Console.
```

## Что спросить у SEO-специалиста?

- Какие страницы должны индексироваться?
- Какие страницы должны быть закрыты?
- Какие canonical правила нужны?
- Какие шаблоны title/description использовать?
- Какие фильтры имеют спрос?
- Нужны ли hreflang?
- Какие structured data нужны?
- Какие KPI у релиза?

## Что объяснить команде?

Если команда делает SPA:

```text
Для публичных SEO-страниц CSR может усложнить индексацию и превью. Давайте решим, где нужен SSR/SSG/prerender, а где можно оставить клиентский рендеринг.
```

## Мини-шпаргалка

- Frontend сильно влияет на technical SEO.
- SEO начинается с HTML, URL и статусов.
- SSR/SSG - архитектурное решение, а не косметика.
- Разработчик должен уметь проверить rendered HTML.
- Лучший формат работы - договориться о правилах шаблонов страниц.
