# Как получать params, query, body и headers?

> [!summary]
> NestJS дает parameter decorators для чтения частей request: `@Param`, `@Query`, `@Body`, `@Headers`, `@Req`, `@Ip` и другие. Это делает controller-код декларативным.

## Params

```ts
@Get(':id')
findOne(@Param('id') id: string) {
  return this.usersService.findOne(id);
}
```

`params` - это части URL, которые являются частью route pattern. В запросе `GET /users/42` значение `42` попадет в `@Param('id')`.

По умолчанию `id` приходит строкой, даже если визуально это число. Если service ожидает number, лучше использовать pipe:

```ts
@Get(':id')
findOne(@Param('id', ParseIntPipe) id: number) {
  return this.usersService.findOne(id);
}
```

## Query

```ts
@Get()
findAll(@Query('page') page = '1') {
  return this.usersService.findAll(Number(page));
}
```

`query` - это часть после `?`: `GET /users?page=2&limit=20`.

Для реального endpoint лучше не делать `Number(page)` руками, а использовать pipe или DTO/schema validation:

```ts
@Get()
findAll(
  @Query('page', new DefaultValuePipe(1), ParseIntPipe) page: number,
  @Query('limit', new DefaultValuePipe(20), ParseIntPipe) limit: number,
) {
  return this.usersService.findAll({ page, limit });
}
```

Если query сложный, например `page`, `limit`, `search`, `sortBy`, `sortOrder`, лучше валидировать весь объект через DTO, `ValidationPipe` или Zod pipe.

## Body

```ts
@Post()
create(@Body() dto: CreateUserDto) {
  return this.usersService.create(dto);
}
```

`body` - это payload запроса. Обычно body используют в `POST`, `PUT`, `PATCH`.

```ts
@Patch(':id')
update(
  @Param('id', ParseIntPipe) id: number,
  @Body() dto: UpdateUserDto,
) {
  return this.usersService.update(id, dto);
}
```

В controller лучше не писать бизнес-валидацию вручную:

```ts
if (!dto.email.includes('@')) {
  throw new BadRequestException();
}
```

Такую проверку лучше вынести в DTO validation или Zod schema. Controller должен быть тонким: принять request, передать данные в service, вернуть response.

## Headers

```ts
@Get()
find(@Headers('authorization') authorization?: string) {
  return authorization;
}
```

Headers нужны для auth, tracing, language, content negotiation и интеграций.

```ts
@Get('me')
findMe(
  @Headers('authorization') authorization: string,
  @Headers('x-request-id') requestId?: string,
) {
  return this.usersService.findMe({ authorization, requestId });
}
```

Для авторизации обычно не стоит разбирать `authorization` прямо в каждом controller method. Лучше использовать guard, который один раз проверит token/session и положит пользователя в request.

## Req, Res и стандартный подход NestJS

NestJS позволяет получить весь request:

```ts
@Get()
findAll(@Req() req: Request) {
  return req.query;
}
```

Но в обычном controller лучше использовать `@Param`, `@Query`, `@Body`, `@Headers`, потому что так код проще тестировать и переносить между Express/Fastify.

С `@Res()` нужно быть осторожным:

```ts
@Get('download')
download(@Res() res: Response) {
  return res.download('report.csv');
}
```

Если использовать `@Res()` без `passthrough`, NestJS считает, что ты сам полностью управляешь response. Тогда обычный `return` может перестать работать так, как ожидается.

## Как это выглядит в полноценном controller?

```ts
@Controller('users')
export class UsersController {
  constructor(private readonly usersService: UsersService) {}

  @Get(':id')
  findOne(
    @Param('id', ParseIntPipe) id: number,
    @Headers('x-request-id') requestId?: string,
  ) {
    return this.usersService.findOne({ id, requestId });
  }

  @Get()
  findAll(
    @Query('page', new DefaultValuePipe(1), ParseIntPipe) page: number,
    @Query('limit', new DefaultValuePipe(20), ParseIntPipe) limit: number,
  ) {
    return this.usersService.findAll({ page, limit });
  }

  @Post()
  create(@Body() dto: CreateUserDto) {
    return this.usersService.create(dto);
  }
}
```

## Частые ошибки

| Ошибка | Почему плохо | Как лучше |
|---|---|---|
| Считать `@Param('id')` числом | params приходят строками | `ParseIntPipe` |
| Парсить query руками в controller | много повторов и edge cases | pipe, DTO или Zod |
| Читать `authorization` в каждом method | дублируется auth logic | guard |
| Использовать `@Req()` везде | controller привязывается к платформе | dedicated decorators |
| Использовать `@Res()` без необходимости | можно отключить стандартный response flow | обычный `return` |

## Мини-шпаргалка

- `@Param` читает path params.
- `@Query` читает query string.
- `@Body` читает request body.
- `@Headers` читает headers.
- `@Req` дает весь request, но чаще лучше dedicated decorators.
- `@Res` переводит handler ближе к Express/Fastify-style response handling.
- Params и query приходят строками, поэтому нужны pipes/coercion.
- DTO + ValidationPipe лучше ручного разбора body.
