# Как хранить sessions, tokens, feature flags и temporary state?

> [!NOTE]
> Redis хорошо подходит для short-lived state: sessions, reset tokens, verification codes, OAuth state, feature flags и временные workflow-данные. Главное правило - TTL и понятный namespace.

## Sessions

```redis
SET session:abc '{"userId":"1","role":"admin"}' EX 3600
```

Node.js:

```ts
await redis.set(`session:${sessionId}`, JSON.stringify({
  userId,
  roles,
}), {
  EX: 60 * 60,
});
```

Зачем Redis:

- быстрый доступ;
- общий store для нескольких backend-инстансов;
- TTL;
- быстрое удаление при logout.

## Reset tokens

```redis
SET reset-token:user:1 token-hash NX EX 900
```

Не храни raw token, если можно хранить hash. Тогда утечка Redis не даст готовый reset link.

## Email verification code

```redis
SET verify-email:user:1 123456 EX 600
```

Проверка:

```ts
const savedCode = await redis.get(`verify-email:user:${userId}`);

if (savedCode !== inputCode) {
  throw new Error('Invalid code');
}

await redis.del(`verify-email:user:${userId}`);
```

## Feature flags

Для простого объекта:

```redis
HSET flags:tenant:1 betaDashboard true newBilling false
```

Чтение:

```redis
HGET flags:tenant:1 betaDashboard
```

Для distributed config важно добавить fallback, если Redis недоступен.

## OAuth state

```redis
SET oauth:state:random-state '{"redirectTo":"/dashboard"}' EX 300
```

TTL обязателен, иначе temporary auth state будет накапливаться.

## Что нельзя хранить бездумно?

- plaintext passwords;
- raw refresh tokens без threat model;
- PII без encryption и access controls;
- huge session objects;
- данные, которые обязаны пережить Redis loss без backup.

## Мини-шпаргалка

- Short-lived state в Redis - нормальный backend pattern.
- Всегда ставь TTL.
- Для secrets храни hash/encrypted value, если возможно.
- Session key должен быть random и high entropy.
- Feature flags требуют fallback strategy.
