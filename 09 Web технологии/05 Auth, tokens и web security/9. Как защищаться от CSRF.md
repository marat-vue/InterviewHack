# Как защищаться от CSRF?

> [!summary]
> Защита от CSRF обычно включает CSRF tokens, SameSite cookies, проверку Origin/Referer, запрет state-changing GET-запросов и дополнительное подтверждение для чувствительных операций.

## CSRF token

Server выдает token, а client отправляет его с state-changing request:

```http
POST /api/profile
X-CSRF-Token: random_csrf_token
```

Server проверяет, что token валиден для текущей session.

Атакующий сайт может заставить browser отправить form, но не должен знать правильный CSRF token.

## Double submit cookie

Один из подходов:

```txt
Cookie: csrf=abc
Header: X-CSRF-Token: abc
```

Server сравнивает token из cookie и header. Для более строгой защиты token связывают с session и подписывают.

## SameSite

```http
Set-Cookie: sid=abc; SameSite=Lax; Secure; HttpOnly
```

`SameSite` снижает вероятность автоматической отправки cookie в cross-site request, но не должен быть единственным слоем защиты для чувствительных операций.

## Origin и Referer checks

Server может проверять:

```http
Origin: https://app.example.com
```

Если origin чужой - reject.

Это полезный слой, но нужно учитывать privacy settings, proxies и корректную обработку отсутствующих headers.

## Не меняй состояние через GET

Плохо:

```http
GET /api/delete-account
```

Хорошо:

```http
POST /api/account/delete
```

State-changing operations не должны выполняться через safe methods.

## Мини-шпаргалка

- CSRF tokens - основной слой защиты.
- `SameSite` помогает, но не всегда достаточно.
- Проверяй `Origin`/`Referer` для state-changing requests.
- `GET` не должен менять состояние.
- Для опасных действий можно требовать re-authentication.
