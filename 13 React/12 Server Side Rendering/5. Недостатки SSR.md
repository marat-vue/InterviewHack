# Недостатки SSR

> [!summary]
> SSR улучшает первый HTML и SEO, но добавляет серверную нагрузку, сложность hydration, ограничения серверного окружения и более сложное кеширование. Его нужно выбирать по задаче, а не считать универсальным улучшением.

## Нагрузка на сервер

При CSR сервер часто отдает статические файлы.

При SSR сервер на каждый запрос может:

- проверить cookies;
- загрузить данные;
- выполнить React render;
- собрать HTML;
- встроить данные и asset links.

Это дороже, чем раздать `index.html` с CDN.

## TTFB может стать хуже

TTFB, или Time To First Byte, может увеличиться, потому что сервер думает перед отправкой ответа.

```text
request -> auth -> data fetching -> render -> response
```

Если API на сервере отвечает 800 ms, первый байт HTML тоже задержится.

## Hydration cost

SSR не отменяет клиентский JavaScript. После показа HTML браузер все равно должен:

- скачать bundle;
- распарсить JavaScript;
- выполнить React;
- выполнить hydration;
- подключить события.

На слабых устройствах hydration может быть заметной.

## Browser-only код ломается на сервере

Плохо:

```jsx
function Theme() {
  const theme = localStorage.getItem('theme')

  return <div>{theme}</div>
}
```

На сервере нет `localStorage`, `window`, `document`.

Такой код выносят в `useEffect` или client-only компонент.

## Hydration mismatch

Серверный HTML и первый клиентский render должны совпасть.

Проблемные источники:

- `Date.now()`;
- `Math.random()`;
- `window.innerWidth`;
- locale/timezone differences;
- разные данные на сервере и клиенте;
- невалидная HTML-вложенность.

## Кеширование сложнее

Публичную SSG-страницу легко кешировать.

Персональную SSR-страницу сложнее, потому что HTML может зависеть от cookies, региона, языка и прав доступа.

## Мини-шпаргалка

- SSR дороже для сервера.
- TTFB может увеличиться.
- Hydration все равно нужна.
- Нельзя выполнять browser-only код на сервере.
- Hydration mismatch - частая категория SSR-багов.
