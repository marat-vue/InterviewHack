# Как создавать API routes в Nitro?

> [!NOTE]
> API route в Nitro - это файл, который экспортирует request handler. Nitro автоматически сопоставляет путь файла с URL и, если указан suffix метода, ограничивает route конкретным HTTP method.

## Минимальный route

```ts
// server/routes/api/health.get.ts
import { defineHandler } from 'nitro';

export default defineHandler(() => {
  return {
    status: 'ok',
  };
});
```

URL:

```txt
GET /api/health
```

В Nuxt:

```ts
// server/api/health.get.ts
export default defineEventHandler(() => {
  return {
    status: 'ok',
  };
});
```

URL:

```txt
GET /api/health
```

## Как путь файла превращается в URL?

Standalone Nitro:

```txt
server/routes/api/users.get.ts
  -> GET /api/users

server/routes/admin/reports.ts
  -> /admin/reports
```

Nuxt:

```txt
server/api/users.get.ts
  -> GET /api/users

server/routes/sitemap.xml.ts
  -> /sitemap.xml
```

## Зачем использовать suffix метода?

Suffix метода делает route более явным:

```txt
users.get.ts     -> GET /users
users.post.ts    -> POST /users
users.put.ts     -> PUT /users
users.delete.ts  -> DELETE /users
```

Это помогает:

- не смешивать разные операции в одном файле;
- меньше писать `if (method === 'POST')`;
- лучше видеть API surface в файловой структуре;
- проще тестировать отдельные handlers.

## Какие HTTP methods поддерживаются?

В Nitro method suffix может быть:

| Suffix | Метод | Когда использовать |
|---|---|---|
| `.get.ts` | `GET` | чтение ресурса |
| `.post.ts` | `POST` | создание, команды, формы |
| `.put.ts` | `PUT` | полная замена ресурса |
| `.patch.ts` | `PATCH` | частичное обновление |
| `.delete.ts` | `DELETE` | удаление |
| `.head.ts` | `HEAD` | headers без body |
| `.options.ts` | `OPTIONS` | preflight/service metadata |
| `.connect.ts` | `CONNECT` | редко, proxy/tunnel cases |
| `.trace.ts` | `TRACE` | почти не используют в app API |

## Как писать CRUD routes?

```txt
server/routes/api/users/
  index.get.ts        -> GET /api/users
  index.post.ts       -> POST /api/users
  [id].get.ts         -> GET /api/users/:id
  [id].patch.ts       -> PATCH /api/users/:id
  [id].delete.ts      -> DELETE /api/users/:id
```

Пример:

```ts
// server/routes/api/users/index.post.ts
import { defineHandler } from 'nitro';
import { readValidatedBody } from 'h3';
import { z } from 'zod';

const createUserSchema = z.object({
  email: z.string().email(),
  name: z.string().min(1),
});

export default defineHandler(async (event) => {
  const body = await readValidatedBody(event, createUserSchema);

  return userService.create(body);
});
```

## Где держать бизнес-логику?

Handler лучше делать тонким:

```txt
route handler
  -> validation/auth/request parsing
  -> service
  -> repository/Prisma
```

Пример:

```ts
// server/routes/api/users/[id].get.ts
import { defineHandler } from 'nitro';
import { getRouterParam } from 'h3';

export default defineHandler(async (event) => {
  const id = getRouterParam(event, 'id');

  return userService.findById(id);
});
```

## Мини-шпаргалка

- Один route - один exported handler.
- Файл мапится в URL.
- Method suffix ограничивает HTTP method.
- В Nuxt `server/api/foo.ts` автоматически получает `/api/foo`.
- Handler лучше оставлять тонким.
- Validation, auth и parsing делаются на входе, бизнес-логика уходит в service.
