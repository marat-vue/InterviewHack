# Как поднять Nuxt dev окружение через Docker Compose?

> [!NOTE]
> Dev Compose для Nuxt нужен, когда вся команда хочет одинаковые Node.js, PostgreSQL, Redis и системные зависимости. В dev важны hot reload, bind mount исходников и отдельный volume для `node_modules`.

## Минимальный dev compose

```yaml
services:
  nuxt:
    image: node:22-bookworm-slim
    working_dir: /app
    command: sh -c "corepack enable && pnpm install && pnpm dev --host 0.0.0.0"
    ports:
      - "3000:3000"
    volumes:
      - .:/app
      - nuxt_node_modules:/app/node_modules
    environment:
      NUXT_HOST: 0.0.0.0
      NUXT_PORT: 3000
      DATABASE_URL: postgresql://app:secret@db:5432/app
      REDIS_URL: redis://redis:6379
    depends_on:
      db:
        condition: service_healthy
      redis:
        condition: service_started

  db:
    image: postgres:18
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: secret
      POSTGRES_DB: app
    volumes:
      - pgdata:/var/lib/postgresql/data
    ports:
      - "5432:5432"
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app -d app"]
      interval: 5s
      timeout: 3s
      retries: 10

  redis:
    image: redis:8-alpine
    ports:
      - "6379:6379"

volumes:
  nuxt_node_modules:
  pgdata:
```

## Почему нужен volume для `node_modules`?

Когда ты монтируешь проект:

```yaml
volumes:
  - .:/app
```

host-файлы перекрывают `/app` внутри контейнера. Если `node_modules` установлен внутри image или container, bind mount может его затереть.

Поэтому добавляют отдельный volume:

```yaml
volumes:
  - .:/app
  - nuxt_node_modules:/app/node_modules
```

Так зависимости живут внутри Docker, а исходники редактируются на host.

## Что делать на Windows, если hot reload не видит изменения?

Иногда файловые события через bind mount работают нестабильно. Тогда включают polling:

```yaml
environment:
  CHOKIDAR_USEPOLLING: "true"
  WATCHPACK_POLLING: "true"
```

Это может быть тяжелее по CPU, но для dev-окружения часто приемлемо.

## Где хранить `.env`?

Для dev можно сделать:

```yaml
env_file:
  - .env
```

`.env`:

```env
DATABASE_URL=postgresql://app:secret@db:5432/app
REDIS_URL=redis://redis:6379
NUXT_PUBLIC_SITE_URL=http://localhost:3000
```

Важно: внутри контейнера host базы - `db`, а не `localhost`.

## Как запускать команды?

```bash
docker compose up
docker compose exec nuxt pnpm lint
docker compose exec nuxt pnpm typecheck
docker compose exec nuxt pnpm test
```

Установить пакет:

```bash
docker compose exec nuxt pnpm add @nuxt/image
```

## Когда dev через Docker не нужен?

Если проект простой, вся команда уже использует одинаковый Node.js через `nvm`/`fnm`, а Postgres/Redis поднимаются отдельно, можно запускать Nuxt локально.

Docker dev полезнее, когда:

- есть PostgreSQL, Redis, MinIO, Mailpit, search engine;
- нужны одинаковые версии Node.js и package manager;
- есть native dependencies;
- команда работает на разных ОС;
- надо быстро поднять проект после клонирования.

## Что отвечать на собеседовании?

Для Nuxt dev-окружения через Compose я монтирую исходники bind mount-ом, но `node_modules` держу в отдельном Docker volume, чтобы host не затирал зависимости контейнера. Nuxt запускаю с `--host 0.0.0.0`, Postgres и Redis поднимаю отдельными services, а приложение подключается к ним по DNS-именам `db` и `redis`.

## Частые ошибки

- Запускать dev server без `--host 0.0.0.0`.
- Монтировать проект и случайно затирать `/app/node_modules`.
- Использовать `localhost` в `DATABASE_URL`.
- Каждый раз пересобирать image вместо обычного `docker compose up`.
- Не открывать dev port `3000:3000`.
- Хранить production secrets в dev `.env`.

## Мини-шпаргалка

- Dev command: `pnpm dev --host 0.0.0.0`.
- Source code: bind mount.
- Dependencies: named volume.
- DB host: `db`.
- Redis host: `redis`.
- Hot reload на Windows иногда требует polling.
