# Как выбирать структуру данных Redis под задачу?

> [!NOTE]
> Главная ошибка новичка - класть все в JSON string. Redis силен не только скоростью, а тем, что разные структуры данных дают разные атомарные операции.

## Быстрый выбор

| Задача | Структура |
|---|---|
| Cache JSON ответа | String |
| Объект с частичным обновлением | Hash |
| Counter | String или Hash field |
| Очередь FIFO | List или Stream |
| Reliable event processing | Stream |
| Online users | Set |
| Permissions | Set |
| Leaderboard | Sorted Set |
| Delayed jobs | Sorted Set или Stream |
| Unique visitors approximate | HyperLogLog |
| Daily active boolean flags | Bitmap |
| Nearby locations | Geo |

## Вопрос 1: нужны ли отдельные поля?

Если нужно менять одно поле:

```redis
HSET user:1 lastSeen 1786000000
```

лучше hash.

Если читаешь объект целиком:

```redis
GET cache:user:1
```

string может быть проще.

## Вопрос 2: нужен ли порядок?

Без порядка:

```redis
SADD online user:1
```

С score/rank:

```redis
ZADD leaderboard 100 user:1
```

С append-only событиями:

```redis
XADD events * type login userId 1
```

## Вопрос 3: нужна ли надежная доставка?

Если сообщение можно потерять:

```redis
PUBLISH notifications payload
```

Если нужен retry:

```redis
XADD notifications * payload "..."
```

## Вопрос 4: нужен ли TTL?

TTL задается на весь ключ, не на отдельный field hash.

Если нужны разные TTL для полей, лучше делать отдельные ключи:

```txt
otp:user:1:email
otp:user:1:phone
```

## Вопрос 5: какой размер данных?

Если collection может расти бесконечно:

- добавляй trimming;
- делай pagination;
- разбивай по времени;
- используй TTL;
- мониторь big keys.

## Мини-шпаргалка

- Не начинай с JSON string автоматически.
- Выбирай структуру по нужным операциям.
- Если нужна атомарность, ищи готовую Redis-команду.
- Если нужна история, используй Streams.
- Если нужен rank, используй Sorted Set.
- Если нужна уникальность, используй Set.
