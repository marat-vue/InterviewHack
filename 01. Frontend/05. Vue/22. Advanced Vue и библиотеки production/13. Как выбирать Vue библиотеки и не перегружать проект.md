# Как выбирать Vue библиотеки и не перегружать проект?

> [!NOTE]
> Библиотека должна решать реальную проблему, а не просто быть популярной. В Vue-проекте особенно важно учитывать SSR, bundle size, TypeScript, accessibility, поддержку и конфликт с уже выбранной архитектурой.

## Вопрос

Как выбирать Vue-библиотеки и не перегружать проект?

## Главный принцип

Перед установкой библиотеки нужно ответить на вопросы:

- какую проблему она решает;
- сколько собственного кода она заменяет;
- как она влияет на bundle;
- работает ли с Vue 3, TypeScript, Vite, SSR/Nuxt;
- насколько активна поддержка;
- можно ли заменить ее позже;
- есть ли accessibility и security риски;
- понимает ли команда ее API.

Если библиотека добавляет больше архитектурной цены, чем пользы, ее лучше не ставить.

## Чеклист выбора

| Критерий | Что проверить |
| --- | --- |
| Документация | есть ли актуальные Vue 3 примеры |
| TypeScript | типы встроены или отдельные, нет ли `any` в public API |
| SSR | нет ли прямого `window`/`document` в server render |
| Bundle | сколько KB добавляет, есть ли tree-shaking |
| Accessibility | keyboard/focus/ARIA для UI-компонентов |
| Theming | можно ли встроить в design system |
| Testing | легко ли mock/test |
| Maintenance | свежие релизы, issues, совместимость |
| License | подходит ли для коммерческого проекта |
| Escape hatch | можно ли заменить или обернуть |

## Pinia или composable

Pinia:

- global business state;
- user/session/cart/permissions;
- devtools;
- plugins;
- SSR state transfer;
- testing helpers.

Composable:

- local reusable logic;
- browser API;
- form state внутри feature;
- derived state;
- маленький shared UI-state.

Правило: если появляются actions, persistence, несколько экранов и важный debugging - выбирайте Pinia.

## Vuetify или Tailwind/headless

Vuetify:

- быстрее собрать admin/dashboard;
- много готовых компонентов;
- единая Material Design-система;
- хорош для internal tools.

Tailwind + headless components:

- больше контроля над дизайном;
- проще уникальный UI;
- меньше зависимости от конкретного component framework;
- больше ответственности за accessibility и states.

Неудачный компромисс - подключить Vuetify, Tailwind, еще одну UI-библиотеку и писать поверх них много CSS overrides без правил ответственности.

## VueUse или свой composable

VueUse стоит брать, если:

- задача типовая;
- есть SSR-aware реализация;
- нужен cleanup;
- команда уже использует VueUse;
- API понятнее самописного helper-а.

Свой composable лучше, если:

- логика доменная;
- нужен маленький wrapper на 10 строк;
- VueUse composable слишком общий;
- нужно жестко контролировать API.

## Motion или CSS transitions

CSS transitions:

- hover/fade/expand;
- простые enter/leave;
- минимум runtime;
- легко поддерживать.

Motion:

- сложные gestures;
- spring animations;
- scroll animations;
- choreography;
- shared animation patterns.

Правило: не ставить animation library ради одного fade.

## Vite plugins

Vite plugins полезны для:

- Vue SFC;
- auto imports;
- components auto registration;
- Vuetify integration;
- SVG as components;
- bundle analysis;
- generated routes.

Но каждый plugin меняет build pipeline. Нужно понимать:

- что он генерирует;
- как типы попадают в проект;
- работает ли в tests;
- работает ли в SSR;
- как debug-ить результат.

## Библиотеки, которые часто встречаются в Vue-проектах

| Задача | Частые варианты | Когда нужны |
| --- | --- | --- |
| Forms validation | `vee-validate`, `zod`, `valibot` | сложные формы, схемы, backend-compatible validation |
| I18n | `vue-i18n` | мультиязычность, pluralization, locale messages |
| Server state | TanStack Query for Vue | cache, retries, invalidation, pagination, background refetch |
| Headless UI | Reka UI, Headless UI Vue | accessible primitives без готового visual style |
| Tables | TanStack Table, Vuetify Data Table | сложные таблицы, sorting/filtering/pagination |
| Virtual lists | `vue-virtual-scroller` | тысячи элементов в списке |
| Charts | ECharts, Chart.js wrappers | dashboards, analytics |
| Dates | `date-fns`, Day.js | форматирование и расчеты дат |
| Icons | `lucide-vue-next`, MDI | кнопки, navigation, actions |
| Auto imports | `unplugin-auto-import` | меньше ручных imports, но нужны generated types |
| Components auto import | `unplugin-vue-components` | auto registration, особенно с UI libraries |
| File-based routing | `unplugin-vue-router` | route generation и typed routes |

Эти библиотеки не обязательно должны быть в каждом проекте. Это список кандидатов, которые стоит знать и оценивать по задаче.

## Как безопасно внедрять библиотеку

1. Сделать маленький proof of concept.
2. Проверить TypeScript и SSR.
3. Проверить bundle через analyzer.
4. Проверить accessibility на ключевых сценариях.
5. Обернуть библиотеку в локальный adapter/component, если API может поменяться.
6. Добавить 1-2 теста на критический сценарий.
7. Зафиксировать правило использования в проектной документации.

## Adapter pattern

Вместо использования внешней библиотеки по всему проекту можно сделать локальный wrapper.

```vue
<!-- AppButton.vue -->
<script setup lang="ts">
defineProps<{
  variant?: "primary" | "secondary" | "danger";
}>();
</script>

<template>
  <v-btn
    :color="variant === 'danger' ? 'error' : 'primary'"
    variant="flat"
  >
    <slot />
  </v-btn>
</template>
```

Плюсы:

- проще заменить UI library;
- единый API для команды;
- меньше дублирования props;
- легче контролировать accessibility.

Минусы:

- нельзя оборачивать все подряд;
- wrapper должен упрощать, а не скрывать половину возможностей.

## Признаки перегруженного проекта

- Несколько UI-kit одновременно без ясных границ.
- Одна задача решается тремя разными библиотеками.
- Bundle растет, а пользовательская ценность нет.
- В проекте много adapters без реальной пользы.
- Команда боится обновлять зависимости.
- Сложно написать тест без большого количества mocks.
- SSR ломается из-за browser-only packages.

## Частые ошибки

- Выбирать библиотеку по популярности, а не по задаче.
- Не проверять SSR/Vite/TypeScript до внедрения.
- Игнорировать accessibility у UI components.
- Не анализировать bundle.
- Ставить TanStack Query там, где хватает одного `fetch`.
- Ставить Pinia для состояния одного компонента.
- Ставить Vuetify и пытаться сделать из него полностью другой дизайн.

## Что отвечать на собеседовании

Библиотеку во Vue выбирают по задаче, совместимости с Vue 3/Vite/TypeScript/SSR, качеству документации, bundle size, accessibility, поддержке и возможности замены. Pinia нужен для shared business state, VueUse - для типовых composables, Vuetify - для готового Material UI, Tailwind/headless - для кастомного дизайна, TanStack Query - для сложного server state. Хороший production-подход - проверять библиотеку через PoC, держать критические интеграции за adapters и не смешивать несколько решений одной задачи.

## Мини-шпаргалка

- Не каждая популярная библиотека нужна проекту.
- Проверяй SSR, TS, bundle, a11y, maintenance.
- Pinia - business state.
- VueUse - browser/composable utilities.
- Vuetify - готовый UI-kit.
- Tailwind/headless - кастомный UI.
- TanStack Query - server state.
- Adapter помогает не привязать весь проект к external API.
