# Как dockerize Next.js приложение?

> [!summary]
> Next.js приложение обычно собирают через multi-stage Dockerfile. Для production важно учитывать standalone output, server runtime, переменные окружения, static assets и разницу между build-time и runtime env.

## Базовая идея

Next.js может работать не как статический frontend, а как серверное приложение:

- SSR;
- Route Handlers;
- Server Actions;
- Image Optimization;
- middleware;
- dynamic rendering.

Поэтому production image часто запускает Node.js server, а не только Nginx static files.

## next.config.ts

Для компактного Docker image удобно включить standalone output:

```ts
import type { NextConfig } from 'next'

const nextConfig: NextConfig = {
  output: 'standalone',
}

export default nextConfig
```

Next.js соберет минимальный server output в `.next/standalone`.

## Production Dockerfile

```dockerfile
FROM node:22-alpine AS deps
WORKDIR /app
COPY package*.json ./
RUN npm ci

FROM node:22-alpine AS build
WORKDIR /app
COPY --from=deps /app/node_modules ./node_modules
COPY . .
RUN npm run build

FROM node:22-alpine AS runner
WORKDIR /app
ENV NODE_ENV=production

COPY --from=build /app/public ./public
COPY --from=build /app/.next/standalone ./
COPY --from=build /app/.next/static ./.next/static

USER node
EXPOSE 3000
CMD ["node", "server.js"]
```

## Compose пример

```yaml
services:
  web:
    build: .
    ports:
      - "3000:3000"
    environment:
      NODE_ENV: production
      DATABASE_URL: postgres://app:secret@db:5432/app
    depends_on:
      db:
        condition: service_healthy

  db:
    image: postgres:18
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: secret
      POSTGRES_DB: app
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app -d app"]
      interval: 5s
      timeout: 3s
      retries: 10
```

## Build-time и runtime env

В Next.js важно отличать:

- build-time env - используется во время `next build`;
- runtime env - доступна server code при запуске container;
- public env `NEXT_PUBLIC_*` попадает в client bundle.

Нельзя класть секреты в `NEXT_PUBLIC_*`.

## Что отвечать на собеседовании?

Next.js в Docker обычно собирают multi-stage Dockerfile. Для production часто используют `output: 'standalone'`, затем копируют `.next/standalone`, `.next/static` и `public` в runtime image и запускают `node server.js`. Нужно понимать разницу build-time/runtime env и не помещать secrets в `NEXT_PUBLIC_*`.

## Частые ошибки

- Раздавать Next.js SSR приложение как обычный static Vite build.
- Не копировать `.next/static`.
- Не включить standalone output и получить огромный image.
- Класть secrets в `NEXT_PUBLIC_*`.
- Ожидать, что build-time env можно поменять после build для клиентского кода.
- Запускать container под root.

## Мини-шпаргалка

- Next SSR требует Node runtime.
- `output: 'standalone'` уменьшает image.
- Копируй `.next/standalone`, `.next/static`, `public`.
- Запуск: `node server.js`.
- `NEXT_PUBLIC_*` публично.
- Runtime env работает для server code.
